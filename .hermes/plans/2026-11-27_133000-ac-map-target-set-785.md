# Make the plan's acceptance-criteria map point only at files it can actually deliver (#785)

**Issue:** [agent-eve#785](https://github.com/ricardoblackskye/agent-eve/issues/785) (`bug`)
**Branch:** `fix/785-ac-map-target-set` (from `origin/main` @ `e9522d3`, 0 behind)
**Status:** plan only. No code until GATE 1.

## Why we are doing this

A plan tells an approver two things: which files it will write, and which test file covers each acceptance criterion.
Nothing checks that those two agree. So a plan can promise, in prose, to write a test file - omit that file from the
list of files it will write - and still map four acceptance criteria to it, and still pass validation.

That is not hypothetical. R4's measurement produced exactly this plan on the second of two runs of an identical
story, and it passed validation. R2 already stops the run from writing a file outside its approved set, so the write is
contained - but by then the approver has approved a plan whose own evidence cannot be produced, and the acceptance
criteria are mapped to a file the run was never allowed to touch. That is the defect #764 fixed at the DoD, reappearing
one layer earlier, in the artifact approval rests on.

**What changes:** a plan whose acceptance-criteria map names a test file that it will neither write nor find in the
repository is refused, with a message naming the file and the target set.

**What this does not change:** the plan may still map criteria to a test file it does not modify, when that file
already exists - reusing an existing suite is legitimate and common. And nothing here inspects the plan's prose: the
"a new X" wording for an existing file cannot be judged mechanically, which is a stated limit of this fix rather than
something it pretends to solve.

## Design

1. **The rule, in the precise form.** Refuse when a mapping's `testFile` appears in neither `plan.targetFiles` nor
   `context.files`. A plan may reuse an existing suite, or write a new one - it may not point at a file that is neither
   in its target set nor present in the repository, because that mapping can never be satisfied by anything the run
   does.
2. **Why not the stricter "must be in targetFiles".** Because it would refuse legitimate plans: reusing an existing
   test file to cover a criterion is correct behaviour, and the probe shows it happens. A rule that refuses correct
   plans is the one that gets worked around.
3. **Where the existence case comes from.** `context.files` is already passed by the runner at both call sites - #770
   added that seam - so this needs no new plumbing.
4. **A stated limit, and it matters.** This will **not** catch Run B. Run B's `testFile` (`src/App.test.jsx`) *does*
   exist, so the rule above is satisfied; Run B's defect is that its **prose** promises a new file while its target set
   omits it. That is not mechanically judged from the plan structure, and the containment for that instance is
   #764's fix at the DoD: if the case was never executed, `done` is withheld rather than certified.

## Tasks

### Task 1 (RED) - a mapping to a file the plan neither writes nor finds is refused

The clean-cut case: `testFile` absent from `targetFiles` and absent from `context.files`.

### Task 2 (control) - reuse is not refused

A mapping to an existing file that is not a target proceeds. Without this, the rule would forbid reusing a suite, and
would break the plans that legitimately do.

### Task 3 (control) - a mapping to a targeted file proceeds

The ordinary case, which must not regress.

### Task 4 - the message names the file and the target set

A refusal that says only "invalid mapping" leaves a repair round re-guessing, the same reason R3's refusals name the
replacement.

### Task 5 - verify the neighbors

The R3 lesson, learned twice: a new refusal rule is exactly what breaks existing fixtures. Run the plan-validator,
architect-repair and runner-park suites **with** this change, not after it.

## Out of scope

- **Judging the prose.** Run B's wording ("A new `src/App.test.jsx`") for a file that exists is not mechanically
  decidable, and a heuristic that guesses would be worse than the stated limit.
- **The selector decision from R4** (#781) - separate, and a design change rather than a check.
- **Consolidating the path normalizer.** R2's lives in `approved-target-set.ts` and R3's in `plan-validator.ts`; a
  shared home is a tidy-up, and folding it in here would widen a bug fix into a refactor.
