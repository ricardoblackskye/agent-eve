# Dark Factory Run Query API Implementation Plan

> **For Hermes:** Implement this plan with strict RED→GREEN→REFACTOR TDD, one behavior at a time. Do not start implementation until the user approves this plan.

**Goal:** Add an authenticated, provider-neutral read API over the durable Dark Factory run ledger, including bounded list/detail queries, filters, and aggregate metrics for the progress board.

**Architecture:** Keep query semantics and DTOs independent of Next.js
request/response types and storage drivers. Extend the canonical `RunHistoryStore`
read contract for date filtering and aggregates, implement it consistently for
SQLite and PostgreSQL, then expose it through thin authenticated HTTP route
adapters. Reuse the existing signed `eve_session` authentication without
introducing Vercel dependencies.

**Tech Stack:** TypeScript, Next.js App Router Route Handlers, Vitest, existing SQLite and PostgreSQL run-history adapters, existing `jose` session verification.

## Scope and proposed API contract

### Endpoints

1. `GET /api/dark-factory/runs`
   - Filters: repeated `status` values, `repo`, positive `issue`, inclusive UTC `from`, exclusive UTC `to`.
   - Bounded keyset pagination: default page size 25, maximum 100; expose an opaque validated cursor rather than the store cursor shape.
   - Returns canonical run summaries and an optional next cursor, newest first with deterministic tie-breaking.
2. `GET /api/dark-factory/runs/{runId}`
   - Returns the canonical summary and an ascending-sequence page of lifecycle events, with a bounded event limit and continuation cursor.
   - Preserve “not found” separately from store/configuration failure.
3. `GET /api/dark-factory/metrics`
   - Supports a bounded UTC date range and optional repository filter.
   - Returns counts for every canonical status (including `aborted` separately), aggregate measured-cost/latency summaries with observation counts, and a daily terminal-outcome trend grouped by `completedAt`.
   - Duration summaries use only runs with both `startedAt` and `completedAt`. Missing cost/latency/duration observations remain absent; never synthesize zeroes. Current non-terminal statuses remain available in status counts and are not presented as terminal outcomes in the trend.

All responses are JSON, `private, no-store`, and use a stable generic error envelope. Invalid query input maps to 400, missing/invalid viewer session to 401, missing run to 404, and unavailable/unconfigured storage to 503. Never return database errors, connection details, provider credentials, or internal provider identifiers to the caller.

### Authentication and portability

- Add a small viewer-auth interface at the HTTP edge and an initial adapter that validates the existing `eve_session` cookie with the configured session secret. Keep Next.js types in the route adapter only; query services take plain typed inputs and a `RunHistoryStore` dependency.
- Keep the API route protected by the existing fail-closed `proxy.ts` policy as defense in depth. Do not add these endpoints to public path allow-lists.
- Do not introduce a Vercel SDK or a new viewer-auth environment variable for this increment. If implementation discovery shows a genuinely required provider selector, stop and propose it before changing deployment configuration.

## Risks and decisions

- **Trend semantics:** the proposed series counts terminal outcomes by `completedAt`; active/blocked/queued counts remain in current status totals. This avoids pretending the current-summary ledger is a historical status-event time series.
- **Pagination:** public cursors must be size-bounded and validated before passing values to the store; SQL values remain parameterized.
- **Authentication:** the app-wide proxy already protects unknown API paths, but handlers need an explicit viewer-auth seam so route behavior is testable and is not dependent on one hosting platform's middleware.
- **Data exposure:** report only canonical summaries/events and generic failures; no raw worker prompts, findings text, database URLs, or SQL error messages.
- **Scope boundary:** no dashboard UI, visual design, Vercel-specific storage/hosting/auth SDK, realtime transport, writes, or PR merge behavior; those remain outside #199 (the UI is #200).
- **PostgreSQL test availability:** PostgreSQL integration tests are opt-in via `DF_RUN_HISTORY_TEST_DATABASE_URL`; never point them at production or print the URL.
