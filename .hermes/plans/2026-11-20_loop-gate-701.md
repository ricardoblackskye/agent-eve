# 701 - the loop's gate is not the target's gate

**Goal:** make a run's own verdict mean what it reads as. Today the coding loop verifies a change with the
target's *unit* tests and then reports `PASS`, which is read - by the run, the record and the operator - as
"this work is verified". The target's e2e suite is never run, so a run can satisfy every gate it has, open a
pull request, and have that pull request fail CI.

**Architecture:** the repository already has the seam this needs, and a rule about how to use it. `resolveLintCommands`
reads the target's `package.json` and turns *its own* script names into commands (`#659`), and
`workspaceCommandsFor` widens the run's allow-list with them. `ALLOWED_WORKSPACE_COMMAND_PREFIXES` is NOT
widened in place, because `#437` settled that a consumer states its own command set rather than increasing
the Developer Agent's blast radius. This change follows that pattern for e2e, and adds the thing that is
missing regardless of whether the e2e can run: an honest statement of what the gate did **not** run.

**Tech stack:** TypeScript, Vitest, the sandbox command seam, the loop's existing `feedback` channel (`#373`).

---

## Root cause - verified

The loop's allowed commands (`agent/lib/dark-factory/developer-agent.ts:567`) are:

```ts
export const ALLOWED_WORKSPACE_COMMAND_PREFIXES: readonly string[] = [
  "npx vitest",
  "npm test",
  "npx tsc",
];
```

and its verdict is a two-word summary of one of them (`scripts/dark-factory-runner.ts:1435`):

```ts
`     Test result: ${testOutcome.passed ? "PASS" : "FAIL"}`
```

So `PASS` is true of the unit suite and silent about everything else. #701's own evidence, run
`e1af302b` against WebFeedPOC#237:

- the loop printed `Test result: PASS`; the PR's `test` job was green;
- the PR's `e2e` job failed **9 / 765** - `expect(page.locator('footer')).toBeVisible()` hit a Playwright
  strict-mode violation because the run had added a second `<footer>`;
- and the DoD, which could see it, had no way to act.

**One line of that issue is now stale and worth correcting in the record**: it says the DoD "has no sandbox
and no fix capability". `#718` gave it both, and PR #251 carries the fix cycle's own commit as proof. What
remains is #701's core: the loop cannot see the failure in the first place, so the DoD is left to discover
it ~30 minutes later and repair it at the end, instead of the loop catching it before the PR exists.

## Intended fix

### Leg 1 - the verdict names its suites

The cheap half, and the one that is correct even if the e2e can never run in the sandbox: the verdict says
what it ran and what it did not.

```text
Test result: PASS (unit) - NOT run: e2e
```

`PASS` keeps meaning "what this gate ran, passed"; it stops implying the rest. There is already a precedent
for a verdict that reports its own limits - `Test result: COULD NOT RUN - the tests did not start`
(`scripts/dark-factory-runner.ts:1393`) - so this is the same idea applied to suites rather than to starts.

### Leg 2 - the target's e2e is resolved, declared, and attempted

- `resolveE2eCommand(packageJson)`, modelled exactly on `resolveLintCommands`, returns the target's own
  script when it has one (`e2e`, then `test:e2e`) and `[]` when it does not. A repository without an e2e
  suite is not made to pay for one.
- The command reaches the sandbox through the existing `#659` seam - a consumer's own command set - not by
  widening `ALLOWED_WORKSPACE_COMMAND_PREFIXES` in place, per `#437`.
- The loop attempts it **after** the unit suite passes, and a failure is fed back through the same
  `feedback` channel the loop already uses for a failing iteration (`#373`), so the agent gets the
  diagnostics and a chance to correct itself while it still has iterations left.
- Bounded like every other loop action: the existing self-correction budget and circuit breaker apply
  unchanged, so a target whose e2e cannot pass cannot spend the run's whole budget on it.

### Leg 3 - where it cannot run, say so

The e2e needs browsers, and the sandbox image may not have them. When the command cannot start, the loop
must report `NOT run` rather than `PASS` - the same rule as leg 1, reached for a different reason. The probe
is a capability question, not a guess: attempt it and classify the outcome.

## Risks and open questions

- **Does the sandbox image have browsers?** Unknown, and it decides whether leg 2 is a real gate on day one
  or a capability probe that reports `NOT run`. The plan is written so that either answer is correct
  behaviour rather than a failure. Worth measuring before claiming the e2e is gated.
- **The e2e is slow (~30 minutes on WebFeedPOC).** Running it inside the loop makes an iteration much longer,
  and the loop's budget is iterations, not minutes. It may want its own bound, and the run's cost estimate
  should reflect it.
- **Unit-then-e2e ordering is deliberate**: a failing unit suite should not pay for a browser suite.
- **`#720` interaction.** A generated test that cannot run in the sandbox already burns the
  self-correction budget; adding another command increases the surface for that class, which is another
  reason leg 1 lands first.
- **Not in scope**: the sandbox lint gap the issue notes in passing (`npm run lint` failing on a missing
  `typescript-eslint` in the checkout). Same family, different cause; it should be its own issue.
