# Plan: close the loop on the target's linting before reporting done (#659)

**Issue:** #659
**Branch:** `feat/df-lint-gate-659`
**Base:** `origin/main` @ `695409f` (includes the merged #631 and #657)

## Goal

A run does not report `done`, and does not leave a PR that fails the target's own checks, while its
changed files violate the target repository's linting.

## Evidence

PR ricardoblackskye/WebFeedPOC#209 (the e2e run for WebFeedPOC#208) reported `DoD Status: done` /
`Is DONE (ok): true` while its MegaLinter job FAILED. From the job log:

| Finding                                                       | File                              | Caused by    |
|---------------------------------------------------------------|-----------------------------------|--------------|
| cspell `Unknown word (behavioural)`                           | `.hermes/plans/df-208.md:32:217`  | the run      |
| markdownlint `MD034/no-bare-urls` on `http://localhost:5173/` | `.hermes/plans/df-208.md:103:272` | the run      |
| lychee `Connection refused` on the same URL                   | `.hermes/plans/df-208.md:103:272` | the run      |
| markdown-table-formatter, one error                           | `.hermes/plans/df-208.md`         | the run      |
| osv-scanner `minimatch 10.2.6 -> 11.0.1`                      | `package-lock.json`               | PRE-EXISTING |

Every failure the run caused is inside its OWN artifact - a file the factory writes, commits and never
lints. Reproducible: PR #207 (from the #206 run) also failed both MegaLinter runs.

## What already exists (do not rebuild)

- **The DoD review loop.** `runDefinitionOfDone` already calls `deps.runChecks(round)`, turns the result
  into findings, can `attemptFixes`, and re-checks under a budget - and `FindingSource` ALREADY includes
  `"linter"` (`definition-of-done.ts:55`).
- **The run's changed-file set.** `filesToCommitFromRun(authored, plan, extraPaths)` (#361) is the honest
  list of what the run produced, which is the scope a lint gate wants.
- **The unmeasured-versus-failed discipline** for a command that could not start (#541).
- **The sandbox command allow-list.** ONE shared list, `ALLOWED_TEST_COMMAND_PREFIXES`, consumed by both
  the in-process runner and the sandbox driver.

## The gap (four parts)

1. `runChecks` is fed `execSync("npx tsc --noEmit")` in the RUNNER's working directory. On the vault path
   the run's code lives in the SANDBOX, so that type-check inspects a tree WITHOUT the run's changes - a
   check that cannot fail on the thing it claims to check.
2. The sandbox allow-list permits only test commands, so a lint command is REFUSED by the driver.
3. The sandbox is DISPOSED when the coding phase ends, and the DoD runs afterwards - so a lint gate
   cannot live in the DoD and still see the sandbox's output.
4. Nothing reads the PR's own checks, which is where the target's REAL gate (MegaLinter) runs.

## Approved approach (user: Both)

- **Stage 1 - the artifact.** Harden `renderPlanFile`: its own lines are already sanitised (MD013, MD040,
  MD024, MD026, MD034), but MODEL PROSE is embedded verbatim, and that is where the bare URL and the
  table came from. A bare URL becomes a link or a code span; a table is emitted in the pinned formatter's
  shape.
- **Stage 2 - (B), the inner gate.** In the sandbox, after the tests pass, run the TARGET's own lint over
  the run's CHANGED files. A failure is a FAILED ITERATION, so the existing self-correction loop fixes it
  the same way it fixes a failing test.
- **Stage 3 - (A), the authoritative outer gate.** The DoD's `runChecks` reads the PR's check runs on the
  current head. A failing check becomes a `"linter"` finding, so the existing fix-and-re-check loop runs
  and `done` follows only when they are green.

### What (B) can and cannot catch - measured, not assumed

WebFeedPOC declares `lint` (`eslint .`), `typecheck` (`tsc --noEmit`) and `format` (prettier), and ships
`.mega-linter.yml`. So (B) catches JS/TS findings and prettier's markdown findings, but NOT the
cspell/lychee findings that MegaLinter raises. That is why (A) is required rather than a bonus.

## Settled decisions (after GATE 1)

**The lint gate covers the WHOLE project, not only the changed files (user decision).**

The gate runs the target's own lint command exactly as the target defines it, over everything it
covers - `npm run lint` (`eslint .` in the observed target). It does NOT scope down to the run's
changed files.

This SUPERSEDES the acceptance criterion that a failure the run did not cause be distinguished from one
it introduced. The consequence is accepted knowingly: **on a repository with a pre-existing lint
finding, no run can reach `done` until that finding is fixed**, because the gate reports the project's
state rather than the run's delta. The reasoning is that the PR is what a human has to get merged, and
a PR whose checks are red is not done - regardless of which side of the diff the cause sits on.

What still holds from the original criteria:

- "the linter could not run" (unmeasured) stays distinct from "the linter passed" and from "the linter
  failed". A target that declares no lint command is unmeasured, NEVER a pass and never a failure.
- The gating set still comes from the TARGET's configuration - its own scripts - rather than a list
  hardcoded in the factory.
- A repository-wide scanner such as osv-scanner is still not part of this gate: it is a dependency
  inventory check, not a lint of what the run produced.

## Posture, and why this needs an ADR

The allow-list is a SECURITY control: "the ONLY test commands either execution backend will run".
Widening it changes that posture, so it gets an ADR. The design keeps it tight - specific commands
(`npm run lint`, `npm run typecheck`, `npx eslint`, `npx prettier`), NEVER a wildcard `npm run *`, which
would make every package script runnable including a postinstall that does anything.

## Risks and open questions

- **Waiting on the PR's checks takes minutes and can flake.** A real `npm ci` ECONNRESET failed PR #207's
  `test` job for infrastructure reasons. The outer gate needs a bounded wait AND an
  infrastructure-versus-finding distinction, or a flaky runner becomes a fake lint failure that burns the
  fix budget.
- **Pre-existing findings must not block a run forever.** The gate is scoped to the run's changed files;
  a repository-wide scanner such as osv-scanner is the target's own problem, not the run's.
- **Spelling cannot be fixed offline.** cspell's dictionary belongs to the target, so the inner gate must
  not pretend to cover it - this is exactly the class that (A) exists for.
- **Stage 3 is the natural split point** if stages 1-2 grow: the outer gate carries a different risk
  profile (network, waiting, flake) and could ship as its own PR without holding up the artifact fix.
