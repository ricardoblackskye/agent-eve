# #744 - a re-run must continue the Dark Factory branch, not restart from main

## Goal

A re-run of an issue whose `feat/dark-factory-<issue>` branch already exists on the remote must be
able to push. Today the sandbox checkout is synced to `main`, so the new commit is not a descendant
of the branch tip the first run pushed, git rejects it, and the run aborts and releases its claim:

```text
 ! [rejected]        feat/dark-factory-256 -> feat/dark-factory-256 (non-fast-forward)
[ERROR] The run aborted after acceptance; released the claim on ricardoblackskye/webfeedpoc#256
```

Re-running is broken exactly when it is most useful - a failed check, an amended plan, a follow-up
fix - which is the case where a first run already got as far as pushing.

## Settled decisions

| Decision                                                                                   | Why                                                                                                                                                                                                                |
|--------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| The checkout base is the remote DF branch **when one exists**, and `main` when it does not | that is what "continue this issue" means                                                                                                                                                                           |
| The prepare step **fetches the branch and checks out its tip explicitly**                  | so the guarantee does not depend on what the sandbox image happened to have. Syncing to a branch and checking out its tip are the same only when the fetch actually happens, and this is the invariant a test pins |
| **No force-push, ever**                                                                    | it would discard the earlier commit, and the earlier commit may be the only record of an approved plan s implementation                                                                                            |
| The push path is left alone                                                                | with the correct base the push becomes a fast-forward, so the fix is in the base, not in the push                                                                                                                  |

## Phase 0 - settle these before writing code

1. **Locate the prepare step.** The runner logs `-> Sandbox checkout synced to <sha> (from <sha>)` at
   `scripts/dark-factory-runner.ts:1334` from `prepared.base`, so the base is chosen upstream of that
   line. Name the function and file that produces it - the plan changes that function, nothing else.
2. **Does the prepare step fetch at all?** If it does not fetch `origin`, checking out the branch is not
   possible and the fetch is part of this change.
3. **What is in the image at start?** A branch already present locally would make a lazy implementation
   pass locally and fail on a fresh sandbox - which is exactly the "depends on what the image happened
   to have" trap. Record what a fresh sandbox actually holds.

## Tasks (TDD: RED then GREEN, separate commits)

| Task | RED asserts                                                                                                                                       | GREEN does                                                                                                                |
|------|---------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------|
| 1    | a pure chooser of the checkout base: a remote DF branch present -> that branch; absent -> `main`; a blank or `#`-bearing name -> refused          | the chooser, in the run-config or prepare module beside the existing branch-name rules                                    |
| 2    | the prepare step fetches `origin` and checks out the remote branch tip before handing the checkout on                                             | the prepare step, per Phase 0                                                                                             |
| 3    | a wiring guard: the runner reaches the prepare step on the re-run path                                                                            | nothing - a guard on the call site, per the #739 lesson that a unit test on a helper is not evidence the product calls it |
| 4    | with the correct base, the branch cut (`git checkout -B <branch>`, `git-push.ts:129`) descends from the remote tip, so the push is a fast-forward | nothing - a guard that the push path stays unmodified                                                                     |

Task 3 exists because a halt has already once been written in a function the runner never called, with
every unit test passing against the wrong function.

## Acceptance

- A second run on an issue whose branch was already pushed reaches its push and updates the branch,
  instead of aborting on `non-fast-forward` - **provable on the laptop** with the local stack, not
  only in CI.
- The chooser s control case passes: with no remote branch the base is `main`, so a change that always
  checks out a branch fails.
- A deliberately broken fetch still fails loudly - fixed, not disarmed.

## Risks

| Risk                                                          | Handling                                                                                                          |
|---------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| A remote branch that has diverged from the claim s assumption | the fetch is explicit and the checkout takes the remote tip; divergence is then a normal git outcome on top of it |
| A stale locally cached branch in the image                    | Phase 0 records it, and the explicit fetch makes the behaviour independent of it                                  |
| Re-running an issue whose branch was deleted on merge         | the chooser falls back to `main`, which is the current behaviour and is correct                                   |

## Provider- and repo-agnostic checkpoint

Nothing here names a vendor or a repository: the remote is `origin`, the branch name derives from the
issue through the existing rule, and the chooser takes what it is given. The same change holds for a
target the work never touched.
