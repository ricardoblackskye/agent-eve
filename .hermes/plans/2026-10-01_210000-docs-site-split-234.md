# Split ARCHITECTURE.md into a docs/ tree and serve /documentation (#234)

**Branch:** `feat/docs-site-split-232b` (off `origin/main`)
**Issue:** #234 — leg 2 of 6 under #232. Unblocked by #233 (merged).
**Blocks:** #235 (generated reference pages), #236 (deep-dives), #237 (glossary/ADRs)

## Goal

Turn the single 414-line `ARCHITECTURE.md` into a linked set of pages served at
`/documentation`, reusing the existing markdown + Mermaid pipeline rather than
building a new one.

| Question | Finding |

| Rendering today | `app/architecture/page.tsx` — a **client** component that `fetch`es `/api/architecture` at runtime, renders with `react-markdown` + `remark-gfm`, and swaps ` ```mermaid ` blocks for `<MermaidDiagram>` |

### Two findings that change the plan

**1. `docs/` is not a documentation tree — it is a mixed bag.** It currently holds
`adr/`, `dark-factory-run-query-api.md`, `df-progress-board-mockups/`,
`df-progress-board-mockups.zip`, `df-progress-board-wireframes.html`, and
`superpowers/`. A `/documentation/[...slug]` route cannot naively map every
`docs/**/*.md` without publishing mockups and a zip as pages.

**2. The e2e spec asserts more than the count.** It pins
`.mermaid-wrapper svg` to **6** *and* asserts, per section, that an `h2` is
immediately followed by its own rendered diagram
(`h2:has-text("${section}") + .mermaid-wrapper svg`). Splitting moves those
sections onto different pages, so both assertions break — the per-section one
would fail even if the count were made dynamic.

## Design decisions to make (recorded as an ADR)

- **Where pages live.** Proposal: `docs/pages/**` as the documentation root, so
  `docs/adr/` (leg 5) and the mockups stay out of the route. Alternative: keep
  `docs/*.md` and drive the route from an explicit manifest. Prefer the
  directory root — a manifest is a second source of truth that can drift.
- **Client-fetch vs server component.** The existing page fetches markdown at
  runtime, which flashes empty content before hydration. A server component can
  read the file directly and still render the client-only `MermaidDiagram` child.
  Proposal: server component for docs pages, reusing `MermaidDiagram` unchanged —
  better for a documentation site, and it removes the API round-trip. This is an
  ADR-worthy change of approach.
- **Back-compat.** `/architecture` must keep working — redirect to the new index
  or preserve it as a page. Decide which, and note that `app/api/architecture`
  becomes either shared or redundant.

## Intended fix

1. Move — **not copy** — the 19 sections out of `ARCHITECTURE.md` into grouped
   pages under `docs/pages/`, keeping the Mermaid diagrams with their sections.
2. Add `/documentation` (index) and `/documentation/[...slug]`, reusing the
   existing markdown renderer and `MermaidDiagram`.
3. Add navigation between pages, and cross-links from the index to every page.
4. Reduce `ARCHITECTURE.md` to a pointer at `docs/pages/`, or delete it. There
   must be exactly **one** source of truth — duplicated docs are how docs rot.
5. Rework `e2e/architecture.spec.ts` so it is count- and location-agnostic, then
   add a spec covering the new pages.

## Risks / open questions

- **Content loss is the real risk, not routing.** A 414-line file moved across
  pages is easy to drop a section from. The "union covers every original heading"
  assertion is the guard, and it should be written *before* the move.
- **The e2e spec is the known blocker** and is bigger than the count: it asserts
  per-section diagram adjacency, which splitting invalidates by design. It must be
  reworked, not merely made dynamic.
- **`docs/` is shared.** `docs/adr/` belongs to leg 5, and the mockups/zip are not
  documentation. Choosing `docs/pages/` avoids publishing them; confirm no other
  tooling assumes `docs/*.md`.
- **Local Playwright may not run.** The dev server failed to start twice today
  (`e2e-regression-discipline` → `references/local-server-startup-failures.md`).
  If it fails again, say so plainly and name CI as the gate rather than implying
  a green run.
- **Diagrams multiply client-side Mermaid risk.** Six diagrams across several
  pages means more independent render chances to fail; the existing renderer has
  a prior fix in `plans/2026-09-21_fix-mermaid-diagrams-rendering.md`.
