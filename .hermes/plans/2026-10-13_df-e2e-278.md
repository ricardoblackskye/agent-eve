# Plan — #278: e2e coverage for the runs UI, one full pipeline, and the #277 panels

**Branch:** `test/df-e2e-278`
**Issue:** [#278](https://github.com/ricardoblackskye/agent-eve/issues/278) — the last open sub-issue of #267.

## Starting point (verified)

- Five specs in `e2e/`; `dark-factory-overview.spec.ts` already covers the overview page, including an exact
  `toHaveText([...])` header assertion and _"the outcome trend renders as a chart, not a solid block"_.
- CI seeds six sqlite stores (tenant, usage, cost-budget, run-history, control) so panels render rows —
  _"an empty store shows the panel's empty state instead"_.
- The runs UI and control API exist in code and are covered by **nothing**: `app/dark-factory/runs/page.tsx`,
  `app/dark-factory/runs/[runId]/`, `app/api/dark-factory/control/`.

## The trap this plan exists to avoid

An e2e that asserts on an **empty state** passes while proving nothing. The #277 panels are new, so if the
fixture lacks task-type / token / duration / measured-cost rows they will render empty states and any
assertion about them is vacuous. T3 therefore seeds the rows and T5 makes vacancy fail loudly.

## Tasks (RED → GREEN)

### Decision taken (route 1) and a second constraint found

**Route 1 adopted:** assert only what the browser-test step actually configures; leave the rest where it is
already proven. No CI-environment change.

Applying route 1 surfaced the same constraint in T1: the browser-test step omits **`DF_CONTROL_DRIVER`** as
well as the cost driver (`Deliberately WITHOUT DF_COST_BUDGET_DRIVER (or the control driver)`). So a control
ACTION cannot be exercised end-to-end in that job either. Split accordingly:

- **e2e:** the runs **list** and **detail** — both read `DF_RUN_HISTORY_DRIVER`, which IS configured.
- **integration (existing):** the control actions and the `held` refusal — asserted against the API with the
  control store configured, where the invariant is genuinely testable.

**T1 (RED) — runs list and detail.**
List renders seeded runs; detail shows a run's evidence. The control actions — including the #328 `held`
refusal for a second dispatch on the same `(repo, issue)` — are covered at the API level, where that store is
configured. A suite that only tested the happy path would miss the invariant #328 exists to protect.

### T2 reshaped — the AC is already satisfied by #269; the real gap is the terminal stage

`tests/dark-factory/dark-factory-pipeline-e2e.test.ts` (322 lines, added by **#269**) is already a
full-pipeline e2e: it composes the REAL modules — `decideDarkFactoryTrigger` → `runDarkFactoryDispatch`
→ `Dispatcher` → `createDispatchHandler(developer → tester → pr)` → **PR OPENED (never merged)** —
over real in-memory SQLite, with the LLM, the command runner and the PR opener as injected stubs. So
"one e2e exercises the full pipeline" is **already met**, and writing a second one would duplicate it.

The genuine remaining gap is named in that test's own header: it proves the pipeline only **up to
PR-opened**. The terminal stage has a library seam (`run-finalizer.ts`, #284) which the runner drives on
success and on every terminal-failure path, but this end-to-end test explicitly asserts that **no
terminal label is applied here** — the finalizer runs after the stages it composes. So the pipeline's
last stage is covered only in isolation, never as part of the end-to-end path.

**T2 (reshaped): compose the finalizer into the full-pipeline e2e** — drive the composed run through
`run-finalizer.ts` and assert the run reaches a **terminal** state with its terminal labels applied, so
issue → PR → completion is one path rather than two halves. Extend the existing test; do not add a
parallel one.

**T2 (original wording, for the record) — one full-pipeline e2e.** Trigger → lifecycle → terminal evidence, over the seeded sqlite
stores, **no real LLM spend**. Assert what an operator would actually check at the end, not merely that the
page returned 200.

**T3 (RED) — the #277 panels in the browser.** Extend `dark-factory-overview.spec.ts`:

- the charts backed by stores the browser-test step actually configures render as charts
  (reuse the existing anti-solid-block precedent);
- the by-task-type table renders rows;
- **a value nobody measured renders as absent** — no bar, no point — never as zero.

**Scope correction found during recon (before writing a line of spec).** The CI browser-test step
deliberately runs _without_ `DF_COST_BUDGET_DRIVER`, with a hard-won reason recorded in the workflow:

> configuring the budget store arms the orchestrator's cost gate, which refuses every model call with
> `not_configured` until a global cap is provisioned (ADR 0015) — which broke the chat specs.

The seed step writes cost rows, but the dev server serving the specs is not pointed at that store, so
the **budget burn-down chart renders its empty state** in that job. Asserting it as-written would fail.

Two honest routes, and the choice is the operator's because it changes CI for a shared job:

1. **Assert the three charts with seeded stores** (daily cost, cost by model, spend by tenant all read
   the usage/tenant stores the run step does configure) and leave the burn-down to the unit tests plus
   the CSS/baseline guards. Smallest change, no CI-env risk.
2. **Provision the cost store AND a full set of caps in the run step.** The caps must go in as a set
   with the driver or the gate stays armed and refuses (fail-closed), so this touches the env the chat
   specs depend on — to be done only with the suite re-run to prove the chat specs still pass.

This is recorded rather than silently adopted, because it is a CI configuration decision, not a code one.

**T4 (GREEN)** — seed the fixture rows the panels need (task type, tokens, duration, measured cost) and make
T1–T3 pass.

**T5 — anti-vacuity.** With a store unseeded, the suite must FAIL. If it passes, the assertions are reading
empty-state markup and the coverage is fictional.

## Constraints

- Deterministic and offline: sqlite stores under `.eve/`, no network, no provider spend.
- Reuse the existing helpers (`e2e/auth.ts`) and assertion idioms rather than introducing a second style.
- The suites run against Next 16.4.0 (#337) with the scoped undici override (#303).
