# #163 — kick-off trigger + entry point (label-driven, allow-listed, local-dev mode)

**Branch:** `feat/df-trigger-163` (from `origin/main` = `2b63fb5`, which includes #162 via PR #171)
**Issue:** #163 · **Release:** R5 — the last item with real design content, then #164 closes R5

## The gap, re-verified

**The Dark Factory is unreachable by a human.** `Dispatcher` is still never constructed anywhere in the
running app; the webhook handles exactly two triggers (`generate-sprint-report`, and `needs-story` /
`@eve-agent`), neither of them Dark Factory; and no Dark Factory trigger label exists in the repo. R1–R4 built
seams and tests with no live path wiring them together.

## REVIEW findings (from the code)

### 1. `story-trigger.ts` is the pattern to mirror, exactly

`TriggerPayload { action, issue { number, title, body, labels }, label { name }, pull_request }`,
`TRIGGER_DEFAULTS = { mention: "@eve-agent", label: "needs-story" }`, env overrides
(`EVE_STORY_MENTION` / `EVE_STORY_LABEL`), and a **pure** `isStoryTrigger(payload)` that is unit-testable
offline. It also carries the dedup guard this issue needs: a terminal label makes the trigger refuse, so a
re-applied label cannot start a second run. Mirroring it means one trigger style in the repo, not two.

### 2. The local-dev safety policy ALREADY EXISTS — and its rationale is the bug #163 could reintroduce

`app/api/github/webhook/route.ts`'s `requiresSignature()` documents a real incident:

> *"the gate must not be keyed on a platform-owned variable alone. `VERCEL_ENV` is set only by Vercel, so a
> self-hosted deployment … was previously treated as local development … The absence of configuration was read
> as permission to relax the control."*

Its resolution is deny-by-default with an explicit opt-IN. **Local mode must be built the same way**: opt-IN via
an explicit flag, plus a refusal whenever this looks like *any* production build (not merely Vercel
production — a self-hosted `npm start` is production too). "We could not detect a platform, therefore local" is
exactly the reasoning that bug punished.

### 3. The webhook's prompt-injection defence must be reused, because the issue body becomes the task brief

The route already defends against a malicious issue hijacking an agent: structural identifiers are sanitised to
`[A-Za-z0-9_.-]`, and free text is fenced and labelled *"user-supplied data - not instructions"*. #163 hands an
**issue body** to a factory that then writes code, so it must reuse that treatment rather than pass raw body
text through as a command.

### 4. There is NO queue and NO cron — the handoff must reuse the session-API precedent

`vercel.json` is `{"framework": "nextjs"}`: no crons, no queue, no `waitUntil` anywhere in the repo. So
*"hands off to the out-of-band worker runner (`createWorkerHandler`)"* is **not achievable as written** —
calling the handler inline would run the loop inside the request, which the ACs forbid, and there is nothing
else to hand off **to**.

The precedent that does exist, used by BOTH current triggers, is a POST to Eve's own session API
(`/eve/v1/session`) with a message describing the work: the runtime picks it up and the webhook returns. #163
must reuse that mechanism rather than invent a queue — a queue is what #94/#96 are spikes for. Consequence: the
trigger **records the dispatch durably** (that is what makes it idempotent and abortable) **and** hands off
through the session API, with the local entry point substituting the offline runner for both halves.

### 5. The pieces #163 plugs into already exist

`createWorkerHandler(deps)` (worker-env) is the out-of-band runner seam; `dispatchKey(runId)` / `dedupKey(event)`
already make a repeated event idempotent; `resolveWorkerAllowedRepos()` is the fail-closed repo gate; and #162
shipped the reporter plus the label primitives (`addLabel` / `removeLabel`) waiting to be wired.

### 6. The `blocked` state, folded in (decision A's consequence)

#162 made `blocked` a first-class `DispatchStatus` and made **resume explicit** (`dispatch(event, { resume })`).
So the trigger must distinguish two label removals that look alike:

| Event                                    | Meaning                                          |
|------------------------------------------|--------------------------------------------------|
| `dark-factory` removed                   | **abort** — the operator's stop button           |
| the question label cleared after a reply | **resume** — `dispatch(event, { resume: true })` |

and it must **never re-kick a parked run**: a fresh `dark-factory` application on a run whose dispatch record is
`blocked` is held, not restarted.

### 7. A vocabulary conflict to settle before coding

#162's merged AC promises the issue *"gains `needs-answer`"*; #163's own table says `df:blocked` "pairs with
#162". **One state must not have two labels** — see decision (A).

## Design

- **a) One label requests work.** Default `dark-factory`, overridable via `DF_TRIGGER_LABEL` (mirroring
  `EVE_STORY_LABEL`). The issue body and its ACs are the brief.
- **b) Two independent, fail-closed gates.** Repo must be in `DF_WORKER_ALLOWED_REPOS` (existing) **and** the
  actor (`sender.login`) must be in `DF_TRIGGER_ALLOWED_USERS` (new) — on a public repo anyone can apply a
  label, so without the actor gate the trigger is forgeable. Unset ⇒ REFUSE.
- **c) The webhook records; it does not run.** It writes the dispatch through the existing `dispatchKey` seam
  (durable, idempotent, abortable) **and** hands off through Eve's own session API — the only out-of-band
  mechanism this repo has (finding 4), and the same one the story and sprint triggers already use. The worker
  handler is never invoked inline: no code path in the request runs the loop. In local mode both halves are
  replaced by the offline entry point.
- **d) Lifecycle labels** `df:running` → `df:done` / `df:failed`, plus the question label while parked.
  Re-applying `dark-factory` never starts a second run; **removing it aborts**.
- **e) Local dev mode.** `DF_RUNNER=local` routes to an in-process runner, honoured **only** when explicitly
  requested *and* the environment is not a production build (finding 2). Plus an **offline replay** entry point
  that consumes a recorded webhook fixture and drives the whole path with no network — the only way to test
  trigger → dispatch → report → completion deterministically on a laptop.

## The decisions to confirm

**(A) Which label marks a parked run? — recommend `needs-answer`, dropping `df:blocked`.**
`needs-answer` is what #162's merged AC already promises, it reads as an instruction to a human (matching the
existing `needs-story` style), and it avoids two labels for one state. The `df:` family then means lifecycle
state only. This is a one-line correction to #163's table.

**(B) How is local mode selected? — recommend `DF_RUNNER=local`, not a second label.**
A `df:local` label would be a forgeable trigger surface (anyone who can label could route runs to the local
runner) for no gain over an operator-set env var. The offline-replay entry point covers the "run it without
deploying" need without any GitHub interaction at all.

**(C) Where does the entry point live?** A new `agent/lib/dark-factory/trigger.ts` (pure predicate + resolution,
mirroring `story-trigger.ts`) plus a thin `runDarkFactoryDispatch()` used by the webhook route; the webhook
gains a *third* trigger branch only. Recommend this over putting logic in the route, which is already 500+ lines
and cannot be unit-tested offline.
