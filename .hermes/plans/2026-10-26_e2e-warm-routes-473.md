# #473 — E2E compile cost is paid in setup, never inside an assertion

## Goal

A genuinely cold local E2E run must stop reporting four failures that look like product
regressions. They are Next's dev-mode per-route compile latency racing assertion timeouts.

## Root cause (verified in the issue)

The server log from a cold run shows application code answering in 149–355 ms while the
request as a whole takes 25–37 s, because `next dev` compiles the route on first touch:

| request            | total  | application code |
|--------------------|--------|------------------|
| list runs          | 26.1 s | 355 ms           |
| list runs (warm)   | 1.4 s  | 150 ms           |
| unknown run detail | 37.6 s | 192 ms           |

The spec budgets are `expect` 15 s and `test` 60 s, both sized for CI where compilation is
far quicker. So 4 of the 5 specs die at the ledger assertions before any product behaviour is
exercised. `test.slow()` was already tried on #470 and did not help — the test still died at
the configured budget, so a longer expect timeout could never complete.

## Decision — option 1, as chosen

Warm the routes before any assertion runs. Explicitly **not** raising assertion timeouts: the
issue rejects that, because it hides the real signal and slows every run including CI.

Warming happens in a Playwright **setup project** with the assertion projects depending on
it, rather than in `globalSetup` or a per-file `beforeAll`:

- a setup project is ordered after `webServer` is ready and before every dependent project,
  which `globalSetup` does not guarantee;
- it runs **once** for the whole run, not once per worker per file, so `fullyParallel` cannot
  re-race the compiler.

## Design

### A testable decision module

`tests/support/warm-routes.ts` holds the warming decisions behind an injected request
function, mirroring the catalog helper from #472. This follows the lesson recorded in #376:
logic that lives only inside a Playwright spec is untestable, and untestable is how the defect
survived. The rules it encodes:

- De-duplicate targets, so a route is warmed once even if two callers ask for it.
- **A status below 500 counts as warmed.** A 404 on the unknown-run-id route still proves the
  route compiled; treating it as a failure would make the warm-up report a lie, and treating a
  5xx as success would let a genuinely broken route through to the assertions.
- Retry a failing target a bounded number of times, then **throw naming the route**. A warm-up
  that silently gives up leaves the original race in place while looking fixed.

### The Playwright wiring

- `e2e/warmup.setup.ts` — signs in with the existing `signInAsAllowed`, discovers a real run
  id from the list API, then warms: the list API, the ledger page, and the detail page. If the
  store is empty it falls back to the unknown-id path, which still compiles the dynamic route.
- `playwright.config.ts` — a `setup` project matching only the warm-up file, and
  `dependencies: ["setup"]` on the browser project.

## Risks / open questions

- Warming adds a few seconds to every E2E run. It buys determinism, and it does not weaken a
  single assertion.
- It does not make the assertions faster; it removes a compiler from their critical path. If a
  route becomes slow for a real reason, that still shows up.
- Only routes the specs actually use are warmed. A new spec touching a new route must add it,
  or it re-introduces the race for that spec alone.

## ADR

One decision needs recording: dev-mode compile cost belongs in E2E setup, and widening
assertion budgets to cover a compiler is not an acceptable substitute.
