# #731 — An e2e failure caused by the sandbox image must not be read as broken code

**Goal:** when the target's declared e2e fails because the *sandbox could not run it* (a missing browser,
toolchain or binary) rather than because the change broke it, the loop must say so, must not spend
iterations correcting code that is fine, and must still refuse to open a pull request.

**Architecture:** #701 gave the loop an `E2eOutcome` of `not-run | passed | failed`, resolved from the
target's own manifest and folded into the iteration's gate. This adds a fourth outcome — `environment` —
decided by a **narrow, pure, auditable rule** over the suite's own output. The loop consumes it by
*not* self-correcting, and the verdict names the reason. **Fail-closed is preserved: on any doubt the
outcome stays `failed`.**

**Tech stack:** TypeScript, Vitest. Files: `agent/lib/dark-factory/developer-agent.ts`,
`scripts/dark-factory-runner.ts`.

---

## Context, all measured

A real run (WebFeedPOC #253, image `df-sandbox-webfeedpoc:4`) produced this:

```text
Test result: FAIL (unit, e2e)          ← the verdict blamed the code
664) [chromium-tablet-pro] › e2e/product-card-responsiveness.spec.ts:26:3 › ...
    Error: browserType.launch: Executable doesn't exist at
    /home/node/.cache/ms-playwright/chromium_headless_shell-1208/.../chrome-headless-shell
[ERROR] Circuit breaker tripped — workerMinutes:60, limit:60
```

**664 failures, every one the same launch error, and it was the image's fault** — that image carries no
browsers at all. The loop spent its entire 60-worker-minute budget trying to fix code that was correct.

A second image (local-promotion-site `:2`) failed differently and just as wrongly: root-owned
`node_modules` meant `npm run dev` died with `EACCES`, so the suite could not start either.

**The landed #701 shape this must fit:**

```ts
export async function runDeclaredE2e(deps: {...}): Promise<E2eOutcome> {
  if (!deps.command) return { status: "not-run", output: "" };
  const res = await deps.runTests(deps.command, { allowedCommands: deps.allowedCommands });
  if (!res.ran) return { status: "not-run", output: res.output };
  return { status: res.passed ? "passed" : "failed", output: res.output };
}
export function formatTestVerdict(passed: boolean, suites: GateSuites): string
```

**Assumptions:** the suite's output is available in full (it is — `E2eOutcome.output` carries it), and a
reproducible case exists for the live proof (`df-sandbox-webfeedpoc:4` in the cluster, no browsers).

## The decision rule, deliberately narrow

An output is an **environment fault** only when ALL THREE hold:

1. **It contains at least 3 distinct failure entries** — one failure is a test, not a shape.
2. **Every failure entry carries byte-identical error text.** Genuine breakage varies per test, because
   different assertions fail for different reasons.
3. **That text matches a missing-binary/toolchain shape** — a small, explicit, auditable pattern list:
   `Executable doesn't exist`, `command not found`, `No such file or directory` naming an executable,
   `cannot execute binary file`, `error while loading shared libraries`, `EACCES: permission denied`
   on a path inside the workspace.

**Why all three, and why narrow:** a change that breaks a shared import also fails *everything*, with
identical text — and that is a real code fault that must fail. Length is therefore not enough on its own;
the text must name a missing tool. **The asymmetry is intentional:** a false `failed` costs one loop
iteration; a false `environment` would let a red suite reach a pull request, which is the one thing #701
exists to prevent. Uncertain ⇒ `failed`.

## Task 1: `classifyE2eFailure` — the pure rule

**Objective:** decide the outcome from the suite's output alone, with no I/O.

**Files:**

- Modify: `agent/lib/dark-factory/developer-agent.ts`
- Test: `tests/dark-factory/e2e-environment-fault-731.test.ts` (new)

**Step 1: write the failing test** — including a **mutation** and a **control**, so the guard has teeth:

```ts
// mutation: the #253 shape, verbatim from the real run → MUST classify as environment
const launchBurst = Array.from({ length: 12 }, (_, i) =>
  `  ${i + 1}) [chromium-tablet-pro] › e2e/x.spec.ts › test ${i}\n` +
  `    Error: browserType.launch: Executable doesn't exist at /home/node/.cache/ms-playwright/.../chromium_headless_shell`,
).join("\n");
expect(classifyE2eFailure(launchBurst)).toBe("environment");

// control 1: DIFFERENT assertion failures → must stay a code failure
expect(classifyE2eFailure("Expected 'A' to be 'B'\nExpected 3 to be 4")).toBe("failed");

// control 2: identical IMPORT failures → a shared import is a REAL break, not the image
const importBurst = Array.from({ length: 9 }, () => "Error: Cannot find module './missing'").join("\n");
expect(classifyE2eFailure(importBurst)).toBe("failed");

// control 3: a single launch failure is one test, not a shape
expect(classifyE2eFailure(launchBurst.split("\n").slice(0, 2).join("\n"))).toBe("failed");
```

**Step 2: run it, expect all four to FAIL** (`classifyE2eFailure is not a function`).

**Step 3: implement minimally** — count failure entries, compare their normalised error lines, and match
the explicit pattern list. Keep the patterns in one exported `const` so the list is reviewable on its own.

**Step 4: run again, expect 4 passed.**

**Step 5: commit** — `test(731): RED - the image-fault shape, its controls, and its mutation`, then the
GREEN as its own commit.

## Risks and open questions

- **The rule's precision is the whole risk.** The pattern list is a heuristic; the three-condition
  conjunction plus fail-closed-on-doubt is what keeps it safe. Worth a reviewer's eye on the list itself.
- **`EACCES` is included deliberately** (it is the local-promotion-site `:2` failure — #735) but it is
  also a plausible genuine test failure. The byte-identical + count conditions carry the weight there.
- **Should an environment fault release the claim?** It aborts *after acceptance*, as today's runs did.
  Open question for the reviewer: whether that should differ.
- **Does this belong before #734's tiering?** Yes — the classifier removes the pathological case (an
  unfixable failure burning the budget) independently of when the suite runs.
