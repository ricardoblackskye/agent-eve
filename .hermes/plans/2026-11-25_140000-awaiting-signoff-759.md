# #759 - a delivered issue must read as delivered, and wait for sign-off

## Goal

The factory s issue labels and comments must state the TRUE state of the work. A finished run currently
loses `df:done`, gains `df:running`, posts a "Synthesizing ExecutionPlan" comment and raises
`needs-answer` - three signals that say work is happening and the operator is being waited on, on an issue
whose work is delivered and whose pull request is open.

## Root cause (verified at the cited lines, not inferred)

| Claim                                                                                                                                                                                             | Tier                                                                                                      |
|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| The lifecycle labels are constants in one place: `running: "df:running"`, `done: "df:done"`, `question: "needs-answer"`                                                                           | **verified** - `trigger.ts:55-61`                                                                         |
| The code already states the rule being broken - a delivered ticket "would advertise `df:running` AND `df:blocked` at once", and "`df:done` means the work is finished and must not [be replaced]" | **verified** - `trigger.ts:81-102`                                                                        |
| `needs-answer` is documented as "the label that marks a run as waiting for a HUMAN", with no distinction between a parked plan and a delivered result                                             | **verified** - `plan-approval.ts:99`; the cleared-label path was retired in ADR 0064                      |
| The confusing comment is posted unconditionally at dispatch: "Dispatched Hardened Pipeline" + "Synthesizing ExecutionPlan and running pre-flight domain validation"                               | **verified** - `runner.ts:608-611`                                                                        |
| `df:done` requires a PASSING Definition of Done                                                                                                                                                   | **verified** - `run-finalizer.ts:264`                                                                     |
| `retire-claim.ts` states "a ticket that still says `df:running` is the very symptom this release exists to remove" and then applies **no terminal label**                                         | **observed** - the file s own comment, and WebFeedPOC#260 after retiring: labels reduced to "In progress" |

This is not a new rule. It is a rule the code states and then violates.

## Settled decisions

| Decision                                                                                             | Answer                                                                                |
|------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| A delivered state is **terminal** - a later dispatch must never strip `df:done` / `awaiting-signoff` | **No replacement, ever**                                                              |
| A red pull request check                                                                             | **The same state**, with the comment naming the failing check - not a separate label  |
| `Rejected` on a delivered issue                                                                      | **Close the pull request and hand the issue straight back to the factory to re-plan** |
| Retiring a stale claim                                                                               | **Apply the terminal label**, rather than leaving the ticket unlabelled               |

## The change

1. **A distinct terminal label, `awaiting-signoff`**, alongside the existing constants. Applied when the
   Definition of Done has passed and the run is waiting on the operator. `needs-answer` keeps its meaning:
   a parked plan needs approval before coding starts.
2. **A terminal-state guard.** A dispatch must not remove a delivered state. `trigger.ts` already argues for
   this in prose; the guard makes it true, and it is the fix for the `df:done`-replaced symptom.
3. **The comment matches the state.** In the sign-off state it says the work is complete, names the pull
   request, says what the checks are doing - naming a failing check when there is one - and asks for
   `Approved` or `Rejected`. It never claims a plan is being synthesized.
4. **`Approved` / `Rejected` are the sign-off vocabulary** on that state: `Approved` records the sign-off;
   `Rejected` closes the pull request and returns the issue for re-planning.
5. **`retire-claim` applies the terminal label** its own documentation promises, so retiring a delivered run
   leaves the ticket legible.

## Provider- and repo-agnostic checkpoint (before GATE 1)

Would this hold for a repository this work never touched? **Yes.** The change is in the factory s own label
vocabulary and comment wording; no repository, vendor or issue number appears in the invariant. WebFeedPOC#260
is the first case that proves it.

## Phase 0 finding: the mechanism, verified at the line

The first pass called this "a rule the code states and then violates". It is sharper than that, and the
sharper version decides the fix.

`trigger.ts` documents THREE label sets, and the defect is the second one:

```text
TERMINAL_LABELS           [done, failed]           a re-trigger is REFUSED for these
OUTCOME_LABELS            [done, blocked, failed]  what a fresh start CLEARS
RETRIGGER_REFUSED_LABELS  [done, ...]              "df:done must not silently be redone"
```

**`OUTCOME_LABELS` includes `done`, so a fresh start clears `df:done`.** That is the screenshot exactly -
"added `df:running` and removed `df:done`" - and it is not an ordering accident.

**The guard that should have refused it is bypassed by the path.** `RETRIGGER_REFUSED_LABELS` already
refuses a re-trigger on `df:done`, but it guards the LABEL path. The observed re-run came through the CLI
launcher (`df:local-run`), which clears the outcome labels and proceeds. So an operator-driven dispatch can
un-deliver a finished ticket while the label path cannot - which is why WebFeedPOC#260 read the way it did.

**And the new label belongs to the other family.** The file s own vocabulary rule: "`df:*` is LIFECYCLE
state; the question label is deliberately NOT in that family because it is an instruction to a human". So
`awaiting-signoff` sits BESIDE `df:done`, not in place of it - the same shape as the DoD s existing
`df:blocked` + `needs-answer` pair. Neither may be cleared by a re-dispatch.

## Amendments made while implementing (recorded, not implied)

The plan listed six tasks. Implementation changed three things about it and added a seventh, and each was
found by doing the work rather than by reading the plan again. They are recorded here so the record matches
what was built.

### Task 3 gained a second half, as Task 3b

Stopping the run-start clearing was only half of the delivered-state problem. A dispatch that still added
`df:running` to a ticket keeping `df:done` would advertise the contradictory pair `trigger.ts` documents
the clearing as existing to prevent. So the DISPATCH side refuses a delivered ticket by name, mirroring
`RETRIGGER_REFUSED_LABELS`, which guards only the label path - the CLI path is where the original report
came from. Verified live: the lps run cleared `df:blocked, df:failed` and not `df:done`.

### Task 4 landed in `dod-presentation.ts`

The sign-off comment is a PURE renderer beside `renderAcTraceabilityTable` and `renderAcceptedFindingComment`,
so it is tested without mocks, and it carries a control asserting the text never claims a plan is being built
or a pipeline dispatched - the exact language from the report.

### Task 6 became a GUARD, because its premise was wrong

The plan had the retirement path applying a terminal label. Measurement disproved the premise: a delivered
run has already RELEASED its claim, so retirement refuses it with `no-claim` and touches nothing. Retiring is
therefore never the path that clears a delivered state, and the module s documented "no terminal label is
applied" was right. The file now LOCKS that measured behavior - a parked run retires and adds no terminal
label; a delivered run reports `no-claim` - and it is labelled a guard, not a RED.

### Task 7: the wiring, found by the live e2e

Tasks 1-6 built the selector, the comment renderer, the vocabulary and the guard, and every one of them
passed its own tests. The live run on WebFeedPOC#262 then proved what no unit test could: NOTHING CALLED
THEM. The issue showed no `awaiting-signoff` because the only reference to that label outside its own module
was the refusal CHECK, never an application. The selector is now called at the verdict-to-label step in
`run-finalizer.ts`, and the terminal comment asks for the decision.

This is the failure mode the skill names as "two tested ends do not test the WIRE between them", and it is
why the live acceptance below was not waived.

### Live acceptance status

The acceptance criterion is that a finished run leaves `awaiting-signoff` and a comment naming the pull
request. That is NOT yet observed: three e2e attempts on WebFeedPOC ended `blocked` at the check-wait (the
DoD waits up to 20 minutes for the pull request s checks, and that repo s e2e does not settle in time), and
the wiring landed after the first of them. The label is only applied on a `done` verdict, so the run must be
against a repository whose checks complete green. It is unit-verified, and this line is here rather than
left for a reader to infer.
