# Reservation price floor — implementation plan for #498

> **For the implementer:** read the "Dependency" section before branching. This plan is written
> against `origin/main` at `595e88e`, which does **not** yet contain #496.

**Goal:** make it impossible for the number the cost gate reserves against to sit silently below
the dearest published provider rate, so an upstream price rise can never under-reserve spend.

**Architecture:** `admit()` reserves against `modelPriceTable` before a call and `settle()` trues up
afterwards, so the reserved number must be an upper bound (ADR 0027). The table is a hand-maintained
constant, which is exactly what failed. This change adds a shipped, machine-refreshed **floor** of
the dearest rate last verified per model, and `resolvePrice` returns the higher of the table entry
and the floor. The floor can only ever raise the reserved price, so it is inert while the table has
headroom and protective the moment the table falls behind.

**Tech stack:** TypeScript, Vitest, `tsx` scripts, GitHub Actions. No new runtime dependency and no
network call on the reservation path.

## Intended fix

1. Ship the observation as `agent/lib/dark-factory/model-price-floor.ts`: the dearest input/output
   rate seen per model, the date it was verified, and a TTL.
2. `resolvePrice` returns, per axis, `max(table entry, floor entry)`.
3. The **env override still wins.** ADR 0027 documents it as the escape hatch for an operator who
   knows the provider in use, and a cheaper pinned provider is a legitimate reason to set it. The
   floor guards the shared table, not an explicit per-deployment act — that distinction goes in the
   ADR, and Task 4 pins the ordering with a test so it cannot drift.
4. Staleness is surfaced, not fatal — see "Decision required" below.

## Decision required at GATE 1

**How should staleness behave — warning, or fail-closed?**

- **Recommended: warning.** `prices:check` reports it and the scheduled workflow raises it. This
  follows ADR 0067, which faced the same choice for the model-id receipt and chose a warning,
  recording that it is "knowingly the weaker of the two options". The reason is availability: a
  fail-closed floor would refuse to run the factory once the observation lapsed, turning a
  housekeeping lapse into an outage.
- **Alternative: fail-closed past the TTL** — `resolvePrice` returns `null` (or the governor returns
  a new `stale_price` reason) when the floor is older than the TTL, so an under-reserved call is
  impossible rather than merely unlikely. Strictly safer for spend, strictly worse for uptime, and it
  requires the observation to be refreshed on a schedule nobody currently automates.

The plan implements the recommended option; say the word and Task 6 swaps to the alternative.

## Risks and open questions

- **The floor is only as fresh as the last verification.** It cannot prevent under-reserving against
  a rise that happens after the last check — that window is bounded by the scheduled workflow, not by
  this code. The plan does not pretend otherwise; the ADR states the bound.
- **Over-reserving is the safe direction but not free.** Raising the reserved number increases
  transient cap pressure. Today the floor is inert (the table has headroom above it), so the cost is
  prospective rather than immediate; if a future floor exceeds the table, that is a signal the table
  is stale, and it should be raised rather than the floor lowered.
- **Cost-gate coverage.** `resolvePrice` is measured by the coverage ratchet. New lines need tests or
  the ratchet fails; Tasks 1–4 provide them.
- **A test asserting both branches of the max is required.** A one-sided test passes with the merge
  written backwards.
