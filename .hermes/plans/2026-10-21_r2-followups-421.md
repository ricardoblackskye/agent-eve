# #421 — R2 follow-ups: a cursor that can order, and a journey that is proven

## Ground truth (read in the code, not assumed)

- `RunCursor` is `{ createdAt, runId }` and `RUN_SORT_FIELDS` is `["createdAt"]` as a direct consequence: the SQLite
  driver's predicate is `(created_at <cmp> ? OR (created_at = ? AND run_id <cmp> ?))` with
  `ORDER BY created_at <order>, run_id <order>`. The Postgres driver mirrors it.
- `validateRunSort` **already refuses** a sort outside that list, and `validateRunCursor` validates the timestamp and
  the id. So the refusals AC4 protects are real behaviour with tests, not aspirations.
- `run-query.ts` validates the parameters and the route parses `sort` / `direction` into them.
- The list page, the detail page and the runs table are unit-tested; **nothing exercises the click-through** between
  them, which is what AC1 is about.

## Design

**One cursor shape, carrying its own ordering** — `{ sort, direction, key, runId }`, where `key` is the sort column's
value as text. A cursor that does not name the ordering it was issued under cannot be checked against the request, and
that unchecked replay is the defect this release exists to remove.

- **A mismatch is refused, not honoured** (AC3): `validateRunCursor(cursor, options)` rejects a cursor issued under one
  ordering and replayed under another. Honouring it would return page 2 of a different list, silently.
- **Columns come from a whitelist map, never from interpolation.** No string a caller supplies ever reaches the SQL;
  the sort field selects a known column, which is also what keeps this safe to extend.
- **Sort fields**: add `status` and `repo` — both text, both useful, and two of them prove the mechanism.
  `issue` is deliberately LEFT OUT and said so rather than half-done: its key is numeric, so a text `key` would need
  typed parsing per sort. AC2 asks for at least one non-time column; two text columns satisfy it honestly.
- **Legacy `{createdAt, runId}` cursors fail closed.** The shape changed and the API is internal, so an old cursor is
  rejected with a clear message rather than reinterpreted into a possibly-wrong page.

## Tasks

**Task 1 (RED) — the cursor carries its ordering.** A cursor issued for `sort=status&direction=asc` and replayed with
`direction=desc`, or under a different `sort`, throws `InvalidRunRecordError`. Includes a cursor naming a sort that is
not a sort field at all.

**Task 2 (RED) — ordering by `status` and by `repo`.** Rows come back in that order from **both** drivers, and a paged
walk visits every row exactly once: no duplicates, no losses. That walk is the property that makes keyset paging worth
having, and with a non-unique key like `status` the `run_id` tiebreak is what makes the ordering total.

**Task 3 (RED) — the refusals survive (AC4).** Unknown `sort`, unknown `direction`, malformed cursor, wrong-typed key.

**Task 4 (GREEN)** — implement across the store interface, both drivers (`SqliteRunHistoryStore`,
`PostgresRunHistoryStore`), `run-query.ts` and the route, so the API's cursor round-trips the new shape.

**Task 5 — the journey (AC1).** Playwright: the repo list, open a repository, see its runs — asserting a row the API
actually returned, so a wrong `href` or a param-name mismatch cannot pass.

**Task 6 — docs.** Mark these follow-ups done in the R2 plan section, and correct the store comments that say ordering
is `createdAt` only; left alone they would become lies, which is worse than the gap they described.

## Risks

- **A keyset walk that repeats or loses a row is worse than OFFSET**, because it looks correct in the common case; the
  walk test exists for exactly that, over a non-unique key.
- **A column name interpolated into SQL** would be an injection surface, so the mapping is a whitelist and the value
  stays a bound parameter.
- **A stale cursor silently accepted** would show an operator two half-lists; the mismatch refusal is tested, not
  assumed.
- **Correcting the "createdAt only" comments** is part of the change: a comment that contradicts the code is how the
  next person gets it wrong.

## Status (2026-10-21)

**Done.** The cursor carries the ordering it was issued under, and a replay under another sort or direction is
REFUSED (AC3). Ordering by `status` and `repo` works from the store (AC2), with columns chosen from a whitelist so no
caller string reaches the SQL. R2's refusals are preserved and re-pinned (AC4). The cursor validator now lives in the
store and both drivers import it - the Postgres driver had its own copy, and two copies is how two drivers come to
disagree about what a cursor means.

**Evidence.** 10 new tests: the mismatch refusals, ordering by two columns, and a paged walk that visits EVERY row
exactly once over a NON-UNIQUE key. 4 existing tests updated to the new shape, because the contract changed on
purpose and reinterpreting an old cursor could return a page nobody asked for. 93 tests green across 7 files, tsc
clean.

**Not done, and named.** The Playwright journey (AC1). And ordering by `issue` needs typed key parsing rather than the
text key this shape carries - the acceptance asks for one non-time column, so two text columns satisfy it honestly
instead of half-doing a third.
