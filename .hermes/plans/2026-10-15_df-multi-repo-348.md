# Dark Factory — multi-repo management (#348) Implementation Plan

**Goal:** the Factory stops hardcoding `ricardoblackskye/agent-eve`: a run works on the repository the
dispatch concerns, falling back to a repo configured in the app's config, and authorization stays an
explicit allow-list.

**Architecture:** two concerns that are currently conflated, separated. **Resolution** answers *which repo*
(`--repo` → configured default) and **authorization** answers *may we touch it*
(`DF_WORKER_ALLOWED_REPOS`, fail-closed). Both already have a home in the codebase: `REPO_PAIR_PATTERN`
and `resolveWorkerAllowedRepos` live in `agent/lib/dark-factory/credentials.ts`.

**Tech Stack:** TypeScript, Vitest, GitHub REST (patched over operations).

---

## Context — what the recon found

The issue asks *"how is the application notified about which repo to work on? By Project? By Labels?"*
The answer is that **no new mechanism is needed**: the notification already carries the repository.

| Piece                                        | State         | Evidence                                                                                                                                            |
|----------------------------------------------|---------------|-----------------------------------------------------------------------------------------------------------------------------------------------------|
| The webhook learns the repo from the payload | **already**   | `app/api/github/webhook/route.ts:229` reads `data.repository.full_name`; an unknown repo is rejected against `release-manager.config.json` (`:242`) |
| The DF trigger carries + gates the repo      | **already**   | `agent/lib/dark-factory/trigger.ts:227` refuses when `DF_WORKER_ALLOWED_REPOS` is unset; `:233` refuses a repo outside it                           |
| The repo-pair validator                      | **already**   | `credentials.ts:60` `REPO_PAIR_PATTERN`, `:389` `resolveWorkerAllowedRepos` (unset ⇒ `[]` ⇒ refuse everything)                                      |
| A per-repo registry with defaults            | **already**   | `release-manager.config.json` (`repos` + `defaults`)                                                                                                |
| The runner receives a repo                   | **MISSING**   | it parses `--issue`, `--branch`, `--resume` — never a repo                                                                                          |
| The runner's target repo                     | **hardcoded** | `scripts/dark-factory-runner.ts:189` `const targetRepo = "ricardoblackskye/agent-eve"`, used ~20×                                                   |
| The runner's gate                            | **defeated**  | `:108-110` *sets* `DF_WORKER_ALLOWED_REPOS` when unset, so `resolveWorkerAllowedRepos` never sees an unconfigured deployment                        |

So: the trigger knows the repo and gates it; the runner has a gate but is never told the repo, so it
invents one — and the invented allow-list makes that look authorized.

### Consequence worth stating plainly

A dispatch for any other repo **already passes the trigger gate** (the repo is in the allow-list), the
runner then works on `agent-eve`, and because #348's sibling fix (merged) made labels and comments use
the run's repo, the run would now correctly label *its own* — but the wrong — repository. Two bugs
compensating is not a design.

## The design

**Resolution order** (first wins):

```text
1. --repo <owner/name>            explicit: a dispatch, or an operator running the runner by hand
2. default_repo in config         the app's configured default (dark-factory.config.json)
3. otherwise                      REFUSE, naming both ways to supply one
```

Each candidate is validated with the existing `REPO_PAIR_PATTERN`; a malformed value is refused rather
than coerced, and the resolved repo is normalised to lower case exactly as `resolveWorkerAllowedRepos`
does, so the two cannot disagree about identity (GitHub treats owner casing as insignificant).

**Authorization** (unchanged, and now actually reachable): the resolved repo must appear in
`DF_WORKER_ALLOWED_REPOS`. The runner stops faking that variable. An unset allow-list refuses every run
with a message naming the variable — the same stance as `STORY_ALLOWED_REPOS`.

**Why the default lives in config and not in the code:** a default in code is indistinguishable from a
hardcode — this issue exists because of one. A default in config is a stated operating choice, visible in
review, and overridable by the environment without a deploy.

**Why a new config file rather than extending `release-manager.config.json`:** that file answers "what
does the release manager do for this repo" (webhook secret, token, notes path). The Factory's answers
differ (default repo, board, branch prefix), and merging them would make one file mean two things — the
DRY argument cuts the other way once the *fields* diverge. Both files share one shape (`repos` +
`defaults`) so they read the same way.

## R1 tasks (TDD, in order)

### Task 1 — a pure resolver for the target repo

**Files:** create `agent/lib/dark-factory/runner-config.ts`; create
`tests/dark-factory/runner-config.test.ts`.

**Objective:** decide the target repo from arguments + config + env, with no I/O inside the decision.

**Step 1 — write the failing tests.** Cases, each asserting the *reason* as well as the outcome:

1. `--repo owner/name` wins over the configured default;
2. with no `--repo`, the configured `default_repo` is used;
3. a malformed `--repo` (`"agent-eve"`, `"a/b/c"`) is refused, quoting the offending value;
4. neither `--repo` nor a default ⇒ refuse, and the message names **both** ways to supply one;
5. a malformed `default_repo` in the config is refused (a bad config must not silently become a bad run);
6. owner casing is normalised, so `--repo RicardoBlackSkye/agent-eve` equals the allow-list entry
   `ricardoblackskye/agent-eve` (this is the case that would otherwise pass the gate by accident).

**Step 2 — run them; expect 6 failures** for absent behaviour, and confirm there is no `ReferenceError`
(a stub with the real signature is declared first so collection succeeds — a missing named export aborts
the whole file and looks like RED).

**Step 3 — implement** `resolveTargetRepo({ argv, config, env })`. Reuse `REPO_PAIR_PATTERN`; do not
write a second repo regex.

**Step 4 — run; expect 6 passed**, then the whole suite for regressions.

### Task 2 — the config loader

**Files:** modify `runner-config.ts`; create `dark-factory.config.json`; extend the same test file.

**Objective:** read `default_repo` from the config file, failing closed on a malformed file.

Tests: a missing file ⇒ no default (not an error — `--repo` may legitimately be used); malformed JSON ⇒
refuse naming the path; `default_repo` present but not an `owner/repo` pair ⇒ refuse; a valid file ⇒ used.

Config to add:

```json
{
  "default_repo": "ricardoblackskye/agent-eve"
}
```

### Task 3 — the runner uses the resolver, and stops faking the allow-list

**Files:** modify `scripts/dark-factory-runner.ts` (`:106-110`, `:189`); modify
`tests/dark-factory/runner-authoring.test.ts` (or add a focused source-guard test).

**Objective:** one resolution point, and a gate that can actually refuse.

1. Delete the block that *sets* `DF_WORKER_ALLOWED_REPOS` when unset.
2. Replace `const targetRepo = "ricardoblackskye/agent-eve"` with the resolver's result; every existing
   use derives from it already (that was the point of the sibling fix).
3. After resolving, assert membership in the allow-list and refuse with a message naming both the repo
   and the variable when it is absent — this is the fail-closed path, not a warning.

Tests: a source-level guard that the literal is gone and the resolved value is what everything uses;
plus unit coverage of the refusal (empty allow-list ⇒ refuse, naming `DF_WORKER_ALLOWED_REPOS`).

### Task 4 — the runner stops inventing its other inputs

**Files:** modify `scripts/dark-factory-runner.ts` (`:192-196`, `:218-221`).

Two silent inventions of the same class as the hardcoded repo:

- `--issue` defaults to **`179`** — a run for the wrong issue, silently.
- the branch default is `` `feat/dark-factory-#${issueNum}` `` — a `#` in a branch name, which breaks the
  GitHub UI/URLs (this repo's own convention says branch names must not contain one).

Require `--issue` (refuse with a clear message) and drop the `#` from the branch default. **This is a
behaviour change** — a run that relied on either default will now refuse rather than guess — so it is
called out for review rather than slipped in.

### Task 5 — document it

**Files:** modify `.env.example`, `docs/pages/dark-factory-modules.md`.

- `.env.example`: note that `DF_WORKER_ALLOWED_REPOS` is now the *only* source of authorization and that
  an unset value refuses every run. No new env var is introduced — the default lives in the config file.
- Catalogue entry for `runner-config` and the module-count bump (the doc-drift guard fails otherwise).

## Risks, decisions, and open questions

1. **A deployment change is required, out of code scope.** Removing the faked env means the deployment
   must set `DF_WORKER_ALLOWED_REPOS` (Vercel) or every run refuses. This is the intended fail-closed
   behaviour, but it is a switch the user flips — not something this PR can do for them. Steps will be
   supplied at the PR, not applied by API.
2. **Each allowed repo needs a token with access to it.** The credential broker is already per-repo, so
   this is a provisioning question, not a code change — but a repo in the allow-list whose token lacks
   access will fail at clone/PR time, and the message must say which repo.
3. **`--issue` becoming required** may break an existing habit/script. Flagged as a behaviour change
   above; if it is load-bearing somewhere, that somewhere should be told to pass it explicitly.
4. **DECIDED — the target repo is the issue's own repository.** Confirmed directly rather than
   inferred. This is what the payload already carries, so R1 needs nothing from Projects, and the Project
   relationship is only about which *board* a run reports to (per-repo settings — R2). A
   Project-as-authority design was considered and rejected: it would require a Project→repo lookup, and a
   Project item can reference an issue in any repository, so the Project states the target less precisely
   than the issue itself does. R1's ADR records this decision and the alternative it rejected.
5. **Two config files now describe repos.** Mitigated by identical `repos`/`defaults` shapes and by R2
   adding a test that both keys are valid `owner/repo` pairs — but the risk of drift is real and is the
   main argument for merging them later if the fields converge.
