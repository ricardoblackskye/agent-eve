## Goal

Attribute Dark Factory runs and measured LLM usage to stable customer tenants, and
let the operator see usage broken down by tenant.

R1 is **attribution and reporting only**. It does not enforce budgets (R2 / #214)
and does not let customers log in (R3 / #215).

## Intended approach

Follow the seams already proven three times in this codebase (#207 control plane,
#208 policy, #209 usage ledger): a **canonical type + a store seam + per-backend
adapters + an opt-in provider factory**, with `console` as the inert default and
Postgres as the only production backend. No Vercel SDK; standard `pg`.

Two rules shape the design:

1. **Attribution is captured once, at run acceptance, and then immutable.**
   The tenant is resolved from trusted server-side configuration at the moment
   the run is accepted and persisted on the run. It is never re-derived from
   today's repository mapping, because reassigning a repository must not silently
   rewrite history.
2. **Absence is preserved.** An unmeasured value stays absent and renders as
   `—`; historical runs with no trustworthy attribution stay **unassigned** and
   are reported as such. Nothing is zero-filled and no tenant is guessed.

## Tasks (TDD: RED → GREEN → REFACTOR per task)

### Task 1 — Canonical tenant model and validation
`agent/lib/dark-factory/tenant.ts`
- `TenantStatus` = `"active" | "inactive"`.
- `Tenant` = `{ id, slug, name, status, createdAt }`; `id` is **opaque** and
  stable — a `crypto.randomUUID()` value, never the slug, never a repo name.
- `normalizeRepoSlug(input)` → `"owner/repo"` lowercased, sanitised to
  `[A-Za-z0-9_.-]` at the **intake seam** (shared, not only in the writer), so a
  dry-run provider echoing the payload cannot carry injection-capable values.
- `validateTenantId`, `validateTenantSlug`; `InvalidTenantError` (a distinct
  class, not a generic `Error`).
- Tests: opaque-id acceptance, slug/repo normalisation, rejection of malformed
  ids, case-folding, and sanitisation of hostile input.

### Task 2 — Tenant store seam
`agent/lib/dark-factory/tenant-store.ts`
- `TenantStore` interface: `upsertTenant`, `getTenant`, `listTenants`,
  `setTenantStatus`, `assignRepo`, `resolveTenantForRepo`, `listRepoAssignments`.
- Result shape `{ ok: true, value } | { ok: false, error }` — a thrown driver
  exception is a **second error shape** at every seam, so every read *and* write
  is wrapped and converted. `ok: true` means "this call was handled", never
  "the entity is healthy".
- `assignRepo` is **idempotent**: re-assigning the same repo to the same tenant
  is a no-op; moving a repo to a different tenant updates the *mapping* only and
  leaves already-persisted run attribution untouched.
- `resolveTenantForRepo` returns the tenant, or an explicit unassigned result —
  never a default tenant.
- `InMemoryTenantStore` for tests and the inert default.
- Tests: unique repo mapping, idempotent assign, reassignment semantics,
  inactive tenant cannot accept new work, outage path.

### Task 3 — SQLite adapter (local only)
`agent/lib/dark-factory/tenant-store-sqlite.ts`
- File-backed via `node:sqlite`; expose `close()` on the seam so Windows
  teardown does not fail with `EBUSY`.
- Rejected when `NODE_ENV=production` or the stage is preview/production.
- Tests: CRUD, uniqueness, persistence across reopen, `close()` teardown.

### Task 4 — Postgres adapter and migration
`agent/lib/dark-factory/tenant-store-postgres.ts` + `db/migrations/003_df_tenants.sql`
- Tables `df_tenants` (opaque `id` PK, unique `slug`, `status`, `created_at`) and
  `df_tenant_repos` (unique normalised `repo_slug` → `tenant_id`, FK).
- **RLS enabled, no public policies** — matching `001`/`002`.
- Integration tests gated on `DF_TENANT_TEST_DATABASE_URL` (skipped, not faked,
  when absent).

### Task 5 — Opt-in provider factory
`agent/lib/dark-factory/tenant-store-provider.ts`
- `DF_TENANT_DRIVER` = `console | sqlite | postgres`; fail-closed on unknown.
- `isTenantRegistryConfigured(env)`; unset → in-memory/no-op, so nothing is

- Tests: driver selection, unknown driver refuses, production refuses sqlite.

### Task 6 — Tenant attribution on the usage ledger

### Task 7 — Immutable run attribution at acceptance

## Risks and open questions

**R1 — How is the run's tenant persisted?**
Extend the existing run-history store with a `tenant_id` column (one migration,
reuses the proven seam), or a separate `df_run_attribution` table (cleaner
separation, one more join)? *Recommendation: extend run-history* — attribution is
a property of the run, and a separate table invites exactly the re-derivation the
epic forbids. **Needs your call.**

**R2 — Tenant id format.**
`crypto.randomUUID()` (no new dependency, opaque, non-sortable) or a ULID
(sortable, needs a dependency)? *Recommendation: UUID* — sort ordering buys little
here and we already avoid dependencies. **Confirm.**

**R3 — Dashboard surface.**
Add a tenant filter to the existing usage panel, or ship a separate tenant-usage
panel? *Recommendation: separate panel* — the existing panel is model/day
oriented and mixing the two makes both harder to test. **Confirm.**

**R4 — Seeding.**
Is a run-once operator script sufficient, or do you want the seed data in a
migration so it is reproducible in every environment? *Recommendation: script* —
tenant assignments are environment-specific operational data, not schema.

**R5 — Enforcement timing.**
"New customer-tracked runs require an explicit repository-to-tenant assignment"
could be enforced in R1 (unknown repo → refuse the run) or deferred to R2.
*Recommendation: R1 records and reports; R2 refuses* — refusing runs in R1 would
break existing operator work before the seed has been applied everywhere.
