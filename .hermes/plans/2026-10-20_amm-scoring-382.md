# #382 — the AMM scoring model: catalogue, pure scoring, profile

## Ground truth (read, not assumed)

- `agent/lib/dark-factory/amm-readiness.ts` already defines the SHAPE the UI renders — `AmmScan`, `AmmPillar`,
  `AmmSignal`, `AMM_LEVELS`, `AMM_FLOOR_LEVEL` — and R3 (#415, merged) renders it, holding no metric names of its own.
  So this issue's output must PRODUCE THAT SHAPE rather than invent a parallel one, or the UI would need editing to
  consume the real values.
- `agent/lib/sprint-metrics.ts` is the analogue the issue names for a pure metrics module, and the repo already keeps
  domain contracts separate from adapters (ADR 0006), which is the pattern to follow.
- The ingredients exist as tests and config (`dependency-pins.test.ts`, `doc-drift-guards.test.ts`, `adr-integrity`,
  `.mega-linter.yml`, `.gitleaks.toml`, `.github/workflows`) — what is missing is the MODEL that maps them to pillars,
  levels and points.
- R1 (#413) put `organizationalReadiness` in `amm-readiness.ts` and the repo list uses it. That is the SAME metric AC5
  names, so it must end up with ONE implementation, owned here, not a second copy.

## Scope

In: the signal catalogue as data, the pure scoring module, the per-pillar profile, Organizational Readiness.
Out: executing the checks against a checkout (the scanner/runner), and automated remediation — the issue itself
records that it was split from remediation deliberately. **Consequence worth stating plainly: this release does NOT
yet produce real values for this repository.** It makes them computable and testable; a follow-up issue runs the checks
and replaces R3's inferred `present` flags with measured ones.

## Design

**The catalogue is data** — `agent/lib/dark-factory/amm-signals.ts`, one row per signal:

```ts
export type AmmSignalCheck =
  | { kind: "file"; path: string }
  | { kind: "command"; command: string };

export interface AmmSignalDefinition {
  id: string;
  pillar: AmmPillarId;
  level: 1 | 2 | 3 | 4 | 5;   // the point value comes FROM the level: 1/2/4/8/16
  label: string;
  check: AmmSignalCheck;       // automated, never a judgement call (AC6)
  expected: string;            // what the check must show to count as present
  remediation: string;         // what to do when it is absent
  source: string;              // the whitepaper line it comes from (AC1)
}
```

Nothing about a signal lives in code: a reviewer adds or corrects a row without touching the scorer.

**Scoring is pure** — `agent/lib/dark-factory/amm-scoring.ts`:

- `scoreRepo(measurements)` maps each signal to `present | absent | unmeasured` and returns the `AmmScan` shape the UI
  already renders.
- **UNMEASURED is a first-class state, never `present`** (AC3), and it does not count towards a pillar's points; a
  score built on unknowns must not read as a pass.
- Level from points uses the whitepaper's thresholds exactly: **5 / 19 / 36 / 60 / 100**, with L3 as the production
  floor. A score of exactly 36 IS Level 3 (AC2).
- `targetProfile()` gives current versus the Level 5 target per pillar (AC4), which is the radar the whitepaper draws.
- `organizationalReadiness()` reports **at-or-above-the-floor over active repositories as a share** (AC5) — the same
  function the repo list already needs, moved here so there is one.

**One shape, two producers.** The fixture provider and the future measured provider both yield `AmmScan`, so R3's
component and R1's list page are untouched by the change — that is the whole point of building this behind a
contract that already exists.

## Tasks

**Task 1 (RED) — the catalogue's invariants.** Unique ids; every row names a check AND a source; every level in 1..5;
every `check.kind` is `file` or `command` (nothing subjective, AC6); every pillar has at least one signal; and the
point value implied by a level matches the whitepaper's 1/2/4/8/16.

**Task 2 (RED) — the thresholds, at their boundaries.** For each of 5, 19, 36, 60, 100 assert that score → that level,
score−1 → the level below, score+1 → that level, and that 0 is Level 1. Plus: exactly 36 is Level 3 and never
"close enough" to Level 2.

**Task 3 (RED) — unmeasured is not present.** A signal with no measurement is `unmeasured`, contributes no points, and
cannot lift a pillar; a repo whose every signal is unmeasured reports unmeasured rather than a level it has not earned.

**Task 4 (RED) — the profile and readiness.** The profile carries current and target per pillar; readiness is a share
of active repositories (0 with none, 100 with all above the floor) and is not an average of scores.

**Task 5 (GREEN)** — implement the catalogue, the scorer and the profile; point `amm-readiness.ts` at the shared
readiness function instead of keeping its own.

**Task 6** — seed the catalogue from the whitepaper's per-pillar signal lists (the ones already transcribed into R3's
fixture), naming for each signal an automated check that exists in this repository and the whitepaper source line.

## Risks

- **A wrong weight mis-grades silently**, which is why the thresholds are boundary-tested rather than spot-checked.
- **An unmeasurable signal could be counted as present** and inflate a score — the fail-closed rule is tested, because
  a scoring model that flatters itself is worse than one that admits ignorance.
- **Two readiness implementations** would drift, so the existing one moves rather than being duplicated; R1's tests
  keep covering it, which is what makes the move safe.
- **A catalogue row with a vague check** ("code quality is good") would smuggle judgement into a model that forbids it,
  so `check.kind` is structural, not prose.
