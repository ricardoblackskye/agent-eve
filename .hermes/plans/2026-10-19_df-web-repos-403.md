# Epic #403 — Dark Factory web: repo list, repo detail, AMM scale

Plan for R1 (#413), R2 (#414) and R3 (#415). R1 is delivered on this branch; R2 and R3 follow as their own
branches. The AMM scanner itself is out of scope (separate epic).

## Ground truth

| Thing | Reality in the repo |
|---|---|
| Web stack | Next.js 16, React 19, App Router, `app/dark-factory/` already exists |
| Runs API | `app/api/dark-factory/runs/route.ts` and `runs/[runId]/route.ts` already exist |
| Run ledger | `listRuns(...)`, `listRunEvents(...)` on the store |
| AMM | nothing: no scanner, no metrics, no data |

So R1 and R2 compose existing surfaces; only the AMM part is new.

## The seam that keeps R3 cheap

```ts
export interface AmmReadinessProvider {
  scan(repo: string): Promise<AmmScan | undefined>; // undefined = configured but never scanned
}
```

Two adapters: `fixture` (now) and `database` (later, when the scanner exists). The UI reads the interface only, so
the mocked phase and the real phase are the same components. The fixture returns a scan for EVERY configured repo,
which is what makes "hooked = configured AND first-scanned" visible in the mocked phase.

## R1 (#413) — repo list and routing

**Task 1 (RED)** — `configuredRepos()` and the list rule.
- Repos come from the runner's allowed-repo config, split on commas, trimmed, normalized to `owner/repo`.
- A repo is LISTED only when `AmmReadinessProvider.scan()` returns a scan for it. A configured repo with no scan is
  absent. Tests: configured+scanned listed once; configured with no scan absent; unlisted repo never appears; duplicate
  config entries collapse.

**Task 2 (RED)** — the page component.
- `/dark-factory/repos` renders one row per listed repo: name and the AMM overall level from the provider.
- A row links to `/dark-factory/repos/<owner>/<name>`.
- Tests with the existing React/TDD helpers (router hooks), plus a test that a repo WITHOUT a scan has no row.

**Task 3 (GREEN)** — implement the fixture adapter, the list rule and the page. No database reads for AMM.

**Task 4** — the API route for the list (`app/api/dark-factory/repos/route.ts`) so the page is server-rendered from
one source, and the rule is asserted at the boundary too.

**Task 5** — an empty state that names WHY it is empty ("no configured repo has been scanned yet"), because an empty
list that looks like a bug costs a support round trip.

## R2 (#414) — runs table, paged and sorted SERVER-side

**Task 1 (RED)** — paging and sorting in the store.
- Extend `listRuns` with `{ limit, offset, sort, direction }`, returning `{ rows, total }`. Tests: page 2 of 3 is
  correct at a real page size; `total` is the unfiltered count; each sort column orders correctly; ties are broken by
  a stable secondary key so rows do not shuffle between pages; an out-of-range offset returns an empty page, not an
  error.

**Task 2 (RED)** — the API.
- `runs` accepts `limit`, `offset`, `sort`, `direction`, validates them (reject unknown sort columns rather than
  ignoring them) and echoes the effective values. Tests assert the REQUEST the client makes, not the component's
  internal state.

**Task 3 (GREEN)** — the table with **TanStack Table using manual pagination and sorting**, TanStack Query for
fetching, and a page-size control. Render rows lazily only if a real page can exceed a few hundred rows.

## R3 (#415) — AMM readiness scale

**Task 1 (RED)** — the provider contract and the fixture: overall level plus per-metric score.
**Task 2 (RED)** — the scale component renders EVERY metric from provider data. A fixture with a different metric set
must render correctly, which is what proves nothing is hard-coded.
**Task 3 (GREEN)** — implement, including the "not yet scanned" state.
**Task 4** — a stub database adapter in the tests proves the swap needs no component edit.

## Validation (each release)

- `npx tsc --noEmit --incremental false`
- the component/unit tests, then the full suite
- `npx cspell -c .cspell.json` over the WHOLE diff (staged first)
- a local run of the page against fixture data, with the URL, page number and sort shown — provable on the laptop
- Playwright covers the list → detail → runs journey once R2 lands

## Risks

- **TanStack is a dependency decision.** Recommend `@tanstack/react-table` (manual mode) and `@tanstack/react-query`;
  if you would rather not add Query, R2 can fetch with plain `fetch` in a server component, at the cost of client-side
  page changes becoming server round trips either way.
- **"Configured" must have one definition.** The runner already reads an allowed-repo setting; the web app must read
  the SAME value rather than introducing a second list, or the page and the worker will disagree.
- **Mock data retires.** R3's fixture must not leak metric names into components, or the real scanner's metrics will
  need UI edits.
- **Paging is a store change, not a table trick.** A browser-side sort over one fetched page silently lies about the
  other pages; the acceptance is a request-level assertion for exactly that reason.
