## AMM shape, taken from the real scan (not invented)

The current scan of `ricardoblackskye/agent-eve` is the fixture's source of truth:

- **Overall:** Level 4 (Optimized), **74 / 100 points**. Levels are exponential-weight bands:
  **L1 Functional 5**, **L2 Documented 19**, **L3 Standardized 36 (the production-grade FLOOR)**, **L4 Optimized 60**,
  **L5 Software Factory 100**.
- **Dimension 1 - eight technical pillars**, each with a level and the evidence that earned it:

| # | Pillar | Level |
|---|---|---|
| 1 | Style & Validation | 4 |
| 2 | Build System | 4 |
| 3 | Testing | 4+ |
| 4 | Documentation & Instructions | 5 |
| 5 | Dev Environment & Remote Execution | 4+ |
| 6 | Code Quality | 4 |
| 7 | Debugging & Observability | 4 |
| 8 | Security & Governance | 4.5 |

- **Dimension 2 - capability surfaces** (triage, orchestration, guardrail-enforced execution, code review, dynamic QA,
  model routing, release automation, outcome measurement, self-improving pipelines), each with a maturity stage.
- Each pillar carries a benchmark definition and a list of evidence references, which the detail page can render
  as the "why this score" column.

```ts
interface AmmScan {
  repo: string;
  scannedAt: string;
  overall: { points: number; maxPoints: number; level: number; label: string }; // 74 / 100, Level 4 (Optimized)
  pillars: Array<{ id: number; name: string; level: number; label: string; benchmark: string; evidence: string[] }>;
  capabilities: Array<{ name: string; stage: string; summary: string }>;
}
```

The fixture carries the figures above, so R3's UI is built against real data. The level bands, the L3 floor and the
board-level Organizational Readiness metric - `(repos at Level 3+ / active repos) x 100` - come from the same scan.

## What the whitepaper adds (the scanner's checklist, R4's contract)

From `The-Software-Factory-Autonomy-Maturity-Model.pdf`:

- **Signals are BINARY**: present or absent, "no partial credit and no subjective judgment", machine-checkable and
  measurable in under five minutes per repository. Point values per signal: **L1 1, L2 2, L3 4, L4 8, L5 16**.
- **Each pillar has its own signal list.** Examples: pillar 1 - linter enforced, type checker active, formatter
  standardized, pre-commit hooks, validation under 30 seconds. Pillar 6 - files under 500 lines, functions under
  50, complexity under 15, clear boundaries, consistent naming. Pillar 8 - branch protection, secret scanning,
  CODEOWNERS, dependency scanning, STRIDE threat modeling, sandbox enforcement. These lists are the scorer's
  checklist, so they belong to R4 - not hard-coded into the UI.
- **The leadership metric** is Organizational Readiness = `(repos at Level 3+ / active repos) x 100`, with the
  explicit advice that "80% of our active repos are agent-ready" beats "average score 73.2%". That is the headline
  for the repo LIST page (R1), once more than one repo has a scan.
- **Per-repository profile** is the eight pillars plotted as **current versus the Level 5 target** - the radar view.
  R3 renders the scale; the same data supports the radar later without a contract change.
- **Lagging outcome metrics** (cycle time, autonomy ratio, code shelf life, incident mean time to restore, cost per change) are
  deliberately separate from readiness: readiness is the leading indicator. The runs view is where those can land.

So R3 shows, per pillar: level, points, the benchmark, and which signals are present - while the signal catalogue
stays data, so the scanner can supply it later without UI edits.

## TanStack is DEFERRED (decision, 2026-10-19)

R2 ships with the existing fetch pattern and server-side paging parameters. TanStack Table/Query is a **later
change**, revisited when the row volume justifies it: the server-side contract R2 builds (limit, offset, sort) is
exactly what the swap will need, so deferring costs nothing and adding it early buys nothing.

## The seam that keeps R3 cheap

```ts
export interface AmmReadinessProvider {
  scan(repo: string): Promise<AmmScan | undefined>; // undefined = configured but never scanned
}
```

Two adapters: `fixture` (now) and `database` (later, when the scanner exists). The UI reads the interface only, so
the mocked phase and the real phase are the same components. The fixture returns a scan for EVERY configured repo,
which is what makes "hooked = configured AND first-scanned" visible in the mocked phase.

## R1 (#413) — repo list and routing

**Task 1 (RED)** — `configuredRepos()` and the list rule.
- Repos come from the runner's allowed-repo config, split on commas, trimmed, normalized to `owner/repo`.
- A repo is LISTED only when `AmmReadinessProvider.scan()` returns a scan for it. A configured repo with no scan is
  absent. Tests: configured+scanned listed once; configured with no scan absent; unlisted repo never appears; duplicate
  config entries collapse.

**Task 2 (RED)** — the page component.
- `/dark-factory/repos` renders one row per listed repo: name and the AMM overall level from the provider.
- A row links to `/dark-factory/repos/<owner>/<name>`.
- Tests with the existing React/TDD helpers (router hooks), plus a test that a repo WITHOUT a scan has no row.

**Task 3 (GREEN)** — implement the fixture adapter, the list rule and the page. No database reads for AMM.

**Task 4** — the API route for the list (`app/api/dark-factory/repos/route.ts`) so the page is server-rendered from
one source, and the rule is asserted at the boundary too.

**Task 5** — an empty state that names WHY it is empty ("no configured repo has been scanned yet"), because an empty
list that looks like a bug costs a support round trip.

## R2 (#414) — runs table, paged and sorted SERVER-side

**Task 1 (RED)** — paging and sorting in the store.
- Extend `listRuns` with `{ limit, offset, sort, direction }`, returning `{ rows, total }`. Tests: page 2 of 3 is
  correct at a real page size; `total` is the unfiltered count; each sort column orders correctly; ties are broken by
  a stable secondary key so rows do not shuffle between pages; an out-of-range offset returns an empty page, not an
  error.

**Task 2 (RED)** — the API.
- `runs` accepts `limit`, `offset`, `sort`, `direction`, validates them (reject unknown sort columns rather than
  ignoring them) and echoes the effective values. Tests assert the REQUEST the client makes, not the component's
  internal state.

**Task 3 (GREEN)** — the table with **TanStack Table using manual pagination and sorting**, TanStack Query for
fetching, and a page-size control. Render rows lazily only if a real page can exceed a few hundred rows.

## R3 (#415) — AMM readiness scale

**Task 2 (RED)** — the scale component renders EVERY metric from provider data. A fixture with a different metric set

## Risks

- **TanStack is deferred, so R2 must not presuppose it.** Keep the paging contract at the API boundary
  (limit, offset, sort, filter) and keep table rendering dumb: that is the seam the later swap plugs into.
- **"Configured" must have one definition.** The runner already reads an allowed-repo setting; the web app must read
  the SAME value rather than introducing a second list, or the page and the worker will disagree.
- **Mock data retires.** R3's fixture must not leak metric names into components, or the real scanner's metrics will
  need UI edits.
- **Paging is a store change, not a table trick.** A browser-side sort over one fetched page silently lies about the
  other pages; the acceptance is a request-level assertion for exactly that reason.
