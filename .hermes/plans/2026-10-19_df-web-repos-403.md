## AMM shape, taken from the real scan (not invented)

The current scan of `ricardoblackskye/agent-eve` is the fixture's source of truth:

- **Overall:** Level 4 (Optimized), **74 / 100 points**. Levels are exponential-weight bands:
  **L1 Functional 5**, **L2 Documented 19**, **L3 Standardized 36 (the production-grade FLOOR)**, **L4 Optimized 60**,
  **L5 Software Factory 100**.
- **Dimension 1 - eight technical pillars**, each with a level and the evidence that earned it:

| # | Pillar | Level |
|---|---|---|
| 1 | Style & Validation | 4 |
| 2 | Build System | 4 |
| 3 | Testing | 4+ |
| 4 | Documentation & Instructions | 5 |
| 5 | Dev Environment & Remote Execution | 4+ |
| 6 | Code Quality | 4 |
| 7 | Debugging & Observability | 4 |
| 8 | Security & Governance | 4.5 |

- **Dimension 2 - capability surfaces** (triage, orchestration, guardrail-enforced execution, code review, dynamic QA,
  model routing, release automation, outcome measurement, self-improving pipelines), each with a maturity stage.
- Each pillar carries a benchmark definition and a list of evidence references, which the detail page can render
  as the "why this score" column.

```ts
interface AmmScan {
  repo: string;
  scannedAt: string;
  overall: { points: number; maxPoints: number; level: number; label: string }; // 74 / 100, Level 4 (Optimized)
  pillars: Array<{ id: number; name: string; level: number; label: string; benchmark: string; evidence: string[] }>;
  capabilities: Array<{ name: string; stage: string; summary: string }>;
}
```

The fixture carries the figures above, so R3's UI is built against real data. The level bands, the L3 floor and the
board-level Organizational Readiness metric - `(repos at Level 3+ / active repos) x 100` - come from the same scan.

## What the whitepaper adds (the scanner's checklist, R4's contract)

From `The-Software-Factory-Autonomy-Maturity-Model.pdf`:

- **Signals are BINARY**: present or absent, "no partial credit and no subjective judgment", machine-checkable and
  measurable in under five minutes per repository. Point values per signal: **L1 1, L2 2, L3 4, L4 8, L5 16**.
- **Each pillar has its own signal list.** Examples: pillar 1 - linter enforced, type checker active, formatter
  standardized, pre-commit hooks, validation under 30 seconds. Pillar 6 - files under 500 lines, functions under
  50, complexity under 15, clear boundaries, consistent naming. Pillar 8 - branch protection, secret scanning,
  code ownership rules, dependency scanning, STRIDE threat modeling, sandbox enforcement. These lists are the scorer's
  checklist, so they belong to R4 - not hard-coded into the UI.
- **The leadership metric** is Organizational Readiness = `(repos at Level 3+ / active repos) x 100`, with the
  explicit advice that "80% of our active repos are agent-ready" beats "average score 73.2%". That is the headline
  for the repo LIST page (R1), once more than one repo has a scan.
- **Per-repository profile** is the eight pillars plotted as **current versus the Level 5 target** - the radar view.
  R3 renders the scale; the same data supports the radar later without a contract change.
- **Lagging outcome metrics** (cycle time, autonomy ratio, code shelf life, incident mean time to restore, cost per change) are
  deliberately separate from readiness: readiness is the leading indicator. The runs view is where those can land.

So R3 shows, per pillar: level, points, the benchmark, and which signals are present - while the signal catalogue
stays data, so the scanner can supply it later without UI edits.

## TanStack is DEFERRED (decision, 2026-10-19)

R2 ships with the existing fetch pattern and server-side paging parameters. TanStack Table/Query is a **later
change**, revisited when the row volume justifies it: the server-side contract R2 builds (limit, offset, sort) is
exactly what the swap will need, so deferring costs nothing and adding it early buys nothing.

## The seam that keeps R3 cheap

```ts
export interface AmmReadinessProvider {
  scan(repo: string): Promise<AmmScan | undefined>; // undefined = configured but never scanned
}
```

Two adapters: `fixture` (now) and `database` (later, when the scanner exists). The UI reads the interface only, so
the mocked phase and the real phase are the same components. The fixture returns a scan for EVERY configured repo,
which is what makes "hooked = configured AND first-scanned" visible in the mocked phase.

## R2 (#414) — runs table, paged and sorted SERVER-side

**Task 0 - the board menu item, because the page was unreachable without it.**
- **Why:** R1 shipped `/dark-factory/repos` with no entry point, so the only way to reach it was to type the URL. A page
  nobody can navigate to is not delivered.
- **What:** a third rail link in `app/dark-factory/layout.tsx`, labelled **Repositories**, placed directly **under
  Runs**, pointing at `/dark-factory/repos`.
- **Label:** "Repositories" matches the page heading; "Repos" would be an abbreviation the rail has to explain.
- **Test (RED):** render the layout and assert the rail's ORDER -
  `["/dark-factory", "/dark-factory/runs", "/dark-factory/repos"]` - not merely that a link exists. A link that drifts
  above Runs is the same miss in different clothes.
- **Acceptance:** one click from the board reaches the page, and the rail order is pinned by a test.
- **Separate work, by decision (2026-10-20):** marking the active item (`aria-current`), tracked as **#418**. Overview
  and Runs have no active state either, so it is one shared helper for all three links rather than a one-link tweak. The
  trap recorded there: `/dark-factory` is a PREFIX of the other two routes, so a naive prefix match marks Overview active
  everywhere in the board.
- **Status:** done on this branch - RED `fe1820f`, GREEN `7ce0742`.


**Task 1 (RED) - the repo DETAIL route, because it does not exist.**
- R1's list links every row to `/dark-factory/repos/<owner>/<name>`, and that route was never built, so **every row
  currently 404s**. This is a live defect, not a nicety: the epic's "click a row, get a detail page" is half done.
- The route hosts the two things the epic asks for: the AMM readiness scale (R3) and the runs table (here).

**Task 2 (RED) - SORTING in the store. This plan was wrong about paging, and the code said so.**
- `listRuns` ALREADY pages: it takes `RunListOptions` (`limit`, `cursor`, plus repo/issue/status/from/to) and returns
  `Page<RunSummary, RunCursor>` = `{ items, nextCursor }`. There is no offset and no total, and inventing them would be a
  second paging model beside the one in use.
- What is genuinely missing is **order**: `RunListOptions` has no sort field. Add `sort` + `direction`, applied in both
  drivers (sqlite and postgres) with a STABLE tie-break on the run id, so rows cannot shuffle between pages.
- Tests: each sort column and both directions; a stable tie-break proven by paging a set with equal sort keys and
  checking no row appears twice or goes missing; an unknown sort field refused rather than ignored.

**Task 3 (RED) - the API.**
- `app/api/dark-factory/runs/route.ts` already exists, resolves the viewer (auth) and parses params into `RunListParams`.
  Add `sort` + `direction` there and in `run-query.ts`. An unknown sort column must be REJECTED: silently ignoring it
  shows unsorted data, which an operator reads as a data bug.
- Tests assert the REQUEST the client makes, since a browser-side sort over one fetched page lies about the others.

**Task 4 (GREEN) - the detail page and its table.**
- Server-side sorting over the existing cursor paging (Next/Previous from `nextCursor`), a page-size control, and a sort
  control per column. Table rendering stays dumb: the API contract is the seam the deferred TanStack swap plugs into.

**Open decision for the detail page:** cursor paging carries no `total`, so the UI can offer Next/Previous but not
"page 2 of 5". Either accept cursor-only navigation, or add a count to the page payload - say which.

**Status (2026-10-20, branch `feat/df-repo-detail-414`).**
- **Task 0 - done.** RED `fe1820f`, GREEN `7ce0742`.
- **Task 2 - done.** RED `262f51f` (three failures: ascending ignored, the cursor did not follow the order, an unknown
  field accepted), GREEN `180e2ab`. Scope settled by the code, not by preference: `RunCursor` is `{ createdAt, runId }`
  and its WHERE compares those columns, so a keyset cursor cannot resume an ordering by any other column. `createdAt`
  asc/desc ships now; ordering by status/repo/issue needs a cursor carrying its own sort key.
- **Task 3 - done.** The request now carries the order the whole way: query string -> `RunListParams` ->
  `validateRunListParams` (refusing an unknown column or a direction that is neither asc nor desc, which the route
  surfaces as a 400) -> `RunListRequest` -> `queryRunList` -> `store.listRuns`. A RED caught that validating a sort the
  query layer never forwarded is worse than refusing it: the client gets a 200 and unsorted rows.
- **Task 1 and Task 4 - done at unit level.** The detail route exists (it did not, so every row 404'd), driven through
  the environment and asserted on the REQUEST it makes. Cursor paging has no back-pointer, so Previous walks a trail of
  used cursors with an empty string standing for the first page.
- **Known limitation, recorded not hidden:** the cursor does not name the order it was issued under, so a client that
  switches sort mid-pagination gets incoherent pages. That is the same follow-up as ordering by other columns.
- **Remaining before the PR is complete:** the Playwright journey (list -> detail -> runs) named in Validation, and a
  decision on whether the detail page should offer a column picker once the generic cursor exists.

## Risks

- **TanStack is deferred, so R2 must not presuppose it.** Keep the paging contract at the API boundary
  (limit, offset, sort, filter) and keep table rendering dumb: that is the seam the later swap plugs into.
- **"Configured" must have one definition.** The runner already reads an allowed-repo setting; the web app must read
  the SAME value rather than introducing a second list, or the page and the worker will disagree.
- **Mock data retires.** R3's fixture must not leak metric names into components, or the real scanner's metrics will
  need UI edits.
- **Paging is a store change, not a table trick.** A browser-side sort over one fetched page silently lies about the
  other pages; the acceptance is a request-level assertion for exactly that reason.
