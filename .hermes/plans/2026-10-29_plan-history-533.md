# The estimator is given history Implementation Plan (#533, epic #453)

> **For Hermes:** execute with the repo's own TDD discipline (RED -> GREEN per task, separate
> commits), then stop at GATE 2 for PR authorization.

**Goal:** pass the repository's finished runs into the plan estimate, so `confidence` stops being
`"low"` forever and `revisionFactor` stops being `1` forever — and stamp the change, because the same
plan now yields a different band.

**Architecture:** the estimator stays PURE. A composition-root step in the runner reads the window from
the store it already holds and hands it in as `history`; a small pure selector decides which runs are
usable. Best-effort throughout: a history that cannot be read is no worse than today.

**Tech Stack:** TypeScript, Vitest, the existing run-history store, no new dependency.

---

## Verified findings (the reconnaissance this plan rests on)

### Two of the estimator's inputs read as measured, and neither is

`estimatePlanCostSafely({ plan: executionPlan, model: modelId })` — `dark-factory-runner.ts:927` — passes
no `history`. With it empty:

- `confidenceFor([])` returns `"low"`, and `revisionFactorFor([])` returns `1`, so every plan is stamped
  with a confidence that counts nothing and a factor that scales nothing;
- `history_samples` on every persisted estimate is 0.

The whole middle of the estimator is therefore inert: the band is the cold-start band, always.

### The signals are already recorded, and the store can produce them

`revisionFactorFor` sums exactly `RunSummary.iterationCount` and `fixCycleCount`, both required fields on
every run — and `RunSummary` is what `history` already takes. `listRuns` accepts what the window needs:
`repo`, `statuses`, `limit`, `sort` and `direction`, returning a `Page`. The runner holds the store in
scope where it estimates (`runHistory`, built at line 320, used at 927).

Run statuses are `queued | running | blocked | aborted | succeeded | failed`, so "finished" is
`succeeded | failed | aborted`.

### Why the version has to move

`PLAN_ESTIMATOR_VERSION` exists so a later recalibration can never average bands produced by a different
model of the world — its own words: *"Bump this whenever a constant below changes."* No constant changes
here, but the BAND does: the same plan for a repository with history yields a scaled expectation. So the
identity of what produced a band changes, and the stamp must say so.

### Dispersion-aware confidence is now possible, and is its own change

`confidenceFor` carries the note *"Coarse on purpose: dispersion-aware confidence needs the estimate/actual
pairs #490 builds."* Those pairs now exist, end to end (#490, #531, #532). A dispersion-aware label is
therefore feasible — but it needs a second input on a deliberately pure, single-input module, and it
changes what the label MEANS. That is a separate decision with its own risk, so it belongs in its own
issue rather than being smuggled into a wiring change.

## Global constraints

- The estimator stays PURE: no store, no clock, no environment. The window is read by the caller.
- The window is the repository's FINISHED runs, newest first, capped. A `blocked` run is parked, so its
  counters are incomplete, and `queued`/`running` have not run at all.
- Failures are inclusive: a failed or aborted run's revision counts are exactly the thrash this factor
  exists to capture, and including them can only raise the band — never understate it.
- Best-effort: a history that cannot be read produces a warning and an estimate without it, never a failed
  plan.
- No content: counts, statuses and ids only.

## Review focus

- **The window must not include an unfinished run.** A fixture with `blocked`, `queued` and `running`
  alongside finished ones must exclude all three, since a park's counters are not a completed outcome.
- **A thin window must not be treated as an empty one.** One usable run scales the band just as ten do;
  only zero is the cold start. Assert both.
- **A single malformed counter must not poison the factor.** A row carrying `NaN` or a negative count is
  dropped rather than averaged, because one bad row would otherwise make the whole band `NaN`.
- **The version assertion is not decoration.** Assert the persisted estimate's stamp is `v2`, so a band
  from the new behaviour cannot be averaged with the old one.

/** How many finished runs the estimator looks back over. */

/** Statuses whose counters describe a finished run. `blocked` is a park, not an outcome. */

## Settled decisions (agreed at GATE 1)

1. **The window is the repository's finished runs, newest first, capped at 20, failures included.** A
   failed run's revision counts are precisely the thrash this factor exists to capture, and including them
   can only raise the band — the safe direction, since understating is the failure that matters.
2. **`blocked` does not count as finished.** A park is a wait: its counters describe an incomplete
   outcome, and a parked plan says nothing about how much revision the work needed.
3. **The estimator's version moves to `v2`.** No constant changed, but the band does for the same input,
   and the stamp exists so a later calibration cannot average two different behaviours.
4. **Dispersion-aware confidence becomes its own issue.** It needs a second input on a module kept pure on
   purpose, and it changes what the label means — a separate decision, not a smuggled-in one. The pairs it
   needs now exist end to end (#490, #531, #532).
5. **A history read failure warns and estimates without it.** Best-effort, consistent with every other
   telemetry seam: a plan must never fail because its calibration history was unavailable.

## Risks that remain

- **The band rises for repositories with history**, which is the intent — but it means a plan's class can
  move (XS to S) for the same story. The `v2` stamp is what keeps those two regimes apart in the ledger.
- **The window is per repository, not per issue type.** A repository mixing very different work sizes
  feeds one factor; that is coarser than the data allows, and is the kind of thing the calibration report
  (#490) can inform later rather than something to guess at now.
