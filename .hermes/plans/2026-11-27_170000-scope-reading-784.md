# State the classification the plan's target choice rests on (#784)

**Issue:** [agent-eve#784](https://github.com/ricardoblackskye/agent-eve/issues/784) (`enhancement`) - R3's Task 5
**Branch:** `feat/784-scope-reading` (from `origin/main` @ `9d25b52`, 0 behind)
**Status:** plan only. No code until GATE 1.

## Why we are doing this

A plan tells an approver which file it will change. What it does not say is **why that file**, when the story names a
different one. Two plans that look identical can rest on opposite readings of the same story.

R4's runs are the worked example. Both of them - and the three earlier runs of the same story - targeted the
application shell for a story that says "the home page", and both passed validation. They were *correct*, because a
footer credit reads as shell-scoped work: it is not a change to one page. But nothing in the plan says that. An
approver reading it cannot tell "the shell is right because this story reads as shell-scoped" from "the plan picked the
shell by accident", and those two demand different responses.

**What changes:** the plan states the reading its target choice rests on, in the same place as the substitution
declaration, so the two conclusions are distinguishable from the plan alone.

**What this does not change:** it changes no decision. The classifier is untouched, no target moves, and the plan is not
refused for anything new. This release makes a decision legible; it does not make it. Whether a footer-credit story
*should* read as page-scoped is a policy question, deliberately left open - widening the classifier to answer it would
be the silent reclassification the epic exists to refuse.

## Recon, read rather than assumed

| what                                    | where                                                                                                             |
|:----------------------------------------|:------------------------------------------------------------------------------------------------------------------|
| the shell reading                       | `plan-validator.ts:312` - `isShellScopedStory(storyText)`, **exported**                                           |
| the page reading, with shell precedence | `plan-validator.ts:321` - `isPageScopedStory(storyText)`, **exported**; returns false when the shell reading wins |
| where the plan is rendered              | `scripts/dark-factory-runner.ts:1224` (the plan comment) and `:1568` (the plan file)                              |
| what the architect already records      | `architect-agent.ts:896` - `refusedTarget`, true when the target-role rule fired in any attempt                   |

Both classifications are pure functions of the story text and both are already exported, so the reading can be derived
wherever the story is available. The validator already acts on exactly these two inputs - which means the plan can
state **the same reading the validator used**, rather than a second opinion computed somewhere else.

## Design

1. **One line, at the top of the plan, beside the substitution declaration.** They answer the same question from two
   sides: the declaration says *what was chosen*, the reading says *what it was chosen against*. Putting them together
   is what makes an approver able to tell a deliberate substitution from an accident.
2. **Rendered from the same inputs the validator uses** - the two exported classifiers - so the plan cannot state a
   reading the rules disagreed with.
3. **Three cases, including the honest one.** Shell-scoped, page-scoped, and *neither* - because a story that matches
   no scope signal is a real case, and saying so is better than implying a reading was made when none was.
4. **Phrased in general terms**: what the story reads as, and what that implies for the target. No repository, vendor,
   framework or path.

## Tasks

### Task 1 (RED) - a shell-scoped story renders the shell reading

The case that motivated the issue: the story reads as shell-scoped, so the plan says the shell target is intended
rather than accidental.

### Task 2 - a page-scoped story renders the page reading

The opposite case, which must be distinguishable at a glance rather than by absence.

### Task 3 - a story matching no scope signal says so

The honest third case. Without it, "no line" would be ambiguous between *not rendered*, *not computed* and *no reading*.

### Task 4 - the line is at the top, before any section

The same placement assertion the substitution declaration carries, and for the same reason: a reading buried in the
approach prose is the thing this is meant to fix.

### Task 5 - it names no repository, vendor, framework or path

Asserted as an absence, the shape used for R2's approved set and #787's rule.

## A stated limit

The plan will **not** say whether the target-role rule fired during planning - only what the story reads as. That flag
(`refusedTarget`, `architect-agent.ts:896`) is a local of the architect's loop and would need surfacing on its result
first. The acceptance for this issue is that the *reading* is visible, and a plan that states its reading already lets
an approver judge the choice; the flag would add provenance, not legibility. Named as out of scope rather than quietly
dropped.

## Verification

- RED then GREEN committed separately, each verified in its direction, with the third case as a control.
- The rendered plan read back from a real render, not asserted against the renderer's inputs.
- The renderer's own suites (`plan-comment`, `plan-comment-formatting`) run **with** the change, since they exercise
  the same function.
- `tsc --noEmit` clean, cspell over changed files, full gate and coverage ratchet before any PR.

## Out of scope

- **Widening the classifier.** The policy question - should a footer-credit story read as page-scoped - is recorded on
  #780 and stays a decision.
- **A deterministic selector.** #787 measured the variance on that axis as reduced, and no selector is warranted.
- **Surfacing `refusedTarget`.** Provenance, not legibility; above.
- **Any repository-specific rule.**
