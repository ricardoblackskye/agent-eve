# Dark Factory Run Control Plane (off-switch) Implementation Plan — issue #207

> **For Hermes:** Implement with strict RED→GREEN→REFACTOR TDD, one behavior at a
> time. Do not start implementation until the user approves this plan.

**Goal:** Give the operator a dynamic off-switch from the Dark Factory dashboard:
pause/resume the factory (globally) and individual runs, and explicitly stop a
run — with the current control state visible on the dashboard. Cooperative by
default; only Stop is destructive.

**Architecture:** A provider-neutral `ControlStore` seam (canonical control
state + append-only audit), a gate consulted by the `Dispatcher` before any work
is scheduled, a `control-service` application service (framework-free), HTTP
handlers under `app/api/dark-factory/control`, and a dashboard control panel that
extends the #200 board. Control state is **dynamic runtime state** and lives in
Postgres/Supabase; LLM **policy** config stays in Vercel env (R7.2).

**Tech Stack:** TypeScript, Next.js 16 App Router, React 19, plain CSS, Vitest
(+ `jsdom` + `@testing-library/react` from #200), `node:sqlite` locally, `pg` in
deployments.

## Decisions (confirmed with the user)

1. **Scope = all three LLM surfaces** (orchestrator, sandbox Dev/Tester, PR
   review) — but only the *control plane* is in this release; policy is R7.2.
2. **Cooperative pause + an explicit Stop action.** Pause stops scheduling and
   holds a run at its next safe checkpoint (resumable). Stop destroys the sandbox
   and is terminal.
3. **Control state is DB-backed** (Postgres/Supabase) — an off-switch that needs
   a redeploy is not an off-switch. (LLM policy settings are env — R7.2.)
4. **Ship both global and per-run** control.

## Canonical control model

Provider-agnostic types; no vendor fields, JSON-serializable (so the same seam
serves SQLite locally and Postgres in deployment).

```ts
export type ControlScope = "factory" | "run";
export type ControlAction = "pause" | "resume" | "stop";

export interface FactoryControlState {
  paused: boolean;
  updatedAt: string;
  actor?: string;
  reason?: string;
}

export interface RunControlState {
  paused: boolean;
  stopped: boolean;
  updatedAt: string;
  actor?: string;
  reason?: string;
}

export interface ControlEvent {
  at: string;
  actor: string;
  action: ControlAction;
  scope: ControlScope;
  runId?: string;
  reason?: string;
}

export interface ControlStore {
  id: string;
  readFactory(): Promise<ControlReadResult<FactoryControlState>>;
  writeFactory(state: FactoryControlState): Promise<ControlWriteResult>;
  readRun(runId: string): Promise<ControlReadResult<RunControlState>>;
  writeRun(runId: string, state: RunControlState): Promise<ControlWriteResult>;
  appendEvent(event: ControlEvent): Promise<ControlWriteResult>;
  listEvents(limit?: number): Promise<ControlReadResult<ControlEvent[]>>;
  close?(): void;
}
```

Adapters mirror the existing seam pattern exactly:

- `ConsoleControlProvider` — fail-closed default; every operation returns
  `mode: "blocked"` with an explicit "not configured" error (never pretends to
  have persisted state).
- `SqliteControlAdapter` — local dev/ephemeral; tables `df_factory_control`,
  `df_run_control`, `df_control_events`; exposes `close()` (Windows file locking).
- `PostgresControlAdapter` — deployed; same tables in Supabase; `CREATE TABLE IF
  NOT EXISTS` + idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, matching
  `run-history-postgres.ts`.
- `createControlStore(env)` — single selector on `DF_CONTROL_DRIVER`
  (`console` | `sqlite` | `postgres`). **Fail-closed**: unset in a deployed
  runtime → `console` (refuses); `sqlite` in production/preview → refused, as the
  run-history provider does.

## Control gate semantics (the design crux)

The gate is read at the very top of `Dispatcher.dispatch()`, **before** any
`DispatchRecord` is persisted.

| Condition                | Outcome                                                         | Persisted? | Retry consumed?          |
|--------------------------|-----------------------------------------------------------------|------------|--------------------------|
| Factory paused           | `{ ok: true, status: "paused", gate: "factory", paused: true }` | **no**     | no                       |
| Run paused               | `{ ok: true, status: "paused", gate: "run", paused: true }`     | **no**     | no                       |
| Run stopped              | `{ ok: true, status: "stopped", gate: "run", stopped: true }`   | **no**     | n/a (terminal in ledger) |
| Control store unreadable | `{ ok: true, status: "paused", gate: "unavailable", error }`    | **no**     | no                       |
| Not gated                | unchanged normal dispatch                                       | yes        | as today                 |

Two rules matter and must be asserted by tests:

1. **A gated outcome is NEVER persisted as a `DispatchRecord`.** Persisting it
   would make a later delivery look like a *duplicate* and permanently swallow a
   paused run — the pause would silently become a cancel. `ok: true` here means
   "this call was handled" (the same convention the duplicate path already
   documents); the gate state travels in `gate` / `paused` / `stopped`.
2. **Fail-closed on an unreadable control store.** Refuse to schedule and report
   the reason honestly; never fall through to "running" because the gate could
   not be read.

Checkpoint semantics inside the worker loop:

- Add `PausedRunError` (peer of `ParkedRunError`): thrown by a worker handler that
  observes a pause at a step boundary. The dispatcher records `paused` and stops
  **without** retry or backoff — resumable.
- Add `StoppedRunError`: a handler that observes a stop destroys its sandbox via
  the existing `WorkerProvider.destroy()` seam and the run is recorded terminal
  `aborted`.
- **Honest limitation (state it in code comments and docs):** JavaScript cannot
  cancel an in-flight promise. A pause/stop takes effect at the handler's next
  checkpoint; the existing `handlerTimeoutMs` bounds how long the loop waits.

## Implementation tasks (TDD)

### Task 1: Canonical control model + validators (`control.test.ts`)

RED first: `toControlEvent` / `toFactoryControlState` / `toRunControlState` accept
a valid payload and **throw** a named `InvalidControlError` for a missing actor,
an unknown action/scope, and a `run`-scoped event without a `runId`. One behavior
per cycle. Run `npx vitest run tests/dark-factory/control.test.ts`.

### Task 2: `ConsoleControlProvider` fail-closed (`control.test.ts`)

Every method returns `{ ok: false, mode: "blocked", providerId: "console" }` with
an explicit "not configured" error — mirroring `ConsoleStateProvider`. Assert the
gate therefore reads as *unavailable* (never as "not paused").

### Task 3: `SqliteControlAdapter` (`control.test.ts`)

RED→GREEN per behavior: factory state round-trip (paused true/false); run state
round-trip (`paused`, `stopped`); audit append + `listEvents` order; absent row →
`ok: true, value: null` (not an error); unreachable path (a non-existent nested
dir, no `mkdtemp`) → `ok: false, mode: "blocked"` with "unreachable"; `close()`
releases the handle so teardown can delete the file (Windows).

### Task 4: `createControlStore` selector (`control.test.ts`)

- unset → `console` (fail-closed) in a deployed runtime; `sqlite` refused in
  production/preview;
- `sqlite` + `DF_CONTROL_DB_PATH` → `SqliteControlAdapter`;
- `postgres` + URL (or run-history fallback) → `PostgresControlAdapter`;
- an unknown driver THROWS a config error rather than defaulting open.

### Task 5: Dispatcher gate (`dispatch-control-gate.test.ts`)

With a fake in-memory `ControlStore` and the existing `StateStore` fakes:

- factory paused → `status: "paused"`, `gate: "factory"`, `ok: true`, **handler
  never called**, **no record saved** (assert the store's save was not called);
- run paused → `gate: "run"`;
- run stopped → `status: "stopped"`, handler not called;
- control store unreadable → `status: "paused"`, `gate: "unavailable"`, `ok: true`,
  handler not called (fail-closed);
- **resume is not a duplicate:** dispatch while paused (nothing persisted), then
  clear the flag and dispatch again → the handler RUNS (proves the pause did not
  consume the at-most-once guard);
- `PausedRunError` from the handler → recorded `paused`, `attempts` not
  incremented per retry, `sleep` never called (park-like);
- `StoppedRunError` from the handler → `status: "stopped"` / terminal, no retry.

### Correction (discovered during implementation)

`scripts/dark-factory-runner.ts` does **not** drive the Architect/Developer LLM
loops through `Dispatcher`/`WorkerProvider`. It calls `architectAgent.planStory(...)`
and `runMultiFileCodingLoop(...)` directly. A dispatcher gate alone would therefore
NOT control those LLM calls. The cooperative checkpoint must be injected at the
runner's own loop boundaries.

### Task 13: Runner cooperative checkpoint wiring

## Risks / open questions

- **The at-most-once interaction is the sharp edge.** A gated outcome must not be
  persisted; the plan pins this with an explicit "resume is not a duplicate" test.
  If review prefers a persisted `paused` record, the resume path must clear it —
  decided against because it makes pause-by-accident unrecoverable.
- **Stop takes effect at the next checkpoint, not instantly.** Documented honestly in code and docs; the
  sandbox teardown reuses `WorkerProvider.destroy()`.
- **Two Postgres tables/URLs.** The adapter falls back to
  `DF_RUN_HISTORY_DATABASE_URL` so a deployment needs no second secret; if a
  separate URL is wanted, `DF_CONTROL_DATABASE_URL` wins.
- **Dashboard polling cadence.** Reuses the #200 interval approach; no realtime
  channel in this release.
