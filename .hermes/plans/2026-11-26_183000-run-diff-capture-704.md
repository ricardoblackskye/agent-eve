## The defect, measured rather than described

`git_diff` is never written, so the run-details page renders "No diff captured" on every run. The machinery works
and is unit-tested; **the seam is not wired into production.**

Evidence from the repository (ripgrep, verified):

| Fact                           | Where                                                                                                                            |
|:-------------------------------|:---------------------------------------------------------------------------------------------------------------------------------|
| The capture exists             | `diff-capture.ts` — `captureWorkspaceDiff` (:67), `recordRunDiff` (:89), `sanitizeDiff` (:27), `MAX_GIT_DIFF_CHARS` (:17)        |
| One caller, inside the handler | `dispatch-handler.ts:30` imports it, `:89` `const capture = deps.captureDiff ?? recordRunDiff` — after the developer stage (:74) |
| Who constructs the handler     | `index.ts` (re-export only), `dispatch-handler.test.ts`, `dark-factory-pipeline-e2e.test.ts:287`                                 |
| Who does **not**               | **`scripts/dark-factory-runner.ts` — no reference at all**                                                                       |

Live reproduction (independent of the issue): run on `WebFeedPOC#271` finished `succeeded`, opened PR #272 carrying a
one-line change to `src/App.jsx`, and its `df_run_summaries` row has `length(git_diff) = 0`. **Expected value `+1` on
`src/App.jsx`** — a known-good answer to assert against, which the issue itself did not have.

Note: an earlier recon grep reported "no callers" for `recordRunDiff` because of a malformed `--include` search that
returned nothing on a `.` path. That was a false negative, not evidence. Recorded here because the same mistake is
easy to make when hunting for a missing call site: **a search that returns nothing is not a search that ran.**

## Where the capture belongs

`scripts/dark-factory-runner.ts:1555-1572`, inside the coding phase, guarded by
`sandboxProvider.runGit && loopOutcome.status === "success"` and commented *"AFTER the loop, and BEFORE
runCodingPhase disposes the sandbox"*. Everything needed is already in scope there:

| Needed           | In scope as                                                                                     |
|:-----------------|:------------------------------------------------------------------------------------------------|
| a git runner     | `sandboxProvider.runGit` (already used for the commit/push)                                     |
| the workspace    | `sandboxWorkspace` (same call)                                                                  |
| the run identity | `runId`                                                                                         |
| the store        | `runHistory` (passed to `finalizeCodingPhaseFailure` as `{ labelWriter, runHistory, breaker }`) |

So the fix is a **sibling of `commitAndPushFromSandbox` in the same block**: capture the workspace diff and persist it
to the run's summary. No new seam, no new dependency, no change to the capture module.

## Tasks

### Task 1 (RED) — the runner records the diff it produced

A test at the runner's existing seam level (the pattern `runner-plan-invalid-park.test.ts` uses) asserting that a
successful coding phase whose sandbox reports a diff persists it: the store's summary for `runId` carries a `gitDiff`
containing the change.

**Controls, both required:**

- a run whose workspace has **no changes** records **no** diff — `null`, not `""` (the module already returns null;
  the test pins that the runner does not turn it into an empty string);
- a run whose capture **fails** does **not** fail the run (see failure semantics below).

### Task 2 (GREEN) — wire it, bounded

Call the capture in the window above, with the default base ref, and persist through `recordRunDiff`. The module
already sanitises and bounds the diff (`sanitizeDiff`, `MAX_GIT_DIFF_CHARS`), so no size handling is added here.

### Task 3 — the live acceptance the issue's own evidence implies

A real run whose ledger row's `git_diff` is non-null and matches the change it made. My reproduction gives the exact
expected value: a one-line change to `src/App.jsx` must read as `+1`, not NULL, not empty.

## Failure semantics (the honesty requirement)

The capture is **telemetry, not a gate**: a failure to capture must never turn a green run red. But it must not be
**silently** absent either — today `NULL` means "no diff", "capture failed" and "never attempted"
indistinguishably, which is the same fail-open shape as #772 (the ledger cannot show that plan validation ran).

Bounded here: report a capture failure through the run's existing reporting channel rather than swallowing it, and do
**not** widen the schema in this issue. If no channel can carry it without a schema change, record that as the
issue's known limit and cross-reference #772 instead of inventing a sentinel value in `git_diff`.

## To confirm during implementation, not assume

1. That `runHistory` satisfies `recordRunDiff`'s first parameter type (`RunHistoryStore`). `tsc` is the arbiter, as it

2. The base ref `captureWorkspaceDiff` defaults to, and whether the default yields the run's own change or needs an
   explicit base. The acceptance value (`+1` on the changed file) is what decides it.
