# #395 — Re-record the coverage baseline from the gate's own platform

## Goal

Move the committed coverage floor to the value CI itself measures, so the ratchet stops reporting an improvement
that never happened, and so one recorded floor is correct for both platforms.

## Precondition (met)

- #394 (merged `e752844`) made the skeleton-map path guard's rejection reason platform-independent.
- #396 (merged `88ab34e`) exercised the target-is-a-symlink escape guard on Windows for the first time.
- Measured on the merged tree: `developer-agent.ts` reports **200** covered lines on Linux **and** Windows, and the
  repo totals are **6811/8109** on both.

That was the stated blocker on this issue. It is cleared, so a single floor can now be correct.

## The numbers, and what actually moved the floor

| metric     | CI (linux) measured | committed floor   | delta   |
|------------|---------------------|-------------------|---------|
| lines      | 83.99 (6811/8109)   | 83.89 (6803/8109) | +0.10pp |
| statements | 83.28 (7241/8694)   | 83.19             | +0.09pp |
| functions  | 85.85 (1402/1633)   | 85.85             | +0.00pp |
| branches   | 76.85 (5798/7544)   | 76.74             | +0.11pp |

The floor rises by **8 lines**, and the interesting part is where they came from:

- **+7 lines: the platform difference.** The committed floor was measured on Windows. CI measured **6810** for that
  same commit, so the floor had been sitting 7 lines below what the gate's own platform achieves.
- **+1 line: the new cases from #394/#396.** On Linux the target-is-symlink block was *already* covered — that
  asymmetry is precisely what those changes removed — so CI's number barely moved while the Windows number moved
  by several lines.

## Why this is a re-record, not an improvement claim

The floor moves because the **baseline was recorded on the wrong platform**, not because coverage improved. The
commit message has to say which, because the diff alone tells the wrong story: a reader seeing the floor rise with
no test change would reasonably ask how that happened, and might conclude the bar had been moved to make a build
pass. This repository has been burned by exactly that reading before, so it is stated in the first line.

## Intended change

One file: `coverage-baseline.json`, regenerated by `npm run coverage:ratchet -- --update` from a run that matches
CI's conditions. No source, test, or config change.

## Tasks

### Task 1 — reproduce CI's measurement locally, under CI's conditions

- Set the five `DF_*_TEST_DATABASE_URL` variables, as CI does. Without them the gated integration suites SKIP and
  every metric reads roughly 5 points low, which would record a floor that is wrong again in the same way.
- Use a GREEN run: the gate refuses coverage from a failing run, and `--update` refuses too.
- **Match the artifact exactly, not approximately.** Exact agreement is the precondition this issue was waiting
  for; "close enough" would mean the floor is still recording a platform difference.

### Task 2 — record the new floor

- `npm run coverage:ratchet -- --update`, committing the baseline alone, with the message stating that the
  measurement conditions were corrected rather than that coverage improved.

### Task 3 — prove the gate still bites

- The gate passes the new floor: every metric at `+0.00pp`, and specifically **no** "Coverage improved" line.
- The gate still FAILS a real drop: raise the baseline by 2pp in a scratch copy, expect exit 1 naming the metric and
  both percentages, then restore.
- This is the step where a re-record could accidentally neuter the gate, so it is proven by running it, not assumed.

### Task 4 — ADR 0046 (proposed; say if you would rather skip it)

One short record: *a baseline re-record states whether the floor moved because coverage changed or because the
measurement changed.* The next person to read the diff will ask exactly that, and the answer is not in the diff.

- The 2pp-drop proof still exits 1.
- Full suite green; the root guards (`env-example-coverage`, `adr-integrity`, `doc-drift-guards`) pass.
- Local lint gate on every changed file before any push.
- **End-to-end:** this pull request's own CI run must report `+0.00pp` with no improvement line. That is the only
  proof the floor is right for the platform the gate actually runs on.

## Risks and open questions

1. **Zero headroom.** The floor sits exactly at what CI measures. The 0.05pp tolerance absorbs about four lines, so
   benign wobble still passes, but a genuine five-line drop now fails — which is the intent. Noted so a future
   failure is read as the gate working rather than as flakiness.
2. **A floor move can look like cheating.** Mitigated by the commit message and, if approved, ADR 0046 naming the
   cause. Nothing is hidden: the numbers and their provenance are in the pull request body.
3. **These figures will drift.** Any later change moves them, so Task 1 re-measures the tree as it stands rather
   than trusting the table above.
4. **Out-of-code-scope:** none. No repository setting, environment variable, or runner change is required.
