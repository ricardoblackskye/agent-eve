# Plan — Make the declared lint gate able to pass (#742)

**Issue:** [#742](https://github.com/ricardoblackskye/agent-eve/issues/742) · **Branch:** `plan/742-lint-gate`
**Status:** awaiting GATE 1 (plan approval) · **Board:** In progress

## Goal

**Repo-agnostic: any target repo, not this one.** The declared lint is a gate on every run, and a gate
that cannot *run* is worse than no gate — it rejects every run regardless of the code. The goal is a
property of the factory:

> The factory installs what the target declares, runs its gates from the checkout root, and when a gate
> cannot run at all it reports a **setup** finding — never a code failure.

`local-promotion-site` is the **first case that proves it**, not the subject of the work. Its three
faults are instances of that invariant being violated, and the repairs must hold for the next repo that
declares a lint.

## What is actually wrong — three faults, not one

| # | fault                                                                           | evidence                                                                                                                                              | owner                      |
|---|---------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------|
| 1 | the lint runs from a **subdirectory**                                           | `ESLint looked for configuration files in /workspace/__mocks__`                                                                                       | factory (this repo)        |
| 2 | the config imports **`typescript-eslint`**, which the manifest does not declare | `ERR_MODULE_NOT_FOUND` vs `package.json` declaring only `@typescript-eslint/eslint-plugin` + `parser`                                                 | target repo                |
| 3 | the config's **provenance** is unexplained                                      | the sandbox reports `/workspace/eslint.config.js`, but the host checkout `df-workspaces/local-promotion-site-15` contains **no eslint config at all** | **unknown — settle first** |

**Fault 3 gates the plan.** If the sandbox carries a config that is not in the checkout, then fixing the
manifest cannot help, and the repair is somewhere else entirely. Phase 0 settles it.

## Phase 0 — settle the provenance (no code)

Run the declared lint in the host workspace and inspect what is actually there:

- `npm run lint` in `df-workspaces/local-promotion-site-15` — does it fail identically on the laptop?
- where does `eslint.config.js` live in that checkout (tracked? generated? absent?)
- does `npm ci` produce `node_modules/typescript-eslint` from the declared manifest?

The answer decides whether faults 2 and 3 are one repair or two.

## Phase 1 — the cwd (factory side)

The declared lint must execute from the **checkout root**, not a subdirectory. `resolveLintCommands`
(`developer-agent.ts:797`) already decides *which* commands run; the defect is the working directory the
runner hands them.

- **RED:** a test that pins the lint's working directory to the checkout root, and one that fails if a
  nested directory is ever selected. Both must fail first.
- **GREEN:** the fix.
- **Wiring guard:** the runner must be shown to pass the checkout root — a unit test on a helper is not
  evidence the product calls it (learned the hard way in #739).

## Phase 2 — the dependency / config (owner per Phase 0)

**Generic rule first:** the sandbox must install exactly what the target's manifest declares
(`npm ci` honours the lockfile), and run the target's own gate. If the target's config imports something
its manifest does not declare, that is the **target's** inconsistency — the factory's job is to **name
it**, not to paper over it with a per-repo patch.

So the repair is one of: declare the missing package in the target, correct the config, or fix where the
config comes from. **Not guessed in advance**, and no repo-specific special case in the factory.

## Phase 3 — name it when it recurs

Once fixed, a gate that cannot run at all should report as a **harness** finding, not as a code failure.
That is [#743](https://github.com/ricardoblackskye/agent-eve/issues/743)'s taxonomy; this issue only
needs to feed it the classification, not build the mechanism.

## Acceptance

1. `npm run lint` passes on a clean checkout of `local-promotion-site` — **provable on the laptop**.
2. A Dark Factory run on that repo reaches **and passes** its lint gate, so the run is decided by its
   code rather than by its harness.
3. A deliberately broken lint still **fails** — the gate is fixed, not disarmed.
4. **The rule holds for a repo the work never touched:** a second target whose manifest and config fit
   gets a green gate, and one whose manifest does not fit gets a **named setup finding** rather than a
   permanent red. `local-promotion-site` proves the rule; it does not define it.
4. No new lint errors in agent-eve (standing rule).
