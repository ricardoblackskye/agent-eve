# 718 - Wire the Definition of Done's fix cycle

**Goal:** make a finding the Definition of Done raises actually drive re-coding, so a correctly
implemented change is not recorded as `failed` merely because the review loop has no way to
disposition its own finding.

**Architecture:** the seam already exists and its semantics are already pinned. This change
*implements* it: a small, port-injected module re-authors the affected files on the pull request's
branch inside a sandbox, pushes, and returns a `resolved` disposition. Verification is built in -
the DoD already re-runs `runChecks` every round, so a finding that is genuinely fixed stops
reappearing in the next round, and one that is not simply comes back.

**Tech stack:** TypeScript, Vitest, the Dark Factory's sandbox adapters (`commitAndPushFromSandbox`,
`gitPushWithVault`), the existing `DeveloperAgent`.

---

## Root cause - verified, not inferred

`DefinitionOfDoneDeps.attemptFixes` is declared at `agent/lib/dark-factory/definition-of-done.ts:334`:

```ts
attemptFixes?: (findings: ReviewFinding[]) => Promise<FindingDisposition[]>;
```

The DoD's **entire** fix/disposition path is gated behind it (`definition-of-done.ts:965`):

```ts
if (deps.attemptFixes) {
  dispositions = await deps.attemptFixes(unacceptedFindings);
  ...applyAcceptedDispositions(...)
}
// line 949: last round with unaccepted findings still present -> budget exhausted
```

The composition root builds the phase's deps (`DodPhaseDeps`,
`scripts/dark-factory-runner.ts:1859`) **without** `attemptFixes` - at both call sites: STEP 7
(`:1560`) and the verify-only re-entry introduced by #703 (`:640`). So on every production run the
guard is false, the block is skipped, and the loop re-reads the same finding until its round budget
is spent. `git grep attemptFixes` finds the interface, the call site, and nine test
cases - and no implementation anywhere.

This is the same defect shape as #702: an optional property on a deps interface that the
composition root never fills, so a capability the interface's own doc comment promises is silently
absent. It produces no warning, no error, and no failing test.

## Evidence - a live run

WebFeedPOC#246, run `a37cc0c6-3884-4d71-bec0-2a4332bbaa6b`, pull request #247:

| round       | finding_count | resolved_count | accepted_count | AC matrix |
|:------------|:--------------|:---------------|:---------------|:----------|
| 1           | 1             | 0              | 0              | 3/3 PASS  |
| 2           | 1             | 0              | 0              | 3/3 PASS  |
| 3 (blocked) | 1             | 0              | 0              | 3/3 PASS  |

The single finding was the `pr-reviewer` bot's "Architectural Anti-patterns" comment - advisory,
never dispositioned. Every acceptance criterion passed, and **PR #247 is green and
`mergeable_state: clean`**, yet the run is recorded `failed`. The loop could neither fix the
finding nor accept it, so it spun its three rounds and gave up.

## Intended fix

Supply `attemptFixes` from the composition root, implemented as a small module with injected ports
so it is testable without a sandbox, an LLM, or a network.

### What the module does

`createFixCycle(deps)` returns `(findings) => Promise<FindingDisposition[]>`:

1. **Attempt the fix.** Re-author the affected files, given the findings as instructions, on the
   pull request's **head branch**.
2. **Push.** Commit and push from the sandbox, using the existing vault-injected push seam.
3. **Return `{ findingId, status: "resolved" }`** for each finding the pass addressed. The DoD
   verifies it for free: the next round's `runChecks` re-reads the checks and the finding either
   stops appearing or comes back.
4. **Return nothing for a finding it could not attempt.** It stays outstanding, the round budget
   eventually exhausts, and the run blocks. A fix cycle that cannot fix something must not claim
   otherwise.
5. **Accept only with a reason.** The DoD already enforces the rules - an `error`-severity finding
   can never be accepted (`definition-of-done.ts:540`), an accepted finding requires a non-empty
   explanation (`:507`), and every acceptance is posted on the pull request as its own comment
   (`:565`). The module must not attempt a weaker path than the DoD already refuses.

### What it must NOT do

- **No second budget.** `attemptFixes` is called once per review round, so the existing
  `DF_MAX_REVIEW_ROUNDS` already bounds it. A new cap would be a second knob for one budget.
- **No new event vocabulary.** The fix's outcome already lands in the ledger through the round's
  own `review.round` counts (`resolved_count`), which are the columns the run page reads.

### Why a bad fix cannot reach main

The factory never merges; opening the pull request is its terminal action. A fix that breaks the
build turns the next round's checks red, which becomes a new finding and blocks the run. The worst
case is a red pull request and a `failed` run - the same place a real failure already goes.

## Risks and open questions

- **Should the fix cycle auto-accept anything in the first release?** It cannot accept an `error`
  finding (the DoD refuses), and any acceptance it does make is posted publicly with its reason.
  The alternative - fix only, never accept - is simpler and cannot rubber-stamp, but leaves an
  advisory finding to exhaust the budget. Recommendation: fix-first, accept only with a reason;
  make the accept path opt-out via config if that proves too eager.
- **Which agent re-authors?** Reusing `DeveloperAgent` with the findings as instructions is the
  smallest change; a dedicated fixer prompt is a follow-up if the developer prompt proves a poor
  fit for remediation.
- **A verify-only re-entry has no sandbox.** The `:640` path exists precisely to re-read the checks
  *instead of* re-coding ("reading them again rather than re-coding"), so it holds no coding
  workspace and its fix cycle must open one. That is the same requirement as the first pass, so it
  should fall out of the adapter; if not, it becomes its own follow-up rather than widening this
  change.
- **Cost.** One extra fix pass per review round, bounded by `DF_MAX_REVIEW_ROUNDS`.
- **#703 has landed.** PR #717 merged as `df90bf8`, so the DoD is now `runDefinitionOfDonePhase`
  over a `DodPhaseDeps` interface, and there are TWO compositions to extend: STEP 7 (`:1560`) and
  the verify-only re-entry (`:640`).
- **The record cannot name its finding.** #246's own DoD comment says "1 unresolved finding(s)"
  without saying which, which is why identifying it took three API calls. Worth its own issue; not
  part of this change.

## Settled decisions

Recorded after implementation, where the plan and the code diverged.

- **The verify-only re-entry carries NO fix cycle.** This plan said its fix cycle would open a fresh
  sandbox. It cannot: that path runs before the run resolves its workspace, remote and author, so its
  port bodies would read bindings before initialization - a `ReferenceError` at runtime, invisible to
  `tsc` and to any test. Giving it the shared adapter would mean moving that setup earlier or
  duplicating the adapter, and its job is to settle a verdict by re-reading checks rather than to
  start coding again. The wiring guard asserts the count, so a second site cannot appear unnoticed.
- **One adapter, one construction.** Both compositions share `buildFixCycleAdapter`; only STEP 7
  supplies it. Building it twice was the rejected alternative.
- **The findings reach the authoring path as a synthesized plan**, so a fix reuses `authorFiles` and
  inherits its `assessPreservation` guard instead of needing a second authoring seam.
- **The sandbox-wiring guard was tightened, not bumped.** ADR 0032's "exactly one create" becomes
  "every create is owned by something that disposes it" - a third, unowned site is what leaks.
- **ADR 0092 and ADR 0093 were written for this change**, and the module catalog entry added, because
  the doc-drift guard requires a new module to be referenced from a page.
