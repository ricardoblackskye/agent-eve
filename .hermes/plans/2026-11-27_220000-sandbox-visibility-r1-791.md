# Sandbox visibility R1: observe a running local sandbox, read-only

**Issue:** #791 (leg 1 of 4 under epic #790) · **Branch:** `feat/790-observe-local`, cut from current main
**Releases:** this is R1. R2 (#792 events), R3 (#793 provider seam), R4 (#794 remote, blocked on #668) follow separately.

## Why we are doing this

The Dark Factory runs agents in sandboxes and reports what happened afterwards. Nobody can watch it happen. When a run
goes wrong the only evidence is a log and a diff, and the second question anyone asks - *what was it actually doing?* - has
no answer until the run is over.

R1 gives an operator a read-only window into a running local sandbox: the workspace as the agent edits it. It reuses what
already exists - the same sandbox image, the same `DF_SANDBOX_ENDPOINT`, and the console the operator already has open -
and adds no ingress, no tunnel and no new provider. The view grants no ability to change anything the agent is doing.

It deliberately does not cover remote or cluster sandboxes (R4), recording, or any write access. What it changes is that a
local run becomes watchable while it runs; what it does not change is what the run does, how it is gated, or what it
records.

**The run detail page is the important one.** Locally it is `http://localhost:3000/dark-factory/runs/<runId>` - the same
machine as the sandbox - so a local view link belongs there, one click from the run it describes. That settles R1's
delivery mechanism, which an earlier draft of this plan left as a log line.

## The delivery mechanism

The page is a **client component polling an API**, so the link comes from the API rather than being assembled in the
browser. That also solves the deployed-versus-local problem structurally:

- **Locally**, the API process has a local sandbox, so it returns the view link and the page renders a watch entry.
- **Deployed**, that process has no local sandbox, so it returns nothing and no panel renders.

**The gate is server-side and structural, not a hostname check in the browser.** A deployed page cannot show a
misleading `127.0.0.1` link because the deployed server has nothing to point at.

## Acceptance criteria and how each is proven

R1's five criteria, each mapped to something that can fail:

- [ ] **AC1 - an operator observes the workspace changing during a run.**
      *Test:* with a local run in flight, the run detail page renders the watch entry, and the sandbox view served for it
      shows the workspace. Proven by fetching the view and finding a file the agent wrote during the run.
- [ ] **AC2 - the view grants no write access.**
      *Test:* an assertion that the exposed surface is read-only - a write attempt through the view's transport is
      refused, and the exposure path contains no write-capable handle. Also that the code view carries no shell.
      Note the console itself already has run controls (`ControlPanel`); this criterion is about the **sandbox view**,
      and the plan must not let the two be conflated.
- [ ] **AC3 - exposure defaults to localhost.**
      *Test:* with no configuration, the bind address is loopback. Assert on the resolved address, not on the config
      string, so a `0.0.0.0` default cannot slip through. This aligns with the endpoint's existing `127.0.0.1:18082`
      default rather than inventing a new convention.
- [ ] **AC4 - no credential value appears in the URL, output or ledger.**
      *Test:* a leak assertion with a canary credential - the value must not appear in the view URL, the run output, or
      the persisted run record. **A tokenized URL is explicitly forbidden**: no query-string auth, no bearer in the path.
      The security boundary is the loopback bind, which is what #790's own notes prescribe for this image
      (*"bind to localhost or enable `secureAccess: true` if exposing the ingress gateway"* - R1 binds, so no password).
- [ ] **AC5 - the view is released when the run ends or the observer disconnects.**
      *Test:* after the run completes, the view is gone; a stale request gets a clear "run ended" rather than a hang;
      and disconnecting the observer does not leave the exposure alive.

## Tasks, RED first

Every task commits its failing test before the code, per the house process.

1. **RED: the resolved bind address is loopback by default** (AC3). Pure function, no sandbox needed - the cheapest test
   in the plan and the one that guards the riskiest default.
2. **RED: a credential value cannot reach the view URL, output or ledger** (AC4). Canary-based, written before any
   exposure code exists, so the leak cannot be introduced while the feature is built.
3. **GREEN: expose a read-only view for a local sandbox**, reusing the existing image and `DF_SANDBOX_ENDPOINT`.
4. **GREEN: the run-detail API reports the view when - and only when - a local sandbox is live.** This is the server-side
   gate; test it both ways, including the deployed case where it must report nothing.
5. **GREEN: the run detail page renders the watch entry** when the API reports one, and renders nothing when it does not.
6. **RED/GREEN: the view is released on run end and on disconnect** (AC5).
7. **Read-only is enforced, not assumed** (AC2) - the assertion in AC2's test above.
8. **Docs**: `docs/pages/dark-factory-local-runs.md` gains the view, beside the endpoint it uses.

## What this does not change

- **The run itself.** No gate, no verdict, no target, no behaviour of the agent or the sandbox.
- **The console's existing controls.** `ControlPanel` keeps them; only the sandbox view is read-only.
- **Remote or cluster sandboxes** (R4), recording, and write access - all explicitly out of R1's scope.
- **The credential vault's contract.** No credential value moves into a URL, an output or the ledger.

## Risks

| risk                                                        | mitigation                                                                       |
|:------------------------------------------------------------|:---------------------------------------------------------------------------------|
| a tokenized URL becomes "the easy way" to secure the view   | AC4's test is written before the feature, and forbids query-string auth outright |
| a `0.0.0.0` bind slips in as a convenience                  | AC3 asserts the **resolved address**, not the config value                       |
| the deployed page shows a misleading `127.0.0.1` link       | the API decides server-side and reports nothing when it has no local sandbox     |
| the read-only view is conflated with the console's controls | AC2 names the sandbox view specifically, and the plan says so twice              |
| a stale link hangs instead of explaining                    | AC5 requires a clear "run ended" state                                           |
| the exposure outlives the run                               | AC5's release test covers both run end and observer disconnect                   |
