# #754 — a re-run must not refuse the Definition of Done because its pull request already exists

## Goal

A run that finds its pull request **already open** must continue, not refuse. Today a re-run of an issue
whose first run opened a PR calls the creator again, GitHub answers **422**, and the Definition of Done
turns that into `refused` — so a healthy re-run loses its verdict on a change whose unit tier passed.

## Root cause (verified, with the tier stated)

| Claim                                                                      | Tier                                                                                                                                                                                                                                                         |
|----------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| The 422 comes from the **pulls POST**, and the DoD turns it into `refused` | **verified** — `definition-of-done.ts:771` calls `deps.prWriter.createPullRequest`, `:780` returns `status: "refused"`; `pr-writer.ts:126-135` posts to `/repos/{owner}/{repo}/pulls`, `:143` is the only source of `GitHub responded <status>` on that path |
| A pull request already existed for that head                               | **observed** — run 1 opened PR #259 for `feat/dark-factory-258`; PR creation for an existing head is what GitHub answers 422 to                                                                                                                              |
| The 422 body said so                                                       | **inferred** — the response body is never surfaced, which is part of this defect                                                                                                                                                                             |

`AC Matrix Count 0` in the same verdict is consistent: the DoD stops before building the matrix.

**The factory already half-knows this shape.** The runner's DoD dependency carries a verify-only guard —
*"#703 (Leg C): a verify-only re-entry must not open a SECOND pull request"* — implemented as
`createPullRequest: async () => ({ ok: true, pr: existingPr })`. That covers a verify re-entry only; a
**fresh re-run** has no `existingPr`, so it calls the real creator and is refused.

## The decision this change makes (ADR)

**Creating a resource that already exists is a success that returns it, not a failure.** A conflict on
create is resolved to the existing resource and reported as one. This sets the factory's posture for
idempotent creation, so it is an ADR — **0097** — and it is deliberately written so that neither the
invariant nor the ADR names a vendor or a repository: GitHub is the first case that proves the rule.

## Tasks (TDD: RED then GREEN, separate commits)

| Task | RED asserts                                                                                                       | GREEN does                                                |
|------|-------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------|
| 1    | a 422 from the pulls POST **with** an open PR for that head resolves to that PR: `ok: true`, its number, no throw | `pr-writer.ts` resolves the conflict by looking the PR up |
| 2    | the **control**: a 422 with **no** matching PR still fails, and the failure carries the response body             | the same path, refusing rather than swallowing            |
| 3    | the DoD does not report `refused` when the PR already exists — asserted on the verdict, not on a helper           | the DoD continues through its normal path                 |
| 4    | the ADR is linked from the index and every changed module still appears in `docs/pages/`                          | the document and the index row                            |

Task 2 is the one that keeps this honest: an implementation that treats *any* 422 as "already exists"
would pass Task 1 and must fail Task 2.

- The lint gate over the **changed file set from the branch diff**, at the gate's own tool version

  hand-picked subset.
- **Live acceptance: re-run `ricardoblackskye/WebFeedPOC#258` again.** Its PR #259 already exists, so it
  is exactly the failing case — the run must complete without `refused`.

## Risks and open questions

| Risk                                                                       | Handling                                                                                                          |
|----------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| Treating *any* 422 as "already exists", hiding a genuinely invalid payload | the lookup must succeed before the create is forgiven, and the control task fails an implementation that skips it |
| A 422 from a different cause in the same POST                              | the response body is surfaced in the failure, so the next occurrence is diagnosable rather than a status code     |
| Two runs racing to open the same PR                                        | the conflict resolution is the same code path; a loser resolves to the winner's PR rather than failing            |

## Provider- and repo-agnostic checkpoint (before GATE 1)

Would this hold for a provider or a repository this work never touched? **Yes.** The invariant is
"a create that conflicts resolves to the existing resource", stated without a vendor, and the changed
module takes its API base and fetch implementation by injection. The named target is the first case.
