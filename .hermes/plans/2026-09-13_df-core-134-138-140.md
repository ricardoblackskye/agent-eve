# Dark Factory R1 — State · Dispatch · Observability (feat/df-core) Implementation Plan

> **For Hermes:** Use test-driven-development to implement this plan task-by-task.
> **Branch:** `feat/df-core` (off `origin/main` = `7a747c0`, after PR #145 merged the plan docs)
> **Stories (R1 work items):** #134 (Component A — Stateful Execution Memory) · #138 (Orchestration Core) · #140 (Observability)
> **Parent epics (IN SCOPE, all three):** #129 (Component A) · #137 (Orchestration Core) · #139 (Observability) → #128 → #127
> **Date:** 2026-09-13

**Goal:** Deliver the Dark Factory R1 foundation — a durable, deterministic execution-memory store (`#134`), an idempotent event-dispatch/self-correction core (`#138`), and a metrics-ingestion observability layer (`#140`) — as one reviewable release PR, strictly TDD, with the existing provider-seam pattern.

**Architecture (2-3 sentences):** Eve moves from stateless to **stateful**. R1 builds
the three foundation layers behind the same canonical-payload + adapter seam the repo
already uses (`agent/lib/backlog-provider.ts`): a `StateStore` seam for execution
memory, a `Dispatcher` seam for CI-event dispatch, and a `MetricsStore` seam for
observability. Each ships a real R1 adapter (node:sqlite for state; an in-memory/console
dispatcher with a deterministic retry policy; an in-memory metrics store) plus a
fail-closed default, and keeps Redis/pgvector, E2B/Modal, and QStash as pluggable
later adapters.

**Tech stack:** Node 22 (vitest/tsc work on it; Eve runtime needs 24 but CI is the eval gate), TypeScript, Vitest, built-in **`node:sqlite`** (`DatabaseSync`, present in Node 22.5+; typings shipped in @types/node). No new runtime dependency.

## Story #134 — Stateful Execution Memory (`agent/lib/dark-factory/state.ts`)

**Intent (from #134):** persist Eve's execution state between requests so a delivery loop remembers the current issue, assigned worker, last-test outcome, and loop step.

**ACs to satisfy (TDD anchor):**
- AC1: write a context → end request → new request retrieves the identical issue/worker/lastTest/step.
- AC2: update writes to the external store (Sqlite adapter).
- AC3: store unreachable → read/write returns an explicit error (not silent).
- Constraints: store externally; persist the 4 fields; pluggable backends; MAY cache in-memory.

### TDD tasks (#134)

**Task 134-1 — `ExecutionContext` canonical shape**
- Test target: `tests/dark-factory/state.test.ts`
- RED: assert `toExecutionContext({issue, worker, lastTest, step})` round-trips the four canonical fields and rejects/marks missing required fields.
- GREEN: minimal pure helper; type the canonical payload.

**Task 134-2 — `StateStore` seam + console default (fail-closed)**
- Test: RED asserts the console provider is the default, refuses writes with no configured store, and `mode` reports `dry-run`/`blocked` (mirror `PublishResult` semantics).
- GREEN: seam interface + `ConsoleStateProvider` that no-ops and reports `blocked` when unconfigured.

**Task 134-3 — `SqliteStateAdapter` (node:sqlite, file-backed)**
- Test: RED with a temp file DB — write → read returns identical state (AC1); overwrite persists (AC2); corrupt/unreachable path returns an `"state store unreachable"` error (AC3).
- GREEN: `DatabaseSync` open, `CREATE TABLE IF NOT EXISTS execution_state`, `upsert` on a key, `get` by key; open errors mapped to the explicit error shape.
- Real store semantics (no mocks): use `:memory:` / temp path in tests; verify NFR p95 <100ms on a modest loop.

**Task 134-4 — seam factory + env wiring (`index.ts`)**
- Test: RED — `createStateStore(env)` returns Sqlite adapter when `DF_STATE_DRIVER=sqlite`, console/blocked when unset; unknown driver errors.
- GREEN: switch on env with fail-closed default.

## Story #138 — Orchestration Core (`agent/lib/dark-factory/dispatch.ts`)

**Intent (from #137/#138):** ingest CI-failure events, interpret, route back to the correct worker, with idempotency, retries, and a managed dispatch lifecycle.

**ACs to satisfy (TDD anchor):**
- AC1: ingested event → interpreted + routed to the correct worker in the lifecycle.
- AC2: duplicate event re-delivered → deduplicated, not dispatched twice.
- AC3: dispatch attempt fails → retried per configured limit + backoff.
- AC4: retries exhausted → terminal failure status.
- Constraints: dedup (at-most-once); persist dispatch state (retries survive restart — pulls in #134 store); bounded retry with backoff; emit structured logs/metrics per attempt; configurable retry limit/dedup window.

### TDD tasks (#138)

**Task 138-1 — canonical CI-event payload + normalization**
- Test target: `tests/dark-factory/dispatch.test.ts`
- RED: `toDispatchEvent({runId, repo, ref, status})` produces a canonical event with a stable dedup key (`runId`); missing runId rejected.
- GREEN: pure normalizer + `dedupKey()`.

**Task 138-2 — idempotent executor (at-most-once)**
- RED: dispatching the same event record twice executes the worker handler exactly once (dedup via persisted seen-keys from the #134 store).
- GREEN: an `AlreadyProcessedError`/skip path keyed by dedupKey; depends on the StateStore seam (inject a store).

**Task 138-3 — bounded retry backoff**
- RED: a failing dispatch attempt returns a schedule with attempt number + backoff delay; after `maxRetries` the event transitions to a terminal `failed` status instead of infinite retry.
- GREEN: pure `RetryPolicy` (maxRetries, baseDelayMs, backoff multiplier) + a small executor loop.

**Task 138-4 — dispatch lifecycle + routing**
- RED: a CI-failure event for repo/ref resolves to a worker target (`developer`) and progress through `pending → dispatched → retrying|succeeded|failed(terminal)` is observable via a status record.
- GREEN: lifecycle state machine persisted through the StateStore seam; structured `dispatch.attempt` metric emitted (feeds #140).

## Story #140 — Observability (`agent/lib/dark-factory/metrics.ts`)

**Intent (from #139/#140):** capture metrics driving recursive self-improvement — iteration counts, test-fail→fix cycles, success rate per task type — from every component.

**ACs to satisfy (TDD anchor):**
- AC1: task completes → metric record persisted (iteration count, fix-cycle count, task type, success/failure).
- AC2: reported fix-cycle count equals the exact observed failed-then-fixed cycles.
- AC3: success rate per task type = K/N rounded to 2dp.
- AC4: any registered component can emit without changing the ingestion interface.
- Constraints: capture the 4 fields for every task; stable ingestion interface; MUST NOT lose records; queryable per-task-type aggregate.

### TDD tasks (#140)

**Task 140-1 — `TaskMetric` canonical record + ingestion interface**
- Test target: `tests/dark-factory/metrics.test.ts`
- RED: `record(taskType, {iterations, fixCycles, status})` accepts and returns a persisted record; missing required fields rejected.
- GREEN: canonical record + `record()` on a seam interface.

**Task 140-2 — `MetricsStore` seam + in-memory adapter**
- RED: record N tasks → `successRateByType(type)` returns K/N to 2dp (AC3); records survive store instance within a session (AC1).
- GREEN: in-memory `Map`-backed adapter implementing the seam; `round2` helper.

**Task 140-3 — fix-cycle accounting (exactness)**
- RED: a task run through a helper that appends fail→fix events reports the exact cycle count (AC2), not a heuristic.
- GREEN: `countFixCycles(events)` walks the true failed-then-fixed transitions.

**Task 140-4 — adapter factory + no-loss guarantee + wiring**
- RED: `createMetricsStore(env)` fail-closed default; a "flush-on-error" guard so a completed task's record is not silently dropped (AC "MUST NOT lose records").
- GREEN: factory + buffered write that surfaces persistence errors instead of swallowing them; wire `dispatch.ts` attempt metrics into it.

## Risks / open questions

1. **`node:sqlite` is experimental in Node 22** (emits an ExperimentalWarning). It
   satisfies #134's "external store" AC with no dependency and no credentials. If the
   warning or instability proves problematic in CI/deploy, the seam lets us swap to
   better-sqlite3 or Redis with no API change — but flag if you'd rather avoid the
   experiment. I believe `@types/node` is recent enough to type `DatabaseSync`
   (confirmed `sqlite.d.ts` present).
2. **No QStash/real queue in R1** — dispatch is in-process + deterministic. The seam isolates this so QStash becomes a later adapter without touching the lifecycle logic.
3. **Vercel ephemeral filesystem** — a file-backed Sqlite DB does NOT persist across cold starts / instances in serverless. R1 uses it to prove real external-state semantics locally and in CI; production persistence requires Redis/pgvector (R2+). This is documented, not silently assumed.
4. **Env var naming** — `DF_*` prefix proposed; confirm it doesn't collide with Eve/Vercel conventions before the docs commit.
5. **Eve runtime Node 24** — local `npm run dev`/`eve` won't run on Node 22; CI is the eval gate. TDD/build/tsc are fine locally.

Operator decisions already taken: state store = node:sqlite (R1); branch = `feat/df-core` single PR for the trio.
