# #503 — STEP 5 crash: `Cannot read properties of undefined (reading 'replace')`

Branch: `fix/step5-replace-503` (off `origin/main` @ `0065a2b`, the #504 merge)
Issue: https://github.com/ricardoblackskye/agent-eve/issues/503
Parent: #501 (STEP 3.5 crash) — this is its STEP 5 sibling.

## Root cause (correcting the issue's candidate table)

The issue's candidate table ruled out every `.replace` reachable from the dispatch path **except**
`scripts/dark-factory-runner.ts` itself, which has none — and concluded the failing call was "in the
dispatch region". That conclusion is wrong, and the gap is methodological: the repo-wide grep that
fed the table **filtered out regex-literal `.replace` calls**, so `agent/lib/dark-factory/plan-file.ts`
was never examined. It is the crash site.

`renderPlanFile` (called at `scripts/dark-factory-runner.ts:837`, *inside* the `postPlanComment`
argument, i.e. before the `[PLAN] Posted…` log at 847) renders the "Files to change" table with:

```ts
`| \`${cell(file.path)}\` | ${cell(file.action)} | ${cell(file.rationale)} |`
```

`cell(text: string)` and `headingText(text: string)` both start with `text.replace(...)`. The architect's
**returned** plan (the one that actually runs — its 3rd self-correction attempt) used a *different
vocabulary* for `targetFiles`:

```json
{ "path": "src/pages/HomePage.jsx", "changeType": "modify", "reason": "…" }
```

`action` and `rationale` are therefore `undefined`, so `cell(undefined)` →
`undefined.replace(...)` → exactly *"Cannot read properties of undefined (reading 'replace')"*. It dies
before the `[PLAN] Posted…` line, which is why the trace shows the failure immediately after the STEP 5
print and the ledger shows `df_plans=0`.

The plan validator passed this shape at STEP 4 ("Domain Validation Passed") — it does not pin the
`targetFiles` field vocabulary, so the malformed plan reached the renderer. **That validator gap is a
separate concern (see Follow-ups); this PR fixes the crash, not the schema enforcement.**

## Fix design (same principle as #501: display must never assert on plan shape)

Make the two renderer helpers **total functions**: they accept `unknown` and coerce a missing / non-string
value to a visible `—` marker instead of throwing. No other call site changes — the named failing calls
are `cell` and `headingText`, and the commit message names them precisely (AC2). This is *not* a blanket
defensive change: it is the exact pair of functions that throw, made to tolerate the optional fields the
validated plan is allowed to omit.

### Task 3 — release the claim on any post-acceptance abort (AC5)
- Cause: `main()` has no outer try; the entry-point catch (1538–1551) only closes the control store, so a
  throw after `beginRunRecord` (the STEP 5 crash included) strands the claim — which is why two runs in a
  row needed manual retirement.
- **GREEN** (no new failure mode to RED — the existing entry catch already swallows): record the active
  run identity (`repo`/`issue`/`runId` + `labelWriter`/`runHistory`) in a module-scoped `activeRun` set
  right after `beginRunRecord`, cleared on the success path; in the entry-point catch, if `activeRun` is
  set and the run is not already terminal, call `applyTerminalLifecycle({ terminalStatus: "failed" })`.
  `applyTerminalLifecycle` is idempotent (returns `{applied:false, skipped:true}` once finalised), so it
  is safe alongside the existing phase-level catches.
- Test: a small harness asserting the claim/terminal event is written when `main`'s body throws after
  `beginRunRecord` (drive via the extracted seam, or a unit test on the new release helper).
