# Plan: TanStack Query and Table for the Dark Factory run list (#748)

Date: 2026-11-23

Base: `origin/main` at `34d891f`

## Goal

The Execution Ledger's run list becomes a real admin data table: one date/time field per
row, server-side paging (20 by default, a choice of 20/50/100, next and back), most recent
first - built on TanStack Query and TanStack Table, because the dark factory pages are
becoming an Admin surface and this is the first of several admin tables.

The invariant is the **surface**, not this table: an admin list pages, sorts and filters on
the server, and its state lives in the URL. A second admin table (repos, costs, policies)
must reuse the same seam without changing this one.

## Why TanStack, and why now

The dark factory pages are going to be Admin. That is the condition that decides this now
rather than later: the run list is the first of several admin tables, so the convention is
set here instead of being retrofitted. The repo currently has no data-fetching or table
library at all - `use-run-query.ts` and `view-model.ts` are hand-rolled - so this is a new
convention, not an increment.

The reason to adopt Query is not convenience. The criterion "polling must not reset the
page" is currently a bookkeeping problem: the page and the poll are both component state.
With the page and size in the **query key**, a poll fetches the current page by
construction. Table is headless, so it brings the model (column definitions, row ids,
manual pagination) and no vendor into the data layer.

## Provider- and repo-agnostic checkpoint (asked before GATE 1)

Would this hold for a repo or vendor the work never touched? The paging contract is stated
over the store interface - a page, a total, an order - and names no provider. Postgres and
SQLite are two cases that prove the seam rather than define it. The acceptance for Task 4 is
written against the store, so a second provider would be a test rather than a rewrite. **That test is deliberately not in this change: one provider is enough for now, and the existing driver staying green is a regression guard rather than a new provider commitment.**

## Revision: extending the change so the other pages keep working

Agreed after Task 2, when the consumers of the hook turned out to be four and the plan had named
one. The paged hook must not break the pages that already call `useRunQuery`.

### The seam

`useRunQuery(path, options)` stays as the general form, for the pages that show one thing and do
not page. A second hook, `useRunListQuery({ filters, paging }, options)`, is the paged one: it
builds the request with `buildPageRequest` and the key with `runQueryKey` from the SAME input, so
the URL and the cache key cannot drift apart. Both delegate to one Query core in the same module,
so one place decides caching, retries and error mapping.

This breaks less than routing all four callers through the paged form, and it is more honest: the
overview, the repo page and the run detail page are not paged, so handing them a page and a size
invents state they do not have.

### Tasks added

|------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------|

## Revision 2: paging is a cursor, and the client follows it

Found while grounding Task 4: the server does not page by offset. It returns a page plus an opaque
`nextCursor`, and always has.

| Evidence                                |                                                                                           |
|-----------------------------------------|-------------------------------------------------------------------------------------------|
| `agent/lib/dark-factory/run-query.ts`   | `encodeListCursor`, `decodeListCursor`, `MAX_PAGE_SIZE = 100`, `RunListRequest { limit }` |
| `app/api/dark-factory/runs/route.ts`    | answers `{ runs, nextCursor }`                                                            |
| `docs/dark-factory-run-query-api.md`    | the endpoint's own page                                                                   |
| `docs/pages/dark-factory-operations.md` | an opaque cursor; a tampered one is a 400, not a silently wrong page                      |
| `docs/pages/dark-factory-modules.md`    | the codec's shape is `createdAt` and `runId`, or `sequence`                               |

That last row matters twice: the store's cursor already carries **createdAt and runId**, which is the
stable order and the tie-break this plan was going to add. **Nothing needs adding to the server.**

### Task 4, corrected

|       | Was                                                                                        | Now                                                                                                                                                                   |
|-------|--------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| RED   | the store returns a page with a total, ordered by `updatedAt` with the id as the tie-break | a following page is fetched with the `nextCursor` the first one returned; the last page returns none; a cursor the store did not issue is refused rather than trusted |
| GREEN | offset, total, order and tie-break                                                         | nothing on the server: the store and the API already do this. The task becomes a client change plus a test holding the cursor round trip                              |

### Task 1, revisited

Two of its helpers were built against a server that does not exist, so they change.

| Helper              | Was                   | Now                                                                                                                                        |
|---------------------|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------|
| `buildPageRequest`  | `limit` and `offset`  | `limit`, and `cursor` when there is one                                                                                                    |
| `pageBounds`        | arrows from a `total` | `canGoForward` is that a next cursor exists; `canGoBack` is that the stack has a previous entry                                            |
| `pageCount`         | pages from a total    | dropped: the API reports no total, and the UI never showed a page count                                                                    |
| `DEFAULT_PAGE_SIZE` | 20                    | unchanged: 20 is the list's own default and the client always sends it. The 25 in `run-query.ts` applies only when a caller sends no limit |

The page holds a **stack of cursors**: Next pushes what the server returned, Previous pops it. That is
what makes back and forward honest without a total.

### Before any of that: one live risk

The page currently requests `limit=20&offset=0`. `validateRunListParams` is not yet confirmed to
ignore an unknown parameter. If it rejects one, the live list is a 400 today, and the suite would not
show it because the runs-page tests stub `fetch`. **Confirm this first**, then the cursor work follows.

### What does not change

The Factory's own documentation is already correct and needs no edit: the endpoint page documents the
cursor, the operations page states the tamper-is-a-400 rule, and the modules page records the codec's
shape. This revision corrects the plan, not the docs.

### The checkpoint, restated

Would this hold for a repo or vendor the work never touched? The client is handed an **opaque** cursor
and never inspects it, so the storage-specific shape stays behind the seam. That is the weaker claim
than a page plus a total, and it is the true one. No vendor appears in the client.

## Revision 3: story 3 is already satisfied, and the order by recently-changed is its own issue

Grounding story 3 found that the store's default order is already most-recent-first.

| Evidence                                      |                                                                                                        |
|-----------------------------------------------|--------------------------------------------------------------------------------------------------------|
| `agent/lib/dark-factory/run-history-store.ts` | `RUN_SORT_FIELDS = ["createdAt", "status", "repo"]`, and the ordering column "defaults to `createdAt`" |
| the same file's list query                    | `ORDER BY repo, issue, created_at DESC, run_id DESC` - a stable order with the id as the tie-break     |

So the list already defaults to the most recent at the top, and story 3 closes as **already
satisfied** rather than as something this change built. The client sends no `sort` and no `direction`,
so it inherits that default, and the criterion that the client must not re-sort holds.

### The one part that is not satisfied

`updatedAt` is **not a sortable field**, so "a run that just finished rises to the top" cannot be
requested. That is a server change - a sort field, its ordering and its cursor - and it answers a
different question from most recently created. It moves to its own issue: **#750**.

The settled decision that named `updatedAt` is corrected here rather than widened into the store.

### Settled decisions, corrected

| # | Decision | Now                                                                                                                                                              |
|---|----------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 5 | Order    | the store's default: `createdAt` descending, with the id as the tie-break. The client requests no order, and story 3 is satisfied by what the store already does |

### What this leaves for the change

Paging stays the only ordering work here, and it is a cursor round trip rather than an offset. The
prerequisites are now closed with evidence: an unknown parameter is ignored rather than refused, the
repeated `status` parameter is mapped onto `statuses` by the route, and the order needs nothing.

## Revision 4: what the admin gate actually is

Task 6 was planned as "a non-admin viewer is refused, and the UI offers no link that ends in a 403".
Grounding it found that the second half is far larger than that phrasing suggests.

| Found                                | Evidence                                                                                                                                                                                                                    |

| The API half exists and is strong    | `resolveViewer` returns an email, a role and an optional tenant, or 401/403; it reads the membership store on every request and refuses when there is no session, no membership, an unreadable store or a suspended account |
| No dark factory page checks anything | a search of `app/dark-factory/` for the resolver, the auth gate or a redirect returns nothing                                                                                                                               |

So the pages are **not merely offering dead links**: they render for any viewer, and only the API

changed is the size of the work and where it lands.

### Where the check goes, stated

`app/dark-factory/layout.tsx`, because it is a server component and every page beneath it inherits the

the API's fail-closed posture instead of adding a second, weaker check.

`app/auth-gate.ts` already owns `isProtectedPath`, `isApiPath` and `safeNextPath` - the last guarding an
open redirect - so the gate extends that concept rather than inventing a parallel one.

## Revision 5: "admin" means the operator role, and the membership already exists

The acceptance criterion says the pages are reachable only by an admin viewer. The model has no such
role, so the word needs settling before the gate is written.

| Evidence                               |                                                                                                                             |
|----------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| `agent/lib/dark-factory/membership.ts` | the roles are `operator` and `customer`; an operator is unscoped and sees every tenant, a customer is scoped to exactly one |
| `resolveViewer`                        | refuses when there is no session, no membership, an unreadable store or a suspended account                                 |

So **admin means an active operator**. Signing in grants nothing: entitlement is the membership row, and
the same sign-in with a suspended row is refused by the API today.

### The prerequisite, verified rather than assumed

The gate admits only what the API admits, so an absent membership would lock the operator out of the very
pages the gate protects. Checked before writing any gate code, with the operator's own address for the
target of that command:

```text
npm run df:membership -- list    ->  role=operator status=active
```

Nothing needed granting. The command must run where the membership driver is configured; it refuses
elsewhere rather than appearing to succeed, which is the behaviour to want.

### Task 6, in one line

The layout refuses anything that is not an active operator and admits an active operator, using the same
resolver the API uses, so the two cannot disagree about who is entitled.
