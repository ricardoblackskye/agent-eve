## The requirement, in the issue's own words

The approved plan's `targetFiles` is a **contract**. The set of files the run actually writes must be a **subset** of
it. On a violation the run **refuses, or re-parks**, naming the extra path(s).

The evidence is a live escape: **a fix cycle wrote a file outside its plan's approved target set** (a CI workflow), and
nothing objected. The issue notes that the fix cycle is the path that escaped in practice.

**Direction of safety:** prefer refusing to routing around an obstacle. So an out-of-set write must never quietly widen
the set, and where the plan cannot write what it must, refusal with the reason beats substitution.

**Where to enforce, and why there.** At the **authoring** point (`:1403`), not at commit time: the requirement is
about what the run *writes*, and a file written but never committed would slip past a commit-time check. Enforcing at
the commit helper would also be narrower than the requirement.

## Design

1. **A pure helper**, not a runner edit: given the authored paths and the approved plan, return the paths that are
   outside the approved set. Testable with no runner, no sandbox and no network - the same seam shape that worked for
   #770 and #764.
2. **Enforcement at the authoring point**, naming every extra path. The refusal mode follows the issue: refuse, or
   re-park, with the paths named on the ticket.
3. **One choke point, both commit paths.** The helper is consulted where the run learns what it wrote, so the sandbox
   and host commit paths cannot diverge in whether the contract is checked.

**Provider- and repo-agnostic by construction:** the rule speaks about *whether a path is in the approved set*. It
names no vendor, no repository, no framework and no surface kind. That is an acceptance criterion of the issue, and it
is why the helper takes paths and a plan rather than anything repository-shaped.

## Tasks

### Task 1 (RED) - an out-of-set write is refused, with the path named

An authored file outside the approved set is a violation and the refusal names it.

### Task 2 (control) - an in-set write proceeds

Without this, "refuse everything" would satisfy Task 1.

### Task 3 (the join) - the check is actually wired

The issue asks for this explicitly: *"Assert the join - that the executed path really is checked against the approved
plan."* A bounded wiring assertion, **paired with `tsc` and the suite** rather than standing alone: #704 showed a
wiring guard reporting a call present and correctly ordered while the file did not compile, so a source-text guard is
only defensible alongside the compiler and the tests.

### Task 4 - the refusal mode, stated rather than implied

A violation either refuses or re-parks, and it says which and why. What it must never do is widen the approved set to
accommodate the write - that would make the approval meaningless in exactly the case it exists for.
