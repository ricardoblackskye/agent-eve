# #426 — the AMM scanner: produce real measurements instead of fixtures

**Release split (agreed):** **R1 + R2 in ONE PR** on this branch. **R3 (sandbox execution) stays out** — local-sandbox-only when we do it. Scope of this PR: AC1, AC2, AC4, AC6. AC3/AC5 are R3.

## What this PR delivers

Today every AMM figure in the product comes from a fixture: `fixtureAmmProvider()` in `amm-readiness.ts:295`. #382 built the model (catalogue + pure scorer) and #424 built the storage; both deliberately stopped at the edge of I/O. This PR produces the measurements.

- **R1** — every one of the 39 catalogue rows carries a *machine-checkable* expectation, so the runner never interprets prose (AC1).
- **R2** — `runAmmScan({ repo, workspace })` evaluates those expectations and returns an `AmmScan` via `scoreRepo()`, stamped with the catalogue version (AC2, AC4, AC6), invoked by `npm run df:amm-scan`.

## Reconnaissance findings (evidence, not assumption)

### The seam already exists — this PR does not need to build one

`agent/lib/dark-factory/sandbox.ts` (#280) already exports:

```ts
export interface SandboxProvider {
  readonly driver: "local" | "dry-run" | "opensandbox" | "refusing";
  readonly isolated: boolean;
  create(workspaceDir: string): WorkspaceTools;   // readFile, writeFile, listFiles, runTests
  runGit?(args: string[]): Promise<GitRunResult>;
  dispose?(): Promise<void>;
}
export function createRefusingSandboxProvider(reason: string): SandboxProvider
export class SandboxRefusedError extends Error
```

`createRefusingSandboxProvider` is **already AC5's "refuse rather than fall back to host"**, built and tested. R2 routes command checks through `create()`, so a scan with no sandbox yields `unmeasured` — not a host execution and not a false `absent`. That is AC5's behaviour working *for* us in R2 rather than being deferred.

### The catalogue is 39 rows: 34 `file`, 5 `command`

```
command  1 linter             npm run lint              "the linter runs and reports no errors"
command  2 type-checker       npx tsc --noEmit          "the type checker exits zero"
command  6 fast-validation    npm run validate          "the full validation finishes in under 30 seconds"
command  9 fresh-checkout     npm ci                    "a clean install and build succeed from scratch"
command 15 fast-suite         npm run test:unit         "the unit suite finishes in under two minutes"
```

The other 34 are `{ kind: "file", path }`. So **R2 measures 34 of 39 signals for real** with no sandbox; the 5 command signals are `unmeasured`, which is honest and is what R3 fills in. The scanner is genuinely useful in this PR.

### THE HARD PART — several prose expectations cannot be mechanized as "file exists"

This is the crux of R1 and I am not going to quietly narrow it. `expected` is prose today, and some rows assert **more** than a file-existence check can ever prove. A vocabulary of just `exists` would make those rows *claim more than they check*, which is the same class of dishonesty as a silent no-op sandbox.

Two distinct problems:

**(a) The expectation needs a duration, not only an exit code.** `fast-validation` says "finishes in under 30 seconds" and `fast-suite` "under two minutes". An `{ kind: "exitCode", code: 0 }` expectation silently drops the time bound and would report the signal present on a 10-minute run. The vocabulary must carry the bound or the row's claim must change.

**(b) Six rows assert a property a path cannot show.** These cannot be mechanized by `exists` without narrowing what the row claims:

| row | prose today | what a path check can actually show |
|---|---|---|
| `spell-check` | "the spell-checker config exists **and CI runs it**" | config exists (the CI half is a second target) |
| `containerized-build` | "the build is **reproducible** in a container" | a Dockerfile exists |
| `hermetic-local` | "tests run **without external services**" | `vitest.config.ts` exists |
| `doc-drift` | "docs are **compared against code in CI**" | `tests/` exists |
| `render-time-docs` | "reference pages **derive from source** rather than being copied" | `app/documentation/` exists |
| `documented-build` | "a build script exists **and is documented**" | `package.json` contains a build script |

**My recommendation (decision needed):** define the vocabulary so it is *honest* — `exists`, `contains`, `exitCode` (with optional `withinMs`) — and for the six rows above **narrow the row's `expected` prose to exactly what the check shows**, with the narrowing visible in the diff and listed in the PR body. The alternative is a much larger vocabulary (`jsonKey`, `noNetwork`, `contentHash`) whose evaluators are R2 work and whose correctness is harder to argue. I do not think inventing `noNetwork` and then implementing "did the tests really not reach the network" inside a scanner is a good trade in this PR.

If you would rather keep the prose intact and add vocabulary later, say so — but then those six rows are claims the runner cannot verify, and the runner should mark them `unmeasured` rather than pretend.

```ts
export type AmmExpectation =
  | { kind: "exists" }
  | { kind: "contains"; text: string }
  | { kind: "exitCode"; code: number; withinMs?: number };
```

Tasks:
1. Replace `expected: string` with `expectation: AmmExpectation` on `AmmSignalDefinition`, and migrate all 39 rows.
2. Fix the three wrong paths listed above.
3. Extend the existing "names an automated check and its whitepaper source for EVERY signal" test in `amm-scoring.test.ts:42` to assert every row's `expectation` is well-formed, and that its kind is **compatible with the row's `check.kind`** (`file` → `exists`/`contains`, `command` → `exitCode`). This is the test AC1 asks for.

**Deliberately NOT in R1:** the evaluators. R1 is the format and the migration; R2 is the code that reads it.

## R2 — the runner (AC2, AC4, AC6)

**Files:** new `agent/lib/dark-factory/amm-scan-runner.ts`, new `scripts/amm-scan.ts`, `package.json`, new tests.

```ts
export interface RunAmmScanInput {
  repo: string;
  workspace: string;              // a checkout to measure
  provider?: SandboxProvider;     // defaults to createRefusingSandboxProvider(...)
  now?: () => string;
}
export async function runAmmScan(input: RunAmmScanInput): Promise<AmmScan>;
```

Behaviour, one evaluator per expectation kind:

| check kind | evaluator | yields |
|---|---|---|
| `file` + `exists` | `listFiles`/`readFile` through the provider | `present` / `absent` |
| `file` + `contains` | `readFile`, substring search | `present` / `absent` |
| `command` + `exitCode` | `runTests(command)` through the provider, timed | `present` / `absent` / **`unmeasured`** |

The three-state rule (AC2) is the point of the whole issue, so the tests must pin each path:

- **`unmeasured`, never `absent`**, when: the sandbox refuses (`SandboxRefusedError`), the command cannot be run, or a duration bound is exceeded. A tool that is not installed must not read as "the repo lacks this practice".
- **`absent`** only when the check genuinely ran and found nothing.
- **Workspace unreadable** → every check `unmeasured`, never a page of `absent`.

Then: hand the measurements to `scoreRepo()` and stamp `catalogueVersion()` (AC6 — the function already exists at `amm-signals.ts:552`, a digest over `(id, level)` pairs).

CLI: `scripts/amm-scan.ts` + `npm run df:amm-scan -- --repo <name> --workspace <dir>`, printing the scan as JSON. Same `tsx` convention as the existing `df:local-run`.

Tests: a fixture checkout that satisfies some signals and not others → assert the exact triad per signal; a repo with nothing → all `absent`/`unmeasured`; a refusing provider → command signals `unmeasured`; and **a test asserting no command ever executes on the host**, which is AC3's guarantee provable without a sandbox.

## Out of scope — R3

Sandbox execution of the 5 command checks, read-only mounts, per-check timeouts and network isolation (AC3/AC5 proper), plus #344's remote proof. When R3 is done it supplies a real provider to `runAmmScan`; the seam and the refusing default already exist, so R2 needs no change to accept it.

## Risks

- **The six narrowed rows** are the honest cost of this PR. If we widen the vocabulary later, those rows can be strengthened — but until then they claim only what they check.
- **A scan of this repository will report 11 absents.** After the three path fixes, 8 are genuine. If the number looks alarming on the repo list, that is the scanner working, not failing.
- **`unmeasured` is load-bearing.** The single most dangerous failure mode is a command check reporting `absent` because the sandbox was down — the exact false negative AC2 exists to prevent. The tests target it directly.
