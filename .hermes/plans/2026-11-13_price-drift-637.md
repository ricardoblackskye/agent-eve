**Parent:** #637 — *"Main is red after merge 540e37a: Architect timeout flake | Production Evals (cost budget exhausted) | Price Drift (#635)"* — item 3

**ADRs:** 0027 (model prices are reservation ceilings) · 0079 / #499 (the ceiling comes from the peer distribution, not one endpoint) · 0070 (ceilings are checked on a schedule) · 0071 (the reservation price has a floor)
**Approach:** TDD — the refreshed observation makes the existing guard fail for the right reason *before* the ceiling moves.

## 1. Problem

The daily `Price Drift` workflow (`.github/workflows/price-drift.yml`) compares the SHIPPED reservation ceilings against the live provider catalog. Its step 5 exits 1 when a shipped ceiling sits below the dearest provider rate, and step 6 then comments on the drift issue — so a red run is the **signal**, not a broken check. Runs `43443203962` (2026-11-13) and `43243814224` (2026-11-12) are both red on `main @ a6932f8`.

Reproduced locally today, read-only:

```
deepseek/deepseek-v4.1-flash: adopted in=0.0009 out=0.0036 (37 providers) | shipped in=0.0007 out=0.0045
  distribution (output): median 0.00075 | p90 0.0012 | second-dearest 0.0018 | cap 3 x p90 = 0.0036
  OUTLIER declined, not adopted: in=0.003 out=0.012
deepseek/deepseek-v4-pro: adopted in=0.00191 out=0.00383 (13 providers) | shipped in=0.0021 out=0.0105

DRIFT: 1 shipped ceiling(s) no longer cover the dearest provider rate:
  - deepseek/deepseek-v4.1-flash input: ceiling 0.0007 is below the dearest observed 0.0009
```

Only the **input** axis has drifted. The output ceiling (0.0045) already covers its adopted rate (0.0036).

## 2. Why it matters

`admit()` reserves against the ceiling *before* a call and `settle()` trues up afterwards (ADR 0027). An under-priced ceiling therefore lets `spent + reserved + estimate` pass a cap with the money already spent — the exact failure ADR 0027 exists to prevent. This is the same mechanism #637 records as a plausible contributor to the exhausted orchestrator budget (spent 79.79 against an 80 cap).

The runtime floor (`applyPriceFloor`, #498) substitutes the dearest observation for a stale ceiling, so the *reservation* is already safe. What is wrong is the number we SHIP: the table keeps claiming a rate the catalog left behind, and the operator reading it has no idea.

## 3. Design — the new ceiling

The file's own convention (#499 / ADR 0079): the ceiling sits at the adoption cap (`3 x p90`) x 1.25, so it never binds the reservation while leaving margin for a rise between verifications.

| axis | shipped now | adopted (floor) | new ceiling | rule |
| --- | --- | --- | --- | --- |
| input | 0.0007 | **0.0009** | **0.001125** | 0.0009 x 1.25 |
| output | 0.0045 | 0.0036 | 0.0045 (unchanged) | 0.0036 x 1.25 = 0.0045 — already correct |

0.001125 is chosen for consistency with the documented rule and with the output axis's own value. A rounder 0.0012 would give marginally more headroom (ADR 0027: over-reserving is transient, under-reserving is not) — flagging it as the alternative if a round number is preferred.

## 7. Risks

- `--write` is a network read of the live catalog, so the refreshed observation is a snapshot: it can move again before the workflow re-runs. That is expected — the ceiling's margin exists for exactly that.
- A second model could drift between the refresh and the push; the guard would catch it, and it would become its own follow-up rather than being folded in here.
