# Durable Dark Factory Run History Implementation Plan

> **For Hermes:** Implement task-by-task with test-driven development after user approval.

**Goal:** Persist provider-neutral Dark Factory run summaries and lifecycle events durably, with idempotent replay handling, so the future read API and progress board have a truthful source of history.

**Architecture:** Add a focused `RunHistoryStore` contract separate from the
existing key/value `StateStore`: run acceptance, event append, and summary
projection must be atomic. Use a generic PostgreSQL adapter for configured
durable deployments and a file-backed SQLite adapter for local development and
contract tests. Keep lifecycle payloads, status rules, and query contracts
independent of Vercel and of the database vendor.

**Tech Stack:** TypeScript, Node 24, Vitest, `node:sqlite` for local SQLite, and a PostgreSQL-wire-compatible driver using a standard connection string (no Vercel SDK).

## Acceptance criteria to preserve

- A run is successful only when the #164 definition of done is satisfied: the PR is opened and all findings are resolved or explicitly accepted with a reason; the factory never merges.
- `blocked` and `aborted` remain distinct terminal outcomes; neither is success or ordinary failure.
- Optional latency and cost stay absent when not measured; never synthesize zero.
- Replayed webhook/event identities are idempotent. A deliberate new trigger gets a distinct run ID; the webhook delivery ID is a separate deduplication identity.
- Event and projected-summary persistence failures are surfaced. No caller reports success when a required write failed, and no in-memory-only default claims durability.
- Every accepted lifecycle transition has a structured event and a queryable current summary; a run has only one terminal summary.

## Verified current context

- `state.ts` has a generic JSON key/value `StateStore`; `state-provider.ts` configures fail-closed console or file-backed SQLite. The SQLite filesystem is ephemeral on Vercel and the interface has no transactional event-plus-summary operation or list/query contract.
- `metrics.ts` has provider-neutral `TaskMetric` records and an in-memory `createMetricsStore` default. `TaskMetric` supports optional `latencyMs`/`costUsd`, but has no `runId`; `BufferedMetricsRecorder` only protects its process-local buffer.
- `entry.ts` currently derives `runId` deterministically as `owner/repo#issue`, uses that same ID for dispatch state, and directly performs trigger/abort/resume plus the outbound session handoff. `runDarkFactoryDispatch()` does not currently accept GitHub's `X-GitHub-Delivery` ID.
- `app/api/github/webhook/route.ts` invokes the Dark Factory entry for qualifying issue events, but repository search found no current `X-GitHub-Delivery` handling. The route's global signature verification remains a separate security boundary.
- `dispatch.ts` already has structured attempt observations and a durable-write failure path, but no production `new Dispatcher()` call site was found. Preserve this seam and instrument it without claiming that its worker loop is currently the production runner.
- `worker-reporter.ts` validates progress/completed/question messages and stores comment IDs under `reporter:${runId}` in `StateStore`. Its store read/write failures currently fall through or are not surfaced as a durable run result; #198 must not let these failures produce a successful run summary.
- `worker-env.ts` reports aggregate metrics without a run ID. `runDefinitionOfDone()` is a separate library flow that returns `done`, `blocked`, or `refused` and includes PR/findings/round counts; it currently has no run-history writer.
- Existing focused suites include `tests/dark-factory/{entry,dispatch,metrics,worker-reporter,definition-of-done,worker-env}.test.ts` plus `tests/webhook-handler.test.ts`.

## Design decisions proposed for approval

1. Add a capability-specific `RunHistoryStore`; do not overload the `StateStore` key/value API with listing, event ordering, or cross-record transactions.
2. Use random opaque `runId`s. In one transaction, persist the initial event/summary and bind the unique GitHub delivery ID to that run. A replay returns the original run without dispatching again; a distinct deliberate delivery creates a new run ID.
3. Require stable `eventId`s for lifecycle writes. In one transaction, insert the event if new and update the run summary projection only when the event was newly accepted. Duplicate event IDs do not increment counters or replace terminal outcomes.
4. Keep immutable event history and a denormalized current `RunSummary`. A terminal transition is conditional on the run not already being terminal; conflicting late terminal writes fail visibly rather than silently changing the final outcome.
5. Use canonical, bounded statuses/stages and typed optional measurements. Do not persist raw issue bodies, worker prompts, credentials, or unbounded free text in the ledger.
6. Use the standard PostgreSQL protocol for configured durable deployments
   (providers remain swappable; no Vercel SDK). Proposed settings:
   `DF_RUN_HISTORY_DRIVER=postgres` with sensitive
   `DF_RUN_HISTORY_DATABASE_URL`, or `DF_RUN_HISTORY_DRIVER=sqlite` with
   `DF_RUN_HISTORY_DB_PATH` for local development. An unset or unknown provider
   refuses/throws; it never falls back to memory. On Vercel, the PostgreSQL URL
   must point to a durable, serverless-appropriate pooled endpoint.
7. Expose `getRun`, `listRuns`, and `listRunEvents` in the store contract with stable ordering and bounded pagination so #199 can build its authenticated API without knowing the database adapter. Do not add the API or UI in #198.
8. The run ledger is authoritative for delivery deduplication and run status; existing `StateStore` uses outside the ledger (for example reporter comment IDs) can remain separate, but a failure writing a required lifecycle event/summary must be returned as failure.

**Storage assumption for approval:** PostgreSQL is the recommended durable deployment adapter; SQLite is for local development/tests only. This intentionally does not pick a hosted vendor. If you prefer a different durable protocol, change this plan before implementation.

## Implementation tasks (TDD)

### Task 1: Define canonical run and event contracts

**Files:** Create `agent/lib/dark-factory/run-history.ts`; create `tests/dark-factory/run-history.test.ts`; re-export the public contract from `agent/lib/dark-factory/index.ts`.

1. Write failing tests for valid and invalid `RunSummary`/`RunEvent` inputs, all terminal states (`succeeded`, `failed`, `blocked`, `aborted`), optional measurements omitted versus explicit zero, and bounded identifiers/fields.
2. Add typed `RunStatus`, `RunStage`, event kinds, `RunSummary`, `RunEvent`, and normalization/validation errors. Summary fields include run/repo/issue identity, current status/stage, created/updated/terminal timestamps, attempt/review/iteration/fix-cycle counts, optional measured latency/cost, and optional PR URL.
3. Define store result types with explicit `live`/`blocked` outcome and `duplicate`/`created` indication; make failures impossible to interpret as a successful persisted write.
4. Run `npx vitest run tests/dark-factory/run-history.test.ts`; expect the new cases to pass only after the contract/normalizer is implemented.

### Task 2: Add atomic idempotent storage operations

**Files:** Create the focused run-history store/provider module(s) and `tests/dark-factory/run-history-store.test.ts`.

1. Define operations for accepting a webhook delivery, appending a lifecycle event with a summary projection update, reading one run, and listing runs/events with bounded cursor pagination.
2. Add RED tests: duplicate delivery returns the original run ID; a distinct delivery creates a distinct run; duplicate event IDs do not alter counters; a terminal outcome is immutable; and event plus summary are both visible after reopening a file-backed store.
3. Implement a transaction boundary that atomically writes delivery receipt + initial run/event, and event + summary projection. Use unique constraints for delivery IDs/event IDs and parameterized queries.
4. Test the failure path with an unreachable/closed adapter: it returns `ok: false` with no success summary. Test malformed/unknown driver configuration fails closed.

### Task 3: Implement provider adapters and schema

**Files:** Create a local SQLite adapter and a PostgreSQL adapter using a generic driver; add migration/schema code; update `package.json`/lockfile only if a PostgreSQL driver is not already available; add adapter tests.

1. Use a real temporary SQLite file for contract tests; close/reopen the adapter and prove run/event durability across instances. Do not test only with `:memory:`.
2. Implement PostgreSQL operations using the same normalized contract and transaction semantics. Keep vendor SDK imports and vendor environment names out of the domain/API contract.
3. Add explicit env resolution (proposed: `DF_RUN_HISTORY_DRIVER=sqlite|postgres`, a required SQLite path for local mode, and a required standard PostgreSQL connection URL for `postgres`). Unknown drivers and missing companion config fail closed.
4. Verify both adapters satisfy the same contract test suite; PostgreSQL-specific tests may use an injected query/transaction client, with an optional integration test when a local `DATABASE_URL` is supplied.

### Task 4: Separate webhook delivery deduplication from run identity

**Files:** Modify `app/api/github/webhook/route.ts`, `agent/lib/dark-factory/entry.ts`, and their tests.

1. Add a RED webhook/entry test sending the same `X-GitHub-Delivery` twice: only one run is accepted and only one handoff is made. A new delivery for an intentional re-trigger must produce a different run ID.
2. Require and validate the delivery identifier on Dark Factory trigger processing; pass it as a dedup key, never as `runId`. Generate an opaque run ID once and recover the same ID from the durable receipt on redelivery.
3. Resolve current run identity for abort/resume by repo+issue without inventing a new run; preserve the existing explicit resume behavior and terminal-label guard.
4. If durable acceptance fails, refuse the handoff and return an explicit error; if the run record is durable but the session handoff fails, record the truthful failed outcome without reusing the delivery to start duplicate work.

### Task 5: Instrument dispatch, worker reports, and definition-of-done

**Files:** Modify `dispatch.ts`, `worker-reporter.ts`, `worker-env.ts`, `definition-of-done.ts`, and focused tests.

1. Bridge `DispatchObserver` attempt/blocked/succeeded/failed signals to stable `RunEvent`s; a duplicate event remains a no-op.
2. Record worker progress, question/blocked, and completion messages as lifecycle events. Surface required ledger write errors; do not report a successful persisted update when storage refused it.
3. Record Definition-of-Done review-round counts/findings dispositions and map `done` to success only after PR creation plus findings disposition; map budget exhaustion to `blocked`, explicit operator stop to `aborted`, and genuine terminal errors to `failed`.
4. Populate latency/cost only when observed. Preserve `0` when explicitly measured, omit missing values, and derive counters only from accepted event records so replay cannot double-count.
5. Test that exactly one terminal summary is returned after retries/redelivery, the PR URL is retained, blocked/aborted are not folded into failure/success, and a ledger outage overrides any would-be success with an explicit error.

## Risks and boundaries

- A trigger acceptance split across separate writes can mark a delivery processed without recording its run. Keep delivery receipt, initial event, and summary creation in one transaction.
- A second terminal result can overwrite the first if the SQL update is unconditional. Enforce terminal immutability in the store, not just in callers.
- Existing deterministic `repo#issue` run IDs conflate issue identity with execution identity; migrate new runs to unique IDs while preserving repo/issue as indexed fields.
- SQLite on Vercel is not durable across function instances. Never configure it as a production durability claim; require an external PostgreSQL-compatible endpoint there.
- `Dispatcher` and `runDefinitionOfDone()` are not currently wired into one production worker call site. Instrument their existing APIs truthfully; do not claim the entire autonomous workflow is live merely because a unit-level event exists.
- #199 owns the authenticated HTTP read API and #200 owns the board; #198 supplies their durable query contract only.
- No Vercel database or billing settings are changed by this plan. If production storage is required, the operator will configure the chosen generic PostgreSQL-compatible service and Vercel environment variables.
