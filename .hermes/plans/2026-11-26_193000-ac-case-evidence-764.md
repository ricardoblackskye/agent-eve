# Certify an acceptance criterion only against evidence the plan did not supply (#764)

**Issue:** [agent-eve#764](https://github.com/ricardoblackskye/agent-eve/issues/764) (`bug`)
**Branch:** `fix/764-ac-case-verification` (from `origin/main` @ `ac08a6b`, 0 behind)
**Status:** plan only. No code until GATE 1.

## First: the diagnosis in the issue is wrong, and that has to be recorded

The issue hypothesizes that the Definition of Done verifies the test **FILE** exists and passes rather than the named
test **CASE**. Measured against the code:

- `evaluateAcTraceability` (`definition-of-done.ts:430-461`) matches the **case name** - exact, or substring either
  way (`:440-442`) - and returns `passed: match ? match.passed : false`, so an AC with no matching result is `false`.
- The DoD then refuses: `if (!verification.allPassed)` posts "Acceptance Criteria Verification Failed" and blocks
  (`:839-845`).
- Both were introduced on 2026-09-22, **two months before** the run that produced the evidence
  (2026-11-26 14:17).

So the DoD is not the defect and never was. A fix written from the issue's text would have aimed at innocent code,
which is the reason this correction comes first.

## The defect: the evidence is synthesized from the plan itself

`scripts/dark-factory-runner.ts:1495` records a PASSING result for every mapped criterion, sourced from the plan:

```text
1492-1495  // #503 AC4: record a passing result for each mapped AC. …
           recordPassingTestResults(ctx.plan, capturedTestResults);
1721-1723  … : { testResults: capturedTestResults }      ← handed to the DoD as the evidence
```

The AC's name is matched against an entry built from that same name, so every criterion certifies itself. The
matrix is the plan agreeing with the plan.

**Measured against the live case:** `WebFeedPOC#269` certified three criteria while `src/App.test.jsx` was never
written - and the file's **14 real test cases match none of those three names** under the implemented rule. Under the
DoD's own logic that run would have blocked; the passes can only have come from the synthesis.

This is **#770's defect class one layer up**. There a validator trusted the plan's own action claim; here the
traceability matrix trusts the plan's own claim that a test exists.

## Why the synthesis exists - and why that is not a reason to keep it

`#503 AC4` added it deliberately: the coding gate returns a pass/fail **boolean**, not per-case results, so there was
nothing real to record and a typed field to fill. That is an argument for capturing real results, not for inventing
them.

## The decision the plan must make

1. **Preferred:** capture real per-case results from the workspace's own test run, and record only those.
2. **Fallback** if (1) is out of scope here: stop synthesizing, let a criterion with no evidence be reported
   **unverifiable**, and block `done`. Fail-closed and blunt, but honest - the same principle already ruled on
   elsewhere in this project: a check that cannot run is a failure, not an absence of failure.

Under either option, no code path may record a result derived from the plan.

## Tasks

### Task 1 (RED) - a criterion with no evidence cannot certify

A plan whose criterion names a test case that exists nowhere is reported unverifiable and **blocks `done`**, rather
than being certified.

### Task 2 (control) - the check is not vacuous

A criterion whose named case genuinely exists and passes still certifies. Without this, "refuse everything" would
pass Task 1.

### Task 3 (RED/GREEN) - nothing may invent a result

No path records a test result derived from the plan. This is the join that has to be pinned, because the two halves
were each defensible and it was the wiring between them that produced a false certification.

### Task 4 - the second, milder finding

The sign-off comment states the check status it actually observed, or says nothing about it. Measured: it said
"The pull request checks have not reported yet." while the verdict in the same run was `done` and all six checks had
already completed green.
