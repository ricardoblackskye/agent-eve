# Size the DoD's PR-check wait for the checks it waits for (#722)

**Issue:** [agent-eve#722](https://github.com/ricardoblackskye/agent-eve/issues/722) (`bug`)
**Branch:** `fix/722-checks-wait-default` (off `origin/main` @ `32a5b03`)
**Status:** plan for GATE 1 — no code written yet.

**Goal:** raise the Definition of Done's PR-check wait ceiling from 20 to **45 minutes**, so a healthy pull
request whose slowest check takes 22–30 minutes can reach the `done` verdict instead of deferring.

**Architecture:** one number, plus the documentation that keeps it honest. The wait MECHANISM is correct and
is not touched: it polls every 15s and returns the moment nothing is unsettled, so the timeout is a ceiling
reached only by a check that never settles. No per-repository configuration is added — ADR 0087 already
reasoned that away, and it was right.

---

## Current context

### The evidence (five measurements, two sources)

| source | `e2e` observed | cap configured | outcome |
|:---|:---|:---|:---|
| #722, run `dd9b52ad`, WebFeedPOC#248 | ~30 min | 20 min | deferred, resumed, then failed on a genuinely red e2e |
| #722, run `ed387871`, WebFeedPOC#250 | ~30 min | 20 min | deferred (twice) |
| #722, run `82fc959c`, WebFeedPOC#242 | ~30 min | 20 min | deferred |
| #722, run `a37cc0c6`, WebFeedPOC#246 | ~30 min | 20 min | deferred |
| this run, `c2f3ff82`, WebFeedPOC#266 | **22 min 8 s, SUCCESS** | 20 min | deferred with **all six checks green** |

The last row is the sharpest: `e2e` started `11:03:52Z` and completed `success` at `11:26:00Z`. The wait
expired at ~`11:24`, so a wholly healthy pull request was denied `done` by ~2 minutes of cap.

### The mechanism (unchanged by this plan)

- `settlePullRequestChecks` (`agent/lib/dark-factory/definition-of-done.ts:107`) is a **sleep + REST read**
  loop: no model call, no sandbox, no worker-minutes. **Lengthening the ceiling costs zero tokens.**
- It is a **single shared deadline across all review rounds** (`scripts/dark-factory-runner.ts:2050`,
  `checkWaitDeadline`), consumed by the fix cycle's passes as well as the rounds.
- On expiry, whatever is still running is handed back AS running → `PR-CHECK-UNSETTLED:<name>` at severity
  `error` → `blocked` + `deferred`, the label follows the verdict, and the run **keeps its claim** so it stays
  resumable (`--resume`). All of that is correct behaviour and stays.

### Why the default is 20 minutes, and why that is now wrong

`agent/lib/dark-factory/pr-checks-timeout.ts` sizes 20 minutes on the stated premise that *"`e2e` and
`MegaLinter` are each around ten minutes"* on WebFeedPOC, because #659 gates the WHOLE PROJECT. The
repository got slower and the number did not move — 22 min measured today, ~30 min measured across #722's four
runs. The module's own doc comment instructs re-measuring whenever a check changes shape; that instruction was
never actioned for this change.

### The constraints that bound the decision

- **ADR 0087** (accepted): the bound is "a ceiling on a check that never settles, not a latency budget", and
  it **explicitly rejects a per-repository declaration** — *"It would put a surface on every target to work
  around a default that was simply too small."* Raising the default is therefore the ADR-consistent repair;
  adding a per-repo surface is not.
- **ADR 0090** (accepted): the deferral is a **re-entry, not a longer wait**, because *"the deployed path runs
  the loop inline inside a request, so a longer timeout is not available"*. So this ceiling is effectively a
  **local/dispatched-run lever**; the deployed label path is request-bound regardless. That is acceptable here
  — the runs this repo is proven with are `df:local-run` — and it is recorded as an open question, not solved.
- **Cost.** Zero tokens (above). It should also SAVE tokens: on `c2f3ff82` the DoD handed an unsettled check to
  the fix cycle, which ran three authoring rounds — real model calls — to "fix" a check that had not finished,
  and burned its review budget doing it (#756). Once the check settles inside the ceiling, that cycle does not
  run at all.

---

## Proposed approach

Raise the default to **45 minutes** — 50% headroom over the worst measurement (30 min), and free for a fast
repository because the wait returns as soon as the checks settle. Then make the premise non-stale by recording
today's measurements where the next person will read them.

**Deliberately out of scope:**

- **per-repository configuration** — ADR 0087's argument stands unchanged; the environment override already
  exists and is validated;
- **shortening the target's e2e** — a 22–30 minute `e2e` that four other jobs have already finished behind is
  the target repository's own subject;
- **the fix cycle's behaviour on an unsettled check** — that is #756, with its own RED already parked.

## Risks, tradeoffs, open questions

1. **A stuck check now costs up to 45 minutes before the run reports blocked**, against 20. Unaffected for any
   repository whose checks settle, which is every repository today. The run logs the bound before waiting, so
   the ceiling is visible.
2. **This will go stale again.** 45 is 50% headroom over the worst measurement, not a guarantee. The remedy is
   the re-measure instruction in the doc comment (Task 2) and the fact that ADR 0087 now records WHY its first
   figure failed.
3. **The deployed path is not fixed by this** (ADR 0090): it runs the loop inline inside a request, so a longer
   timeout is not available there. Open question for the operator: whether the deployed path needs its own
   answer, or whether #668's parked executor is that answer. Until then this improvement lands on local and
   dispatched runs.
4. **Sizing alone does not make the run self-heal.** #756 still means an unsettled check can be handed to a
   coder that authors nothing. Sizing is sufficient for the `done` path (the check settles and the DoD reads
   it green) but it does not excuse #756.
5. **#722 asked for a re-measure, so the numbers are the deliverable** as much as the constant — hence Tasks 2
   and 3 carry the measurements, not just the number.
