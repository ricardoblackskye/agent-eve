# Give every finding a root cause and an owner, so a blocked run is a decision (#743)

**Issue:** [agent-eve#743](https://github.com/ricardoblackskye/agent-eve/issues/743) (`enhancement`)
**Branch:** `feat/743-finding-owner` (from `origin/main` @ `b92c432`, 0 behind)
**Status:** plan only. No code until GATE 1.

## Why we are doing this

When a run blocks, it says *that* something failed, and "FAIL" reads as: the code is broken. On one day, four different
failures presented exactly that way - and only **one** of them was the agent's code:

| what failed  | why it really failed                                    | who could fix it                           |
|:-------------|:--------------------------------------------------------|:-------------------------------------------|
| a run's e2e  | the sandbox was reaped before the suite finished        | nobody - fixed by moving the e2e to the PR |
| a run's e2e  | the image carried no browsers                           | the image                                  |
| a run's lint | ESLint ran from the wrong directory and found no config | **the factory**                            |
| a PR's e2e   | a locator matched two elements                          | the agent - or relax the spec              |

Three of those told a human to go and fix code that was not broken. Each needed a log read and a judgement call that the
machine could have made, and each was misread at least once before the evidence settled it.

**What changes:** every finding carries a root-cause classification and the owner that follows from it, on the blocked
report a human already reads and in the ledger - so the report answers *do I fix the code, fix the factory, or wait?*

**What this does not change:** it changes no gate and no verdict. A run that blocks today still blocks. This says **why
it is allowed to**, and who can act.

## Recon, read rather than assumed

| what                            | where                                                                                                               |
|:--------------------------------|:--------------------------------------------------------------------------------------------------------------------|
| the precedent, one case of this | `developer-agent.ts:228` - *"Classify a failing suite's own output as a code fault or an environment fault (#731)"* |
| its patterns                    | `:209` - *"Patterns that name a MISSING TOOL rather than a broken assertion"*                                       |
| its consumers                   | `:291` (the gate), `:387` and `:1268` and `runner:1561` (an environment fault is not correctable by authoring code) |
| its test                        | `tests/dark-factory/e2e-environment-fault-731.test.ts`                                                              |
| the reporting surfaces          | `definition-of-done.ts` (the verdict), `worker-reporter.ts`                                                         |

**#731 is this issue's shape already, for one row of the table.** So the work is to generalize its vocabulary rather
than invent a second classifier beside it - and its tests are the pinned invariant that must keep passing.

## Design

1. **A closed vocabulary with a fail-closed default**: `code | spec | harness | image | environment | ci`, plus
   `unknown`. An unclassified finding is **`unknown`, never `code`** - defaulting to `code` is #731's error in the
   opposite direction, and it is what sent a human to fix working code.
2. **The owner follows from the cause**, never chosen separately: `agent` (code, spec), `factory` (harness, ci),
   `operator` (image, environment), and `nobody-yet` for `unknown`.
3. **The evidence stays attached.** The classification quotes the output that decided it, because that is the only
   reason the four rows above were ever distinguishable. A cause with no quoted evidence is an assertion.
4. **Vendor output enters through patterns, and the vocabulary never names a vendor.** Matching a tool's wording is
   unavoidable - #731 already matches a missing-browser message - so that matching is the adapter, and the
   classification it produces is general. The vocabulary names causes, not tools, repositories or frameworks.
5. **Generalize #731 rather than duplicate it**: its code/environment distinction becomes the `code`/`environment`
   cases of one classifier, and its consumers read the new field.

## Tasks

### Task 1 (RED) - a suite that could not run is classified `environment`, not `code`

The row that started this: a missing browser is not a broken assertion.

### Task 2 - an assertion failure is classified `code`, owned by the agent

The one row "FAIL" was always right about, asserted so the change cannot swallow it.

### Task 3 - a lint run from the wrong directory is classified `harness`, owned by the factory

The #742 row, and the one that most misled a reader: it looked exactly like broken code.

### Task 4 (the control that matters) - an unclassified finding is `unknown`, never `code`

Fail-closed. Without this the whole feature can quietly become a `code` default, which is worse than no classification.

### Task 5 - the classification carries the evidence it was decided from

Asserted as content, because a cause without its output cannot be re-examined when it is wrong.

### Task 6 - #731's existing tests still pass, unrevised

The pinned invariant. If generalizing the vocabulary breaks them, that is a finding about the design, not a fixture to
be updated - and #731's one case is a subset of this one.

### Task 7 - the classification reaches the surface (added retrospectively)

Recorded as an addition rather than folded in silently: this plan named the surface - *"the blocked report on the issue,
plus the ledger"* - and gave no task for reaching it. That is the gap that nearly shipped #784 as an inert feature: a
mechanism that cannot fire, with a green suite over it. Found by asking the same question here, *who calls the
classifier?*

- **`ReviewFinding` carries the classification**, so the thing `dod-presentation.ts` already renders is the thing that
  gains it, rather than a parallel report being built beside it.
- **The population point is the run's OWN captured output, not the PR check-runs.** Corrected while writing it: a
  `PrCheckRun` carries a name, a status and URLs - not the failure text - so classifying there would read a job title
  and return `unknown` almost every time. Fail-closed would make that honest but useless, and it would be a check that
  cannot fire - one layer below the one this task exists to prevent.
- **The population point is the RUNNER, not the Definition of Done.** My first correction said the DoD already captures
  the suite and linter output. **That was wrong, and reading the type refuted it one call later:**
  `definition-of-done.ts:329` holds `testResults?: { testFile; testCaseName; passed }[]` - pass or fail, no text. So
  neither carrier has it: not the check-runs (name and URLs), not the DoD (a boolean per case). The failure output lives
  where it is captured, in `scripts/dark-factory-runner.ts` - the lint result and reason, and the suite's own output -
  and the blocked report the runner prints is the surface a human already reads.
- **`checkRunFindings` remains the carrier**: its `ReviewFinding`s gain the classification, so the pipeline that already
  reports findings to a human is the one that carries the cause.
- **`dod-presentation` renders cause and owner** beside the finding, so a reader gets *fix the code / fix the factory /
  wait* instead of "FAIL".
- **A join assertion**: a failing check goes in, a classified finding comes out. The wiring earlier in this initiative
  did not prove that by itself - its guard reported a call present and correctly ordered while the file did not compile.
- **#691's `blockedReason` is the precedent** - the machine-readable reason a run is blocked - generalized here from one
  case to every finding.

## Out of scope

- **Fixing the causes.** The harness row is #742; the image row is #737/#725. This classifies and attributes them.
- **A per-repository or per-vendor vocabulary.** The causes are general; a new tool's output is a new pattern, not a new
  cause.
- **Changing any verdict.** Nothing here makes a run pass that would have blocked.
