# Plan — Take the target's e2e out of the sandbox (#739)

**Issue:** [#739](https://github.com/ricardoblackskye/agent-eve/issues/739) · **Branch:** `plan/739-e2e-out-of-sandbox`
**Status:** awaiting GATE 1 (plan approval)

## Goal

Stop running the target repo's e2e suite inside the sandbox. The run instead: codes against the fast unit tier,
**pushes the branch and opens a draft PR**, and lets the target's **own e2e run on that PR** — where the
Definition of Done reads it and a red check drives a fix attempt.

## Why — measured, not asserted

| evidence                            | value                                                                                                                                  |
|-------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| the declared e2e inside the sandbox | **50–56 min** (10 specs × 9 projects)                                                                                                  |
| the same suite on CI                | parallel runners, pre-installed chromium, no egress proxy                                                                              |
| sandbox ceiling                     | `DF_SANDBOX_TIMEOUT_SECONDS=3600`                                                                                                      |
| #253 (pre-#701)                     | 664 byte-identical failures, **62 worker-minutes, 3 iterations**                                                                       |
| #254 (post-#731)                    | classifier fired correctly (`FAIL (unit, e2e: the sandbox could not run it)`) **and the pod was reaped at 56 min — no verdict at all** |

That last row is the case: when the suite does not fit, we lose the information the step exists to produce.
The sandbox also runs the suite ~6–7× slower than the laptop (transparent mitmproxy egress, shared CPU).

## The guarantee, stated honestly

 bought **"no PR on a red suite"** by paying for the sandbox e2e. This trades it for
**"no DONE on a red suite"**: the PR opens as a **draft** carrying a failing check, and the run cannot
reach `done` while any required check is red.

This is not a new mechanism. **#248's run predates #701 entirely**, and its DoD already read GitHub's own
check-runs, reported `PR-CHECK-FAILED:e2e`, and said *"do not merge until its checks are green."* The path
has already carried a real e2e verdict.

## Design

**Phase 1 — the loop's gate is the unit tier.** The iteration runs the unit suite only. `decideGate` stops
taking the e2e's status as a pass/fail input, so a unit-green iteration succeeds and the existing
push-and-open-PR path is reached — which is the behaviour change the whole issue turns on.

**Phase 2 — the verdict says what happened.** `formatTestVerdict` must read as
`PASS (unit) — e2e deferred to the PR's checks`, because "not run" would be indistinguishable from a gap.
The honesty added by #701 stays; only the reason changes.

**Phase 3 — the branch and the draft PR come first.** Verify the run's own PR-creation path (it exists —
 produced PR #249 unattended) and open it as a **draft**, so a PR whose checks are still running is not
mistaken for a proposed merge.

**Phase 4 — the DoD owns the e2e verdict.** `checkRunFindings` already distinguishes a *pending* check from
a *failed* one. That distinction becomes load-bearing: a pending required check must **block**, never pass.
Only a completed-failed check raises a finding.

**Phase 5 — a red check drives ONE fix attempt.** The fix cycle (`buildFixCycleAdapter`, already wired into
the DoD path) consumes the check finding and re-codes. Bounded by the existing cap and breaker so a
persistently-red check cannot burn the budget (#722's check-wait cap is the relevant lever).

**Phase 6 — what ends a run.** `done` only when every required check is green. A check that cannot be waited
out ends the run with a **named** reason, not a silent pass.

## What happens to #731 (just merged)

The classifier and the loop-halt are **kept, not deleted** — they move level. `classifyE2eFailure` applies to
**check output** just as well as sandbox output: a CI failure where every test died the same way is an
environment fault there too. The halt's principle (an uncorrectable fault must not consume iterations) is
unchanged; only its input changes. **Repurpose in this issue; do not re-litigate it as new work.**

## Out of scope

- Which tier the *unit* suite runs per iteration (#734's remainder).
- Per-stack images (#725/#737) — still needed for coding and the unit tier, **less urgent** now the browsers
  are no longer required in the sandbox.
- Any queued/worker re-architecture (#668 is parked; do not re-propose).

## Acceptance

1. A run **never** executes the target's e2e inside the sandbox.
2. The branch and the draft PR exist **before** any e2e verdict is produced.
3. A **pending** required check cannot produce `done`; a **failed** one produces a finding and one fix attempt.
4. A run's wall-clock is **not bounded by the suite** — assertable against #253's and #254's 62 minutes.
5. Provable on the user's own machine: a run against a real issue reaching a draft PR, with the e2e verdict
   arriving from CI.

## Test plan (TDD — RED and GREEN committed separately)

- **Behaviour:** gate decision with a unit pass and no e2e attempt; verdict wording; the fix cycle triggering
  on a check finding; a run refusing `done` while a check is pending.
- **Wiring guards** (today's lesson — a unit test on a function is not evidence the product calls it):
  the runner must reach the push/PR path when the unit tier passes; the DoD must consume check findings.
- **A negative control:** a completed-failed check must not read as pending, and vice versa.

## Open decisions

- Draft PR vs labelled PR (recommend **draft** — self-describing, no label dependency).
- Whether a pending check blocks for a fixed window or until CI resolves (bounded by #722's cap).
